## 1. Определения и назначение

**Замыкание** — это функция вместе с окружением, в котором она создана. Спецификация не вводит отдельного термина: она говорит, что объекты функций «encapsulate parameterized ECMAScript code closed over a lexical environment» ([10.2 ECMAScript Function Objects](https://tc39.es/ecma262/#sec-ecmascript-function-objects)) `[spec]`. Значит, замыканием является **любая** функция JavaScript, а не только вложенная. Просто у функции верхнего уровня внешнее окружение — модуль, а он обычно живёт, пока его запись есть в кеше загрузчика, то есть в типичном сервере всё время работы процесса (оговорки — [1.1, раздел 4](../01-execution-context-scope-this/theory.md#4-причины-и-следствия-для-backend)).

| Понятие | Коротко | Уровень |
|---|---|---|
| `[[Environment]]` | внутренний слот функции: окружение, где её создали | `[spec]` |
| Связывание (binding) | запись «имя → значение» в окружении; замыкание видит **связывание**, а не копию значения | `[spec]` |
| Context (V8) | объект в куче, где V8 хранит переменные scope, захваченные вложенными функциями | `[runtime]` |
| Удержание (retention) | объект не собирается сборщиком мусора, потому что до него есть путь от корней | `[runtime]` |

**Зачем это backend-разработчику.** Замыкания встречаются в каждом сервисе: колбэки, middleware, фабрики, обёртки `retry` и `memoize`, обработчики событий. Ошибки с ними бывают двух видов:

- **логические** — функция видит не то значение, которое ожидали, потому что замыкание хранит связывание, а не снимок;
- **утечки памяти** — долгоживущий объект (EventEmitter, таймер, кеш) держит замыкание, а замыкание держит данные запроса.

**Главная мысль урока.** Отвечать на вопрос «что удерживает замыкание» нужно на двух уровнях:

- **семантика** `[spec]`: функция связана со всем лексическим окружением и видит любое имя из цепочки;
- **реализация** `[runtime]`: V8 хранит в куче только те переменные scope, на которые ссылается хотя бы одна вложенная функция, и делает это в **одном контексте на scope**. Этот контекст общий для всех замыканий scope.

Поэтому обе популярные формулировки неточны: «замыкание держит всё окружение» и «замыкание держит только то, что использует».

## 2. Внутренний механизм

### 2.1 Функция запоминает окружение: `[[Environment]]`

**Что это.** Когда выполняется объявление или выражение функции, движок создаёт объект функции и записывает в его слот `[[Environment]]` текущее окружение ([10.2.3 OrdinaryFunctionCreate](https://tc39.es/ecma262/#sec-ordinaryfunctioncreate): «Set func.[[Environment]] to envRecord»). Описание слота в таблице внутренних слотов функции: «The Environment Record that the function was closed over. Used as the outer environment when evaluating the code of the function» ([Table 26](https://tc39.es/ecma262/#sec-ecmascript-function-objects)).

**Как работает по шагам.**

1. Вызов `makeCounter()` создаёт новое окружение функции и в нём связывание `count`.
2. Выполняется стрелочная функция `() => ++count`: создаётся объект функции, его `[[Environment]]` указывает на окружение **этого вызова** `makeCounter`.
3. `makeCounter` возвращает функцию. Execution context снимается со стека, но окружение не исчезает: на него ссылается `[[Environment]]` возвращённой функции.
4. При вызове возвращённой функции её новое окружение получает `[[OuterEnv]] = [[Environment]]`, и имя `count` находится там (поиск имени — [1.1, раздел 2.2](../01-execution-context-scope-this/theory.md#22-environment-records-и-scope-chain)).

**Что гарантирует спецификация** `[spec]`. Только семантику: какие имена видит функция и какие связывания она читает и меняет. Как долго окружение физически живёт в памяти, спецификация не определяет (раздел [7.6](#76-что-спецификация-говорит-о-сборке-мусора)).

**Что зависит от реализации** `[runtime]`. V8 не создаёт окружение в куче на каждый вызов. Переменные, которые не захвачены вложенными функциями, живут в кадре стека и исчезают при возврате. Захваченные переменные размещаются в куче, в структуре «context» ([V8: Blazingly fast parsing, part 2](https://v8.dev/blog/preparser)). Подробно — в [2.4](#24-что-физически-удерживается-в-v8-контекст-scope).

**Пример.**

```js
function makeCounter() {
  let count = 0;
  return { inc: () => ++count, get: () => count };
}
const a = makeCounter(), b = makeCounter();
a.inc(); a.inc(); b.inc();
console.log(a.get(), b.get()); // 2 1
```

Каждый вызов `makeCounter` создаёт новое окружение со своим `count`. Функции `a.inc` и `a.get` созданы в одном вызове и разделяют одно связывание. Функции `b` — в другом вызове, их `count` независим.

**Типичная ошибка и диагностика.** Ожидание, что «замыкание создаётся один раз при объявлении функции в коде». Новое окружение возникает **на каждый вызов** внешней функции, а новый объект функции — на каждое выполнение выражения функции. Отсюда цена: фабрика, которая возвращает объект с десятью методами-стрелками, создаёт десять функций на каждый объект (сравнение с классом — [2.6](#26-приватное-состояние-фабрики-module-pattern-обёртки)).

**Как спрашивают.** Вопрос [M1](./interview.md#m1-что-такое-замыкание-и-почему-любая-функция-в-javascript--замыкание).

### 2.2 Замыкание хранит связывание, а не значение

**Что это.** `[[Environment]]` указывает на окружение, а окружение хранит связывания. При каждом чтении имени функция берёт **текущее** значение связывания, а не значение на момент создания функции.

**Как работает по шагам.**

1. Функция создана, когда `mode === 'dev'`.
2. Позже код присваивает `mode = 'prod'`: меняется значение того же связывания.
3. Функция вызывается, ищет `mode`, находит то же связывание и читает `'prod'`.

**Что гарантирует спецификация** `[spec]`. Поиск имени возвращает ссылку на связывание (ResolveBinding), а чтение берёт его текущее значение. Копирования при создании функции нет.

**Пример: связывание живое, но «живёт» именно связывание, а не путь к объекту.**

```js
let mode = 'dev';
const readMode = () => mode;
mode = 'prod';
console.log(readMode()); // prod

let config = { level: 'info' };
const logger = ((cfg) => () => cfg.level)(config);
config = { level: 'debug' };
console.log(logger());   // info
config.level = 'warn';
console.log(logger());   // info
```

`readMode` читает связывание `mode`, поэтому видит `'prod'`. `logger` замыкает **параметр** `cfg` — отдельное связывание, в которое при вызове попала ссылка на первый объект. Присваивание `config = { … }` меняет другое связывание, а `config.level = 'warn'` меняет уже новый объект. Замыкание видит старый объект и `'info'`.

**Почему это важно для backend.** Модуль конфигурации, который при старте передаёт `config` в фабрики (`createLogger(config)`, `createClient(config)`), а при «горячей перезагрузке» присваивает переменной новый объект, не обновит уже созданные замыкания. Работают только два способа: менять поля того же объекта (и тогда помнить про гонки) или читать конфиг через функцию-геттер при каждом обращении.

**Граничный случай: цикл.** То, что `for (var i …)` с замыканиями даёт `[3, 3, 3]`, а `for (let i …)` — `[0, 1, 2]`, — тот же механизм: у `var` одно связывание на функцию, у `let` — новое на каждую итерацию. Подробный разбор с копированием значения между итерациями — [1.1, раздел 2.5](../01-execution-context-scope-this/theory.md#25-блочный-scope-и-связывания-на-каждую-итерацию).

**Типичная ошибка.** «Замыкание запоминает значение переменной». Оно запоминает окружение. Если значение нужно зафиксировать, его копируют явно в отдельное связывание: параметром функции-фабрики или локальной `const` внутри итерации. Если в связывании объект, такая копия фиксирует только ссылку: чтобы содержимое не менялось, объект копируют (`structuredClone`) или замораживают (`Object.freeze`, поверхностно — урок 1.3).

**Как спрашивают.** Вопрос [M2](./interview.md#m2-замыкание-хранит-значение-или-переменную), фрагменты [P1](./interview.md#p1-связывание-или-значение) и [P2](./interview.md#p2-параметр-фабрики).

### 2.3 Каждый вызов — новое окружение

**Что это.** Окружение создаётся при **каждом** вызове функции и при каждом входе в блок с `let` / `const`. Все функции, созданные в одном вызове, разделяют его окружение. Функции из разных вызовов — нет.

**Пример: общее окружение у функций одного вызова.**

```js
function createSession(userId) {
  let lastSeen = Date.now();
  return {
    touch: () => { lastSeen = Date.now(); },
    idleMs: () => Date.now() - lastSeen,
    userId,
  };
}
```

`touch` и `idleMs` пишут и читают одно связывание `lastSeen`. Это и есть приватное состояние объекта: снаружи до `lastSeen` не добраться ни через свойства, ни через `Object.keys`.

**Что зависит от реализации** `[runtime]`. Общий контекст в V8 — это не только «общее состояние», но и общая судьба в памяти: если любая функция вызова жива, жив весь его контекст со всеми захваченными переменными. Разбор — следующий раздел.

**Как спрашивают.** Фрагмент [P3](./interview.md#p3-независимые-счётчики).

### 2.4 Что физически удерживается в V8: контекст scope

**Что это.** V8 решает для каждой переменной, где её хранить: в кадре стека или в контексте в куче. По статье команды V8: «VMs for languages with lexical closures allocate variables referenced from inner functions on the heap, in a structure called a "context"» и «for each variable declared in a function, we need to know whether an inner function references the variable, so we can decide whether to allocate the variable on the stack or in a heap-allocated context» ([v8.dev/blog/preparser](https://v8.dev/blog/preparser)) `[runtime]`.

**Как работает по шагам.**

1. При разборе функции V8 смотрит, на какие её переменные ссылаются **вложенные функции**.
2. Такие переменные он размещает в контексте этого scope, остальные — на стеке.
3. Контекст **один на scope**. Каждая вложенная функция, созданная в этом scope, держит ссылку на него.
4. Пока жива хотя бы одна такая функция, жив контекст и все переменные в нём, даже те, которые эта функция не читает.

**Что гарантирует спецификация, а что нет.** Спецификация не требует ни хранить всё окружение, ни выбрасывать неиспользуемые переменные. Environment Records — «purely specification mechanisms» ([9.1](https://tc39.es/ecma262/#sec-environment-records)). Всё, что ниже, — наблюдаемое поведение V8 `[runtime]`, а не гарантия языка.

**Пример: проверка удержания через WeakRef.** `WeakRef` не удерживает объект. Если после сборки мусора `deref()` вернул `undefined`, объект собран.

```js
// node --expose-gc retain.cjs
const settle = () => new Promise((r) => setImmediate(r));
async function state(ref) {
  await settle(); globalThis.gc(); await settle(); globalThis.gc();
  return ref.deref() ? 'retained' : 'collected';
}
function sharedScope() {
  const big = { payload: new Array(1e5).fill('x') };
  const small = 1;
  const useBig = () => big.payload.length;   // захватывает big
  const useSmall = () => small;              // big не читает
  return { ref: new WeakRef(big), keep: useSmall };
}
function noCapture() {
  const big = { payload: new Array(1e5).fill('x') };
  const small = 1;
  console.log(big.payload.length);           // big используется, но не замыканием
  return { ref: new WeakRef(big), keep: () => small };
}
(async () => {
  const s = sharedScope(), n = noCapture();
  console.log(await state(s.ref), await state(n.ref), typeof s.keep, typeof n.keep);
})();
// 100000
// retained collected function function
```

В `sharedScope` функцию `useBig` никто не вернул, но она ссылается на `big`. Поэтому `big` попал в контекст scope, а `useSmall` держит тот же контекст. В `noCapture` на `big` не ссылается ни одна вложенная функция: **переменная** `big` живёт в кадре стека (сам объект, как и любой объект, лежит в куче), и после возврата на объект не остаётся ссылок — он недостижим.

Почему проверка ждёт `setImmediate` перед сборкой: спецификация требует, чтобы объект, только что переданный в `new WeakRef` или прочитанный через `deref()`, оставался живым до конца текущего синхронного выполнения ([9.11 AddToKeptObjects](https://tc39.es/ecma262/#sec-addtokeptobjects), [9.10 ClearKeptObjects](https://tc39.es/ecma262/#sec-clear-kept-objects)). Без выхода из текущей задачи `deref()` вернул бы объект независимо от замыканий. Подробно о WeakRef — 1.6.

**Типичная ошибка и диагностика.** Большой объект (тело запроса, результат запроса к базе, буфер файла) и маленький долгоживущий колбэк созданы в одной функции. Колбэк регистрируется надолго (подписка, таймер, кеш), а большой объект захвачен **другой** вложенной функцией, например обработчиком ошибки. Память растёт, хотя «колбэк ничего большого не использует». Диагностика: heap snapshot и цепочка retainers, в которой между данными и колбэком стоит `system / Context` ([7.4](#74-как-увидеть-удержание-в-heap-snapshot)). Исправление `[arch]`:

- вынести долгоживущий колбэк в функцию, созданную в отдельном scope, где больших данных нет;
- передавать колбэку только нужные значения параметрами;
- обнулять связывание (`big = null`), когда данные больше не нужны: замыкание держит связывание, и после присваивания объект становится недостижимым.

**Как спрашивают.** Вопросы [SM6](./interview.md#sm6-почему-замыкание-может-удерживать-переменную-которую-не-использует) и [S12](./interview.md#s12-что-удерживает-замыкание-ответьте-на-уровне-спецификации-и-на-уровне-v8).

### 2.5 Кто держит само замыкание

**Что это.** Замыкание удерживает окружение, но само по себе не утечка. Утечка появляется, когда **долгоживущий объект** держит замыкание дольше, чем нужно. В сервере таких держателей несколько.

| Держатель | Как появляется ссылка | Когда освобождается |
|---|---|---|
| EventEmitter / EventTarget | `emitter.on(event, fn)` | `off` / `removeListener`, `once` после срабатывания, уничтожение emitter |
| Таймер | `setInterval(fn, ms)`, `setTimeout(fn, ms)` | `clearInterval` / `clearTimeout`, срабатывание `setTimeout` |
| Кеш в модуле или singleton | `cache.set(key, value)`, где value — функция или объект с данными | удаление ключа, вытеснение, TTL |
| Незавершённый Promise | `await p` или `p.then(fn)` | `p` разрешился, или сам `p` стал недостижим |
| Глобальный объект, `require.cache` | присваивание в `globalThis` или в экспорт модуля | только явное удаление |

**Пример: `setInterval` держит экземпляр, пока таймер не снят.**

```js
// node --expose-gc timer.cjs
const settle = () => new Promise((r) => setImmediate(r));
class Poller {
  constructor() {
    this.buffer = new Array(1e5).fill('x');
    this.handle = setInterval(() => this.poll(), 1000);
  }
  poll() { return this.buffer.length; }
  stop() { clearInterval(this.handle); }
}
(async () => {
  let p = new Poller();
  const ref = new WeakRef(p);
  p = null;
  await settle(); globalThis.gc(); await settle(); globalThis.gc();
  console.log('without stop:', ref.deref() ? 'retained' : 'collected');
  ref.deref().stop();
  await settle(); globalThis.gc(); await settle(); globalThis.gc();
  console.log('after stop:', ref.deref() ? 'retained' : 'collected');
})();
// without stop: retained
// after stop: collected
```

Цепочка: список таймеров Node.js → объект `Timeout` → стрелка `() => this.poll()` → `this` (экземпляр) → `buffer`. Ссылка на экземпляр в коде уже обнулена, но экземпляр жив. `timer.unref()` эту цепочку не разрывает: он только разрешает процессу завершиться, пока таймер активен (проверено запуском) `[runtime]`.

**Что зависит от среды.** Как именно хост хранит таймеры и listeners, спецификация не описывает. Поведение выше — Node.js v22 `[runtime]`. Для backend важен вывод `[arch]`: всё, что сервис регистрирует в долгоживущих объектах, он обязан снимать при остановке. В NestJS это `onModuleDestroy` / `onApplicationShutdown` (урок 7.6). Иначе модуль не собирается после пересоздания (тесты с `Test.createTestingModule`), а процесс не завершается сам.

**Пример: listener на каждый запрос.**

```js
const { EventEmitter } = require('node:events');
const configBus = new EventEmitter();                 // живёт всё время процесса
function handleRequest(req) {
  const body = Buffer.alloc(1024 * 1024);             // 1 МБ на запрос
  configBus.on('reload', () => console.log(req.id, body.length));
  return 'ok';
}
for (let id = 1; id <= 12; id++) handleRequest({ id });
console.log('listeners:', configBus.listenerCount('reload'));
// listeners: 12
// (node:…) MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 reload listeners added to [EventEmitter]. MaxListeners is 10. Use emitter.setMaxListeners() to increase limit
```

Каждый запрос добавляет listener, а listener держит `req` и `body`. Node.js предупреждает, когда на одно событие добавлено больше 10 listeners: «By default, a maximum of 10 listeners can be registered for any single event» ([events](https://nodejs.org/docs/latest-v22.x/api/events.html#eventsdefaultmaxlisteners)) `[runtime]`. Предупреждение выводится один раз для каждой пары «emitter + имя события» (проверено запуском: 30 listeners на двух событиях одного emitter и на одном событии другого дают три предупреждения) и не мешает работе. Это признак, а не защита. Увеличивать лимит через `setMaxListeners` вместо поиска причины — частая ошибка.

**Типичная ошибка и диагностика.** Признаки: `MaxListenersExceededWarning` в логах, растущий `emitter.listenerCount(name)`, линейный рост `heapUsed` с числом запросов. Исправление: подписываться один раз при старте, а данные запроса передавать через аргументы события. Если подписка на время запроса действительно нужна — снимать её в `finally` или использовать `once`.

**Как спрашивают.** Вопросы [M4](./interview.md#m4-как-замыкание-приводит-к-утечке-памяти-в-сервере), [SM7](./interview.md#sm7-почему-unref-у-таймера-не-освобождает-память), фрагмент [P7](./interview.md#p7-таймер-и-экземпляр).

### 2.6 Приватное состояние: фабрики, module pattern, обёртки

**Что это.** До `#private` (ES2022) настоящую приватность давали два способа: замыкание и `WeakMap`, где ключ — сам объект, а значение — его скрытые данные (урок 1.6). Замыкание остаётся удобным для фабрик и функций-обёрток.

**Module pattern.** Немедленно вызываемая функция создаёт окружение и возвращает только публичные функции:

```js
const idGen = (() => {
  let last = 0;
  return { next: () => ++last };
})();
console.log(idGen.next(), idGen.next(), idGen.last); // 1 2 undefined
```

В CommonJS и ESM каждый файл уже имеет собственный scope (1.1, раздел 2.6), поэтому IIFE на верхнем уровне модуля не нужна: неэкспортированная переменная модуля и так приватна. Module pattern остаётся там, где нужно несколько независимых экземпляров состояния внутри одного модуля.

**Обёртки.** `once`, `memoize`, `retry`, `timed` — функции, которые возвращают функцию и хранят состояние в замыкании:

```js
function once(fn) {
  let done = false, result;
  return function (...args) {
    if (!done) { done = true; result = fn.apply(this, args); }
    return result;
  };
}
```

Две детали, которые отличают рабочую обёртку от учебной:

- обёртка возвращает **обычную** функцию и вызывает `fn.apply(this, args)`, чтобы метод, обёрнутый в `once`, получил свой `this`. Стрелка здесь потеряла бы `this` вызова ([1.1, раздел 2.7](../01-execution-context-scope-this/theory.md#27-this));
- состояние обёртки живёт столько же, сколько сама обёрнутая функция. `memoize` над функцией модуля хранит кеш всё время работы процесса.

**Пример: кеш в замыкании растёт без предела.**

```js
function memoize(fn) {
  const cache = new Map();
  const wrapped = (key) => {
    if (!cache.has(key)) cache.set(key, fn(key));
    return cache.get(key);
  };
  wrapped.size = () => cache.size;
  return wrapped;
}
const parseUserAgent = memoize((ua) => ({ ua, mobile: ua.includes('Mobile') }));
for (let i = 0; i < 100000; i++) parseUserAgent(`Mozilla/5.0 (build ${i})`);
console.log(parseUserAgent.size()); // 100000
```

Если ключи приходят от клиента (User-Agent, query-параметры, id), кеш растёт с каждым уникальным значением и не очищается никогда. Это утечка, хотя каждая строка кода «правильная». Нужен предел: LRU с максимальным размером, TTL или кеш вне процесса (9.3). Выбор — [задача В1](./interview.md#в1-memoize-для-данных-которые-приходят-от-клиента).

**Замыкание против класса.**

```js
function createAccount(owner) {
  let balance = 0;
  return {
    owner,
    deposit(x) { balance += x; return balance; },
    get balance() { return balance; },
  };
}
class Account {
  #balance = 0;
  constructor(owner) { this.owner = owner; }
  deposit(x) { this.#balance += x; return this.#balance; }
  get balance() { return this.#balance; }
}
const f1 = createAccount('ann'), f2 = createAccount('bob');
const c1 = new Account('ann'), c2 = new Account('bob');
console.log(f1.deposit === f2.deposit, c1.deposit === c2.deposit); // false true
f1.deposit(10); c1.deposit(10);
const { deposit } = f1;
console.log(deposit(5));                                          // 15
const { deposit: d2 } = c1;
try { d2(5); } catch (e) { console.log(`${e.name}: ${e.message}`); }
// TypeError: Cannot read properties of undefined (reading '#balance')
console.log(JSON.stringify(f1), JSON.stringify(c1));
// {"owner":"ann","balance":15} {"owner":"ann"}
```

| | Фабрика с замыканием | Класс с `#private` |
|---|---|---|
| Методы | новые функции на каждый объект | одна функция на прототипе |
| `this` | не нужен: метод работает после деструктуризации | нужен: метод теряет `this` |
| Приватность | полная, по устройству scope | полная, проверяется движком (`#x`) |
| `instanceof`, наследование | нет | есть |
| Тестирование | подменить внутреннюю функцию нельзя | `jest.spyOn(Class.prototype, 'm')` |
| DI в NestJS | только через `useFactory` | основной способ (уроки 7.1, 7.2) |
| Getter в `JSON.stringify` | getter вызывается, значение попадает в JSON | `#private` в JSON не попадает |

Для backend-кода на NestJS выбор обычно в пользу класса: DI, моки и декораторы рассчитаны на классы. Фабрики с замыканиями хороши для небольших утилит и обёрток, где не нужны ни DI, ни наследование. Устройство классов и `#private` — 1.3.

**Как спрашивают.** Вопросы [M3](./interview.md#m3-как-сделать-приватное-состояние-с-помощью-замыкания-и-чем-это-отличается-от-private), [SM8](./interview.md#sm8-фабрика-с-замыканиями-или-класс-что-выбрать-для-сервиса), [SM9](./interview.md#sm9-как-написать-обёртку-once-или-memoize-которая-не-ломает-this-и-не-течёт), фрагменты [P5](./interview.md#p5-фабрика-и-класс-после-деструктуризации), [P6](./interview.md#p6-обёртка-once-и-this).

## 3. Сценарий: память сервиса растёт с каждым запросом

**Условие.** NestJS-сервис отчётов после деплоя теряет около 50 МБ памяти в час и раз в сутки перезапускается по OOM. В логах вскоре после каждого деплоя — после первых запросов к отчётам — видно `MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 progress listeners added`. Код упрощён:

```ts
@Injectable()
export class ReportService {
  constructor(private readonly jobs: JobEvents) {}   // singleton с EventEmitter внутри

  async build(req: ReportRequest) {
    const rows = await this.repo.load(req.filter);    // до 5 МБ на отчёт
    this.jobs.on('progress', (p) => this.log.debug(`${req.id}: ${p}%`));
    return this.render(rows);
  }
}
```

**Что происходит по шагам.**

1. Запрос вызывает `build`. Создаётся окружение вызова с `req` и `rows`. В V8 `rows` попадает в контекст, если на него ссылается любая вложенная функция этого вызова. Здесь на `req` ссылается стрелка-listener, поэтому `req` в контексте точно `[runtime]`.
2. `this.jobs.on('progress', …)` кладёт стрелку в массив listeners долгоживущего emitter. Стрелка держит контекст вызова, а через лексический `this` — сервис.
3. `build` возвращает результат, но listener остался. Окружение вызова не собирается: на него ссылается listener.
4. На каждый запрос — ещё один listener. После десятого Node.js один раз пишет `MaxListenersExceededWarning` `[runtime]`. Дальше рост идёт молча.
5. Если `rows` захвачен любой вложенной функцией того же вызова (в реальном коде это часто `catch`-обработчик или колбэк `map`, объявленный рядом), удерживаются и строки отчёта. Отсюда мегабайты на запрос, а не байты.

**Диагностика.**

- `this.jobs.listenerCount('progress')` растёт с числом запросов — точный признак.
- Два heap snapshot с интервалом под нагрузкой и сравнение (Comparison). В retainers растущих объектов видна цепочка `EventEmitter` → `_events` → массив listeners → `closure ""` → `system / Context` → `req` / `rows`. Пустое имя у closure — признак анонимной стрелки, переданной аргументом в `on`. Как читать snapshot — [7.4](#74-как-увидеть-удержание-в-heap-snapshot), инструменты и методика в production — 3.5.

**Решение** `[arch]`. Подписка — часть жизненного цикла сервиса, а не запроса:

- подписаться один раз в `onModuleInit`, отписаться в `onModuleDestroy`;
- id запроса передавать в данных события (`emit('progress', { reqId, p })`);
- если подписка на время запроса нужна, снимать её в `finally`, сохранив ссылку на ту же функцию (`const onProgress = …; on(…, onProgress); … finally { off(…, onProgress) }`).

**Что изменится, если заменить стрелку на `this.onProgress.bind(this)`?** Утечка останется: каждый `bind` создаёт новую функцию, и снять её без сохранённой ссылки нельзя ([1.1, раздел 2.8](../01-execution-context-scope-this/theory.md#28-потеря-this-при-передаче-метода-в-callback)). Данных запроса она держать не будет, но listeners продолжат копиться, и каждое событие будет вызывать всё больше обработчиков.

## 4. Причины и следствия для backend

**Время жизни данных определяется самым долгоживущим замыканием, которое до них дотягивается** `[runtime]`. Данные запроса должны жить столько же, сколько запрос. Любая функция, созданная во время запроса и сохранённая в объекте, который живёт дольше (модуль, singleton, emitter, таймер, кеш), продлевает жизнь данных.

**Singleton — долгоживущий держатель по определению** `[lib]` + `[arch]`. Провайдеры NestJS по умолчанию singleton (урок 7.3). Всё, что запрос кладёт в поле singleton (массив колбэков, `Map` ожидающих ответов, кеш), живёт до удаления.

**Утечка проявляется медленно и не в тестах.** Юнит-тест вызывает функцию несколько раз. Утечка в килобайтах на запрос видна только под нагрузкой через часы. Поэтому признаки утечки (`MaxListenersExceededWarning`, растущие `listenerCount` и размер кешей) стоит отдавать в метрики (11.4).

**Ожидающие операции тоже держат замыкания.** Пока Promise не разрешён, его реакции (колбэки `then` и продолжения `await`) живы, а вместе с ними данные вызова. `Map` ожидающих запросов без таймаута — та же утечка, что и забытый listener (подробнее — [7.5](#75-приостановленная-async-функция-тоже-замыкание) и 1.4).

**Замыкания — нормальная часть кода, а не проблема сами по себе** `[arch]`. Короткоживущие колбэки (`map`, `then`, middleware на время запроса) собираются вместе с запросом. Опасны только ссылки из долгоживущих объектов.

## 5. Альтернативы и компромиссы

**Состояние в замыкании, в классе или снаружи процесса** `[arch]`:

- **замыкание (фабрика)** — простая приватность, методы работают без `this`, но новые функции на каждый объект и неудобно тестировать подменой;
- **класс с `#private`** — методы на прототипе, DI и моки NestJS, наследование; теряет `this` при передаче метода (1.1);
- **внешнее хранилище (Redis, база)** — нужно, когда состояние должно быть общим для нескольких инстансов. Состояние в памяти процесса у каждого инстанса своё и пропадает при перезапуске (9.x).

**Ограничение памяти для кешей в замыканиях** `[arch]`:

- `Map` без предела — только для конечного и заранее известного набора ключей (enum, список стран);
- LRU с максимальным размером — для ключей из внешнего мира;
- `WeakMap` с ключом-объектом — когда значение нужно ровно пока жив ключ, например кеш вычислений по объекту запроса (1.6);
- TTL — когда данные устаревают (9.3).

**Подписки** `[arch]`: подписка на время жизни сервиса (`onModuleInit` / `onModuleDestroy`) вместо подписки на время запроса. Если без подписки на время запроса не обойтись — `once` или `off` в `finally` с сохранённой ссылкой.

## 6. Ошибки и заблуждения

- **«Замыкание удерживает только переменные, которые использует».** На уровне спецификации `[spec]` функция связана с окружением целиком, но физическое хранение спецификация не определяет. В V8 `[runtime]` в куче хранятся только переменные, захваченные вложенными функциями, однако в **одном контексте на scope**, общем для всех замыканий scope. Переменная, захваченная одним замыканием, живёт, пока жив любой из них: в эксперименте [2.4](#24-что-физически-удерживается-в-v8-контекст-scope) `useSmall` держит `big`, который читает только `useBig`.
- **«Замыкание удерживает всё окружение».** В V8 переменная, на которую не ссылается ни одна вложенная функция, живёт на стеке и не удерживается (`noCapture` в 2.4). Исключение — прямой `eval` и `with` ([7.2](#72-прямой-eval-и-with)).
- **«Замыкание запоминает значение переменной на момент создания».** Оно хранит ссылку на окружение и при каждом чтении берёт текущее значение связывания (2.2).
- **«Замыкание — это вложенная функция, возвращённая из другой».** По спецификации любая функция замкнута на окружение создания, включая функции верхнего уровня модуля (раздел 1).
- **«Замыкания сами по себе приводят к утечкам».** Утечку создаёт долгоживущий держатель замыкания: listener, таймер, кеш, глобальная переменная, незавершённый Promise (2.5).
- **«`unref()` у таймера освобождает память».** `unref` влияет только на то, может ли процесс завершиться. Таймер, его колбэк и всё, что колбэк удерживает, остаются в памяти до `clearInterval` (2.5).
- **«`MaxListenersExceededWarning` нужно лечить `setMaxListeners`».** Предупреждение — признак того, что listeners копятся. Поднятие лимита скрывает признак, а утечка остаётся (2.5, раздел 3).
- **«`bind` вместо стрелки решает утечку в подписке».** `bind` создаёт новую функцию при каждом вызове. Без сохранённой ссылки её не снять, listeners продолжат копиться (раздел 3).

## 7. Углубление для Strong Middle / Senior

Обязательная часть урока — разделы 1–6. Здесь — детали реализации V8 и граница спецификации, о которых спрашивают на Senior-интервью. Всё, что помечено `[runtime]`, — поведение V8 12.4 в Node.js v22.22.2, проверенное запуском. Это не контракт, оно может меняться между версиями.

### 7.1 Решение о размещении принимается при разборе кода, а не при выполнении

V8 решает, попадёт ли переменная в контекст, по **тексту** функции: есть ли вложенная функция, которая ссылается на это имя. Выполнится ли эта вложенная функция — не важно.

```js
// node --expose-gc deadbranch.cjs (helper state() — как в 2.4)
function deadBranch() {
  const big = { payload: new Array(1e5).fill('x') };
  const small = 1;
  if (Math.random() > 2) { const useBig = () => big; useBig(); } // никогда не выполняется
  return { ref: new WeakRef(big), keep: () => small };
}
// state(ref) → retained
```

Условие ложно всегда, `useBig` не создаётся ни разу, но `big` удерживается: ссылка на него есть в тексте вложенной функции, значит, переменная размещена в контексте. Это следствие того, как V8 разбирает код: решение принимается до выполнения ([v8.dev/blog/preparser](https://v8.dev/blog/preparser), раздел о переменных в preparser) `[runtime]`.

### 7.2 Прямой `eval` и `with`

Прямой `eval` может прочитать любое имя из окружения по строке, которую движок не видит при разборе ([1.1, раздел 7.8](../01-execution-context-scope-this/theory.md#78-окружения-которые-создаёт-не-объявление-имя-функционального-выражения-new-function-косвенный-eval)). Поэтому функция, внутри которой есть прямой `eval`, заставляет V8 разместить в контексте все переменные окружающих scope.

```js
function withEval() {
  const big = { payload: new Array(1e5).fill('x') };
  const useEval = (code) => eval(code);   // имени big в тексте нет
  return { ref: new WeakRef(big), keep: useEval };
}
// state(ref) → retained
```

В нестрогом коде то же делает `with`. Косвенный `eval` (`(0, eval)(code)`) так не действует: он выполняется в глобальном окружении. Ещё один довод не использовать прямой `eval` в серверном коде, кроме безопасности.

### 7.3 Цепочка контекстов: классическая утечка «replaceThing»

Если долгоживущая переменная перезаписывается объектом, который через общий контекст держит **предыдущее** значение этой же переменной, получается цепочка: каждое поколение держит предыдущее.

```js
// node --expose-gc chain.cjs (helper settle() — как в 2.4)
let current = null;
const refs = [];
function replace() {
  const previous = current;                         // захвачено функцией unused
  const unused = () => { if (previous) return 'had previous'; };
  current = {
    data: new Array(1e5).fill('x'),
    describe: () => 'session',                      // делит контекст с unused
  };
  refs.push(new WeakRef(current));
}
(async () => {
  for (let i = 0; i < 5; i++) replace();
  await settle(); globalThis.gc(); await settle(); globalThis.gc();
  console.log('alive generations:', refs.filter((r) => r.deref()).length, 'of', refs.length);
})();
// alive generations: 5 of 5
```

`describe` ничего не читает, но создана в том же вызове, что и `unused`, а `unused` захватила `previous`. Поэтому контекст вызова, на который ссылается `current.describe`, держит `previous` — прошлый `current`, который держит позапрошлый, и так далее. Если создавать `describe` в отдельной функции без `previous` в scope, живым остаётся одно поколение (проверено запуском: `alive generations: 1 of 5`). В реальном коде так выглядят «сессии» или «состояния», которые хранят ссылку на предыдущее состояние для отката.

### 7.4 Как увидеть удержание в heap snapshot

Снимок кучи показывает путь от корней до объекта: retainers. Для объекта, удержанного через контекст, путь выглядит так. Снимок записан через `v8.writeHeapSnapshot()` ([v8](https://nodejs.org/docs/latest-v22.x/api/v8.html#v8writeheapsnapshotfilenameoptions)) и разобран программно; в Chrome DevTools те же данные видны в панели Retainers.

```
BigPayload
  <- [context "big"]      system / Context        — переменная big в контексте scope
  <- [internal "context"] closure "useSmall"      — замыкание держит контекст
  <- [property "keepHandler"] global              — замыкание сохранено в глобальном объекте
```

Это снимок для кода из 2.4, где `useSmall` сохранена в `globalThis.keepHandler`. Как читать снимок:

- узел `system / Context` с ребром, названным по имени переменной, — это переменная scope, захваченная замыканием;
- над контекстом стоит одно или несколько замыканий (`closure "имя"`). Любое из них держит контекст;
- выше — настоящий держатель: массив listeners, `Timeout`, `Map` кеша, глобальное свойство. Именно его исправляют.

Стрелка, присвоенная переменной или свойству, получает имя по нему (`useSmall`) — это правило именования функций из спецификации (NamedEvaluation). Анонимная стрелка, переданная аргументом, в снимке выглядит как `closure ""`: для listener'а из раздела 3 цепочка была `EventEmitter` → `_events` → массив → `closure ""` → `system / Context` (проверено запуском). Поэтому долгоживущим колбэкам стоит давать имена. Как снимать и сравнивать снимки в production, и чем это опасно для работающего процесса, — 3.5.

### 7.5 Приостановленная async-функция тоже замыкание

Async-функция, остановленная на `await`, хранит свои локальные переменные, пока её продолжение может быть вызвано. Продолжение — это реакция на Promise, который ожидается.

```js
// node --expose-gc asyncpend.cjs (helper settle() — как в 2.4)
const pending = new Promise(() => {});        // не разрешится никогда, но на него есть ссылка
let ref1, ref2;
async function waitsOnReferenced() {
  const body = { data: new Array(1e5).fill('x') };
  ref1 = new WeakRef(body);
  await pending;
  return body.data.length;
}
async function waitsOnUnreferenced() {
  const body = { data: new Array(1e5).fill('x') };
  ref2 = new WeakRef(body);
  await new Promise(() => {});                // на этот Promise больше никто не ссылается
  return body.data.length;
}
(async () => {
  waitsOnReferenced(); waitsOnUnreferenced();
  await settle(); globalThis.gc(); await settle(); globalThis.gc();
  console.log(ref1.deref() ? 'retained' : 'collected', ref2.deref() ? 'retained' : 'collected');
  globalThis.keep = pending;
})();
// retained collected
```

Первая функция ждёт Promise, на который есть ссылка: её состояние вместе с `body` живо. Вторая ждёт Promise, недостижимый ни из какого корня: ни Promise, ни продолжение никто не сможет вызвать, и V8 собирает всё. Для сервера это значит: зависший запрос к внешней системе без таймаута держит всё состояние обработчика, пока жив сокет или запись в `Map` ожидающих ответов. Механика Promise и `await` — 1.4.

### 7.6 Что спецификация говорит о сборке мусора

Спецификация не описывает сборщик мусора. Единственное место, где она говорит о «живости» объектов, — раздел о WeakRef и FinalizationRegistry:

- «This specification does not make any guarantees that any object or symbol will be garbage collected. Objects or symbols which are not live may be released after long periods of time, or never at all» ([9.9.1](https://tc39.es/ecma262/#sec-weakref-invariants));
- «Liveness as defined here is undecidable. In practice, engines use conservative approximations such as reachability. There is expected to be significant implementation leeway» ([9.9.2 Liveness](https://tc39.es/ecma262/#sec-liveness)).

Отсюда два вывода для интервью. Утверждение «объект соберут, как только на него не будет ссылок» не следует из спецификации: гарантии сбора нет. И эксперименты с `--expose-gc` в этом уроке показывают поведение конкретной версии V8, а не язык. Устройство сборщика V8 (поколения, Scavenge, Mark-Compact) — 3.5.
