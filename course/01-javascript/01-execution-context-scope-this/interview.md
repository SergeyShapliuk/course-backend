# 1.1 Execution context, scope, hoisting, TDZ, `this` — interview

> Вопросы проверяют не определения, а умение объяснить причину, предсказать результат и разобрать граничный случай. Схема ответа: **тезис** (с чего начать на собеседовании) → **подробно** → **ограничения** → **уточняющие вопросы**. Все фрагменты кода запущены на Node.js v22.22.2; если результат зависит от CommonJS, ESM или strict mode, это указано.

---

## Конспект

- **Три независимых механизма.** Call stack — кто вызвал (рантайм). Scope chain — где искать имя (место объявления). `this` обычной функции — как вызвали (форма вызова).
- **Execution context и Environment Records — спецификационная модель.** Спецификация прямо говорит, что они не обязаны соответствовать реальным структурам движка. V8 держит одни переменные на стеке, а захваченные замыканиями — в heap-context.
- **Поиск имени:** текущее окружение → `[[OuterEnv]]` → … → глобальное. Не нашли — `ReferenceError: x is not defined`.
- **Hoisting = инстанцирование до выполнения.** `var` → `undefined`. Function declaration → готовая функция. `let` / `const` / `class` → связывание есть, но не инициализировано.
- **TDZ — время, а не место.** Обращение до инициализации даёт `ReferenceError: Cannot access 'x' before initialization`. Ловушки: `typeof`, параметры по умолчанию, `switch`, затенение, циклы ESM-импортов.
- **`for (let …)`** создаёт новое связывание на каждую итерацию и копирует в него значение. Изменение переменной в теле видно замыканиям этой итерации.
- **Верхний уровень.** Classic script: `var` / `function` → свойства глобального объекта, `this` — глобальный объект. CommonJS: всё локально в обёртке модуля, `this === module.exports`. ESM: всё локально, `this === undefined`, код строгий.
- **`this`, приоритет:** `new` > `call` / `apply` / `bind` > `obj.m()` > `f()`. Стрелочная функция собственного `this` не имеет.
- **`this` берётся из Reference.** `(obj.m)()` сохраняет `this`, а `(0, obj.m)()`, присваивание, деструктуризация и передача аргументом его теряют.
- **Strict и sloppy.** В strict mode `this` — ровно то, что передали. В sloppy `undefined` / `null` → глобальный объект, примитив → объект-обёртка. Тела классов и ESM строгие всегда.
- **`this` колбэка — контракт вызывающего:** EventEmitter (документировано), `thisArg` у `map`, таймеры Node.js (наблюдаемо, не документировано), NestJS (`callback.apply(instance, args)`).

## Вопросы уровня Middle

### M1. Чем call stack отличается от scope chain?

**Тезис.** Это две разные структуры: стек показывает, кто кого вызвал, и меняется на каждом вызове. Цепочка окружений показывает, где искать имя, и определяется местом объявления функции.

**Подробно.** При каждом вызове создаётся execution context и кладётся на стек; после `return` снимается. Цепочка окружений строится иначе. При **создании** функция запоминает окружение, где её объявили (`[[Environment]]`). При вызове её новое окружение получает это окружение как внешнее (`[[OuterEnv]]`). Поэтому функция, вызванная из глубины стека, всё равно ищет имена там, где объявлена:

```js
const level = 'module';
function show() { return level; }
function caller() { const level = 'caller'; return show(); }
console.log(caller()); // module
```

**Ограничения.** Обе структуры — спецификационные модели `[spec]`. Физически V8 использует машинный стек и heap-контексты `[runtime]`, и спецификация этого не требует.

**Уточняющие вопросы.**
- *«Что будет, если бы scope был динамическим?»* — `show` увидела бы `level` вызывающей функции и вернула бы `'caller'`. В JavaScript динамически определяется только `this` обычной функции, а не имена.
- *«Почему переполнение стека — RangeError, а не ошибка памяти?»* — так V8 сообщает о превышении лимита машинного стека. Лимит задаёт движок, а не спецификация; ошибку можно перехватить, и процесс продолжит работу.

### M2. Что такое hoisting и чем он различается для var, let, const, function и class?

**Тезис.** Код не переставляется. При входе в функцию, скрипт или модуль движок сначала создаёт все объявленные в нём связывания, а потом выполняет код. Различие — в том, инициализированы ли связывания к первой строке.

**Подробно.**
- `var` — создан и равен `undefined`.
- Function declaration — создана и уже содержит функцию, её можно вызвать до строки объявления.
- `let`, `const`, `class` — созданы, но не инициализированы; обращение бросает `ReferenceError` (TDZ).
- Функциональное выражение подчиняется правилу своей переменной: `var f = () => {}` до строки даёт `TypeError: f is not a function`, `const f = …` — `ReferenceError`.

**Ограничения.** В нестрогом коде function declaration внутри блока по Annex B ещё и создаёт `var` в функции (см. [P9](#p9-функция-в-блоке-sloppy-и-strict)).

**Уточняющие вопросы.**
- *«Если `let` не поднимается, почему внутренний `let x` затеняет внешний `x` с первой строки блока?»* — потому что он поднимается: связывание существует с начала блока, просто не инициализировано. Это лучший аргумент против формулировки «`let` не поднимается».
- *«Что будет, если `var dup` и `function dup` объявлены вместе?»* — до первой строки `dup` — функция (declaration инициализирует связывание), после выполнения `var dup = 1` — число ([P1](#p1-var-и-функция-с-одним-именем)).
- *«Зачем вообще нужен hoisting функций?»* — чтобы писать модуль сверху вниз: сначала публичная функция, ниже помощники, и взаимно рекурсивные функции без опережающих объявлений.

### M3. Что такое TDZ и почему она временная, а не пространственная?

**Тезис.** TDZ — время от создания связывания `let` / `const` / `class` до выполнения его объявления. Важно, **когда** выполняется обращение, а не где оно написано.

**Подробно.**

```js
function read() { return value; }
try { read(); } catch (e) { console.log(e.name); } // ReferenceError
let value = 42;
console.log(read());                                // 42
```

Текст функции выше объявления в обоих случаях. Первый вызов произошёл до инициализации, второй — после.

**Ограничения.** Тип ошибки гарантирует спецификация, текст сообщения — V8.

**Уточняющие вопросы.**
- *«Чем `typeof x` для переменной в TDZ отличается от `typeof` необъявленного имени?»* — необъявленное имя даёт `"undefined"` без ошибки, а связывание в TDZ — `ReferenceError`. «Безопасная проверка через `typeof`» с `let` не работает.
- *«Где TDZ проявляется неочевидно?»* — параметры по умолчанию (`function f(a = b, b = 1)`), `let` в разных `case` одного `switch`, класс, используемый выше объявления, циклы ESM-импортов.
- *«Зачем язык ввёл TDZ, а не `undefined`, как у `var`?»* — чтобы чтение до инициализации было ошибкой, а не тихим `undefined`. Для `const` это ещё и гарантия, что связывание никогда не видно с двумя разными значениями.

### M4. Как определяется this при вызове обычной функции?

**Тезис.** `this` обычной функции задаётся при каждом вызове формой вызова, а не местом объявления. Приоритет: `new` > `call` / `apply` / `bind` > вызов как метода > обычный вызов. У стрелочных функций собственного `this` нет.

**Подробно.** Слева от `()` вычисляется Reference. Если это ссылка на свойство (`obj.m`), `thisArg = obj`, иначе `undefined`. Затем OrdinaryCallBindThis:
- в strict mode `this` — ровно `thisArg`;
- в sloppy mode `undefined` / `null` заменяются глобальным объектом, примитив — объектом-обёрткой.

**Ограничения.** Глобальный `this` определяет хост `[spec]`. С каким `this` будет вызван колбэк, решает вызывающий API.

**Уточняющие вопросы.**
- *«Чему равен `this` в `obj.inner.m()`?»* — `obj.inner`: берётся база последней ссылки на свойство.
- *«Чему равен `this` у getter, объявленного в прототипе?»* — объекту, у которого читают свойство, то есть наследнику ([P14](#p14-getter-из-прототипа)).
- *«Что будет с `this`, если вызвать `who.call(42)` в sloppy и strict?»* — strict: `42`; sloppy: объект `Number`, `typeof this === 'object'`.

### M5. Почему метод, переданный как callback, теряет this?

**Тезис.** `obj.m` в позиции аргумента вычисляется в значение — сам объект функции. Связь с `obj` теряется, и принимающий код вызывает функцию как обычную: `this` равен `undefined` в strict mode или глобальному объекту в sloppy.

**Подробно.**

```js
class UserService {
  constructor() { this.users = new Map([['1', 'Ann']]); }
  find(id) { return this.users.get(id); }
}
const s = new UserService();
['1'].map(s.find);
// TypeError: Cannot read properties of undefined (reading 'users')
```

Тело класса строгое, поэтому `this === undefined`. Исправления: `(id) => s.find(id)`, `s.find.bind(s)`, `map(s.find, s)`, поле-стрелка в классе.

**Ограничения.** Если вызывающий API сам задаёт `this` (EventEmitter, `thisArg`), результат другой. Это контракт API, а не язык.

**Уточняющие вопросы.**
- *«Почему в нестрогом коде ошибка может не появиться?»* — `this` станет глобальным объектом. Чтение поля даст `undefined`, а `this.count++` создаст `globalThis.count = NaN`. Ошибка тихая и опаснее.
- *«Как по стектрейсу понять, что потерян `this`?»* — `Cannot read properties of undefined (reading '<поле экземпляра>')` внутри метода, а над ним кадр `Array.map`, `emit` или библиотечный колбэк.

## Вопросы уровня Strong Middle

### SM6. Почему for с var и замыканиями даёт одинаковые значения, а с let — разные?

**Тезис.** `var` создаёт одно связывание на всю функцию, и все замыкания читают его финальное значение. `for (let …)` по спецификации создаёт новое окружение на каждую итерацию и копирует туда текущее значение.

**Подробно.** `for (var i…)` с замыканиями `() => i` даёт `[3, 3, 3]`, с `let` — `[0, 1, 2]`. Механизм — CreatePerIterationEnvironment: перед каждой следующей итерацией создаётся новое окружение, в него копируется значение, затем выполняется инкремент.

**Ограничения.** Копируется **значение на конец итерации**, а не на момент создания замыкания. Изменение переменной в теле видно замыканию этой итерации ([P4](#p4-let-в-цикле-с-изменением-в-теле): результат `[1, 3]`).

**Уточняющие вопросы.**
- *«Как исправить версию с `var` без `let`?»* — IIFE или функция-фабрика, которая принимает `i` параметром и создаёт отдельное окружение на вызов.
- *«Есть ли per-iteration binding у `for…of` с `const`?»* — да. Каждая итерация `for (const x of arr)` получает новое связывание, поэтому `const` там допустим, хотя переприсваивать его нельзя.

### SM7. Чем отличаются верхнеуровневые var и this в classic script, CommonJS и ESM?

**Тезис.** Classic script пишет `var` и функции в глобальный объект, и `this` там — глобальный объект. CommonJS оборачивает модуль в функцию: всё локально, `this === module.exports`. ESM: всё локально, `this === undefined`, код строгий.

**Подробно.** Global Environment Record составной:
- `var` и function declarations попадают в Object Record над глобальным объектом;
- `let` / `const` / `class` — в Declarative Record: видны другим скриптам, но не являются свойствами.

Node.js выполняет CommonJS-файл внутри `(function (exports, require, module, __filename, __dirname) { … })`. Module Environment Record возвращает `undefined` как `this`. В Node.js семантику classic script можно увидеть через `vm.runInThisContext` ([P8](#p8-верхний-уровень-commonjs-esm-и-vm)).

**Ограничения.** Обёртка модуля — поведение Node.js `[runtime]`, оно задокументировано. То, что `this === module.exports`, следует из способа вызова обёртки: в документации модулей это прямо не написано, но видно из примеров в документации `events`.

**Уточняющие вопросы.**
- *«Что сломается при переносе CommonJS-файла в ESM?»* — код, который опирается на верхнеуровневый `this`, на стрелочные функции, читающие его (`() => this` вернёт `undefined` вместо `module.exports`), и на нестрогий режим (случайные глобальные переменные превратятся в `ReferenceError`).
- *«Как переносимо получить глобальный объект?»* — `globalThis`.

### SM8. Почему сообщения «is not defined» и «Cannot access before initialization» указывают на разные проблемы?

**Тезис.** `x is not defined` — связывания нет во всей цепочке окружений. `Cannot access 'x' before initialization` — связывание есть, но обращение произошло в TDZ. Первое — опечатка или отсутствующее объявление, второе — порядок выполнения.

**Подробно.** Для второго типичны четыре причины:
1. Затенение: внутренний `const x` объявлен ниже первого использования внешнего `x`.
2. Использование класса или константы при инициализации модуля выше их объявления.
3. Параметр по умолчанию, ссылающийся на следующий параметр.
4. Цикл ESM-импортов.

Вариант `x is not a function` при `var x = function…` — третий случай: связывание `var` ещё содержит `undefined`.

**Ограничения.** Тексты сообщений — формулировки V8. В других движках текст другой, тип ошибки тот же.

**Уточняющий вопрос.** *«Почему в CommonJS цикл импортов даёт `undefined`, а в ESM — ReferenceError?»* — CommonJS возвращает текущий, ещё не заполненный `module.exports`. ESM связывает импорт с самим связыванием экспортирующего модуля (live binding), а оно ещё в TDZ ([S15](#s15-как-ведёт-себя-tdz-при-циклических-импортах-в-esm-и-commonjs)).

### SM9. Что сильнее: new или bind? Можно ли перепривязать связанную функцию?

**Тезис.** `new` сильнее: связанная функция при вызове через `new` игнорирует привязанный `this`, но сохраняет привязанные аргументы. Перепривязать связанную функцию через `bind`, `call` или `apply` нельзя.

**Подробно.** `[[Call]]` связанной функции всегда передаёт `boundThis`, поэтому `call` и повторный `bind` на неё не влияют. `[[Construct]]` вызывает `Construct(target, args, newTarget)` без `boundThis`, и если `newTarget` — сама связанная функция, он заменяется на целевую ([P6](#p6-bind-call-и-new)).

**Ограничения.** Стрелочную функцию нельзя вызвать через `new` (`TypeError: … is not a constructor`), и `bind` не меняет её `this`.

**Уточняющие вопросы.**
- *«Что вернёт `p instanceof Point` для `new (Point.bind(obj))(1)`?»* — `true`: прототип нового объекта берётся из `Point`.
- *«Где на практике встречается двойной `bind`?»* — в обёртках и декораторах, которые ещё раз вызывают `bind`. Это не работает, `this` остаётся от первого `bind`.

### SM10. Какой способ сохранить this выбрать в NestJS-сервисе и почему?

**Тезис.** По умолчанию — стрелка-обёртка в месте передачи: `ids.map((id) => this.loadOne(id))`. Метод остаётся на прототипе и мокается через `jest.spyOn(Class.prototype, …)`. Для подписок, которые нужно снимать, — `bind` с сохранённой ссылкой. Поле-стрелка — только осознанно.

**Подробно.** Сам Nest вызывает handler контроллера через `callback.apply(instance, args)`, поэтому внутри handler `this` корректен `[lib]`. Проблемы появляются, когда разработчик сам передаёт метод в `map`, `on`, `setInterval` или библиотечный колбэк. Цена вариантов:
- `bind` создаёт новую функцию при каждом вызове: `off(event, this.m.bind(this))` не снимет подписку;
- поле-стрелка живёт на экземпляре, а не на прототипе: её не видит spy на прототипе, к ней не обратиться через `super`, на неё не повесить декораторы методов;
- для singleton-провайдера память не критична.

**Ограничения.** Это `[arch]`-рекомендация, а не правило языка.

**Уточняющие вопросы.**
- *«Почему поле-стрелка ломает `jest.spyOn(Service.prototype, 'method')`?»* — поле создаётся в конструкторе на каждом экземпляре, на прототипе такого свойства нет.
- *«Почему метод с `@Get()` не может быть полем-стрелкой?»* — декораторы методов Nest рассчитаны на методы класса: они работают с дескриптором метода и metadata прототипа.

### SM11. Чем стрелочная функция отличается от обычной, кроме this?

**Тезис.** Стрелочная функция не создаёт собственных `this`, `arguments`, `super` и `new.target`: все четыре берутся из окружающего кода. Она не может быть конструктором и не имеет свойства `prototype`.

**Подробно.** Спецификация: «An ArrowFunction does not define local bindings for arguments, super, this, or new.target». Проверка:
- `(() => {}).prototype === undefined`;
- в `function outer() { const inner = () => arguments[0]; return inner('inner-arg'); }` вызов `outer('outer-arg')` вернёт `'outer-arg'`;
- `new arrow()` → `TypeError: arrow is not a constructor`.

**Ограничения.** Сокращённые методы объекта (`{ m() {} }`) тоже не конструкторы, но `this` у них динамический.

**Уточняющие вопросы.**
- *«Когда стрелка как метод объекта — ошибка?»* — когда метод должен читать поля объекта через `this`: литерал не создаёт scope, и `this` будет из модуля.
- *«Когда стрелка — правильный выбор?»* — колбэки внутри методов, которым нужен `this` метода (`map`, `then`, обработчики).

## Вопросы уровня Senior

### S12. Почему переменная модульного уровня опасна в сервере и почему лексический scope не решает задачу request context?

**Тезис.** Модуль выполняется один раз на процесс, поэтому его верхнеуровневые переменные — общее состояние всех одновременных запросов. Лексический scope привязан к месту объявления, а не к запросу. Чтобы контекст запроса пережил `await` и границы модулей, нужен явный параметр или AsyncLocalStorage.

**Подробно.** `let currentUser` на уровне модуля перезапишется параллельным запросом между двумя `await` одного обработчика. То же относится к полям singleton-провайдеров Nest. Функция из другого модуля не видит локальных переменных обработчика: её цепочка окружений проходит через её собственный модуль. Варианты:
- явная передача — прозрачно, но многословно;
- AsyncLocalStorage — неявно, но привязано к асинхронной цепочке (3.7);
- REQUEST-scoped провайдеры Nest — дорого (7.3).

**Ограничения.** Кеш модулей — поведение Node.js `[runtime]`. Выбор механизма передачи контекста — `[arch]`.

**Уточняющие вопросы.**
- *«Чем `this` хуже AsyncLocalStorage для контекста запроса?»* — `this` относится к объекту, а не к запросу. У singleton-сервиса `this` один на все запросы.
- *«Где в Nest безопасно хранить состояние запроса?»* — в объекте запроса, в параметрах вызова, в ALS-хранилище или в REQUEST-scoped провайдере с осознанием цены.

### S13. Что спецификация говорит о физическом устройстве окружений и что делает V8?

**Тезис.** Спецификация описывает только наблюдаемую семантику и прямо говорит, что Environment Records и execution contexts — «purely specification mechanisms». V8 оптимизирует: переменные, не захваченные замыканиями, держит на стеке, а захваченные — в heap-структуре «context».

**Подробно.** Отсюда следуют два вывода:
1. Вопрос «где лежит переменная» корректно отвечать в два уровня: семантика `[spec]` и реализация `[runtime]`.
2. Утверждения вроде «замыкание держит всё окружение» или «держит только используемые переменные» неточны без указания уровня. Семантически функция связана с окружением. Физически V8 хранит захваченные переменные в контексте, который общий для всех замыканий одного scope (подробно в 1.2).

Источник по V8 — статья «Blazingly fast parsing, part 2: lazy parsing» (v8.dev, 2019).

**Ограничения.** Детали реализации V8 меняются между версиями и не являются контрактом.

**Уточняющие вопросы.**
- *«Почему верхний уровень скрипта всегда в куче?»* — его переменные видны другим скриптам, поэтому их нельзя держать в кадре стека.
- *«Как это влияет на утечки?»* — большой объект, захваченный одним замыканием, удерживается, пока живо любое другое замыкание того же scope (1.2).

### S14. Почему (0, obj.m)() теряет this, а (obj.m)() — нет? Где это встречается в реальном коде?

**Тезис.** `this` берётся из Reference Record. Скобки группировки возвращают Reference без изменений, а оператор запятая вычисляет значение — функцию без базы. Такую форму генерирует TypeScript 4.4+ при выводе в CommonJS: `(0, module_1.fn)()`. Так вызов импортированной функции не получает объект модуля в качестве `this`, как и в настоящих ES-модулях.

**Подробно.** Reference теряется при:
- запятой, присваивании (`(o.m = o.m)()`), тернарном операторе, `||`, `??`;
- деструктуризации, передаче аргументом, сохранении в переменную.

Сохраняется при скобках группировки и optional call `o.m?.()` ([P5](#p5-сохраняется-ли-reference)).

**Ограничения.** Форма `(0, fn)()` в выводе TypeScript описана в release notes 4.4 как breaking change.

**Уточняющие вопросы.**
- *«Что изменилось для кода, который полагался на `this` в импортированной функции?»* — раньше `this` был объектом модуля, теперь `undefined` (strict). Код, читавший `this.otherExport`, ломается.
- *«Как `obj?.m()` и `obj.m?.()` влияют на `this`?»* — обе формы сохраняют `obj` как `this`, если вызов происходит.

### S15. Как ведёт себя TDZ при циклических импортах в ESM и CommonJS?

**Тезис.** В ESM импорт — live binding на связывание экспортирующего модуля. Если в цикле модуль выполняется раньше зависимости и на верхнем уровне читает её `class` или `const`, он попадает в TDZ: `ReferenceError`. В CommonJS тот же цикл даёт `undefined`, потому что `require` возвращает ещё не заполненный `module.exports`.

**Подробно.** `a.mjs` импортирует `b.mjs`, `b.mjs` импортирует `a.mjs`. При запуске `node a.mjs` первым выполняется `b.mjs`. Его верхнеуровневое `typeof A` бросает `ReferenceError: Cannot access 'A' before initialization`. Функция из `b.mjs`, вызванная после выполнения `a.mjs`, видит класс. Это та же временная природа TDZ, только между модулями.

В NestJS-проекте на TypeScript, скомпилированном в CommonJS, цикл файлов даёт `undefined` в metadata типов конструктора. Отсюда ошибки разрешения зависимостей и необходимость `forwardRef` (7.6).

**Ограничения.** Порядок выполнения модулей определяется алгоритмом загрузки графа (3.6). Здесь важна только связь с TDZ.

**Уточняющие вопросы.**
- *«Почему функция из цикла работает, а верхний уровень — нет?»* — функция читает связывание при вызове, когда оно уже инициализировано. Верхний уровень читает его во время выполнения модуля.
- *«Как лечить?»* — убрать цикл (вынести общее в третий модуль), отложить обращение до вызова, а в Nest — исправить границы модулей и только в крайнем случае использовать `forwardRef`.

### S16. Какие правила Annex B меняют результат в Node.js и почему о них стоит знать?

**Тезис.** Annex B описывает поведение ради совместимости с вебом, и V8 его реализует. Для этой темы важны два правила:
- function declaration в блоке нестрогого кода создаёт дополнительное `var`-связывание в функции;
- `var` в `catch` с именем параметра присваивает параметру.

**Подробно.** В sloppy-файле:
- `typeof g` до блока `if (true) { function g() {} }` равен `'undefined'`, после — `'function'`; в strict mode после блока тоже `'undefined'` ([P9](#p9-функция-в-блоке-sloppy-и-strict));
- `var e = 'outer'; try { throw … } catch (e) { var e = 'inner-var'; }` оставляет внешний `e` равным `'outer'` ([P10](#p10-var-в-catch)).

**Ограничения.** Правила действуют в нестрогом коде. ESM, тела классов и файлы с `'use strict'` от них избавлены.

**Уточняющие вопросы.**
- *«Почему это аргумент за строгий режим?»* — поведение кода перестаёт зависеть от исторических исключений.
- *«Можно ли полагаться на Annex B в серверном коде?»* — Node.js его поддерживает, но код, зависящий от этих правил, непереносим и сложен для чтения.

### S17. Как this колбэка зависит от вызывающего API и где граница гарантий?

**Тезис.** Язык гарантирует механизм, а значение `this` в колбэке выбирает вызывающий код. Поэтому для каждого API нужно различать: документированный контракт, наблюдаемое поведение и отсутствие гарантий.

**Подробно.**
- **EventEmitter** — обычный listener вызывается с `this === emitter`, это задокументировано; у стрелочного listener `this` из окружающего кода.
- **`Array.prototype.map`** и аналоги — `this` равен `thisArg` из второго аргумента, по умолчанию `undefined`.
- **Таймеры Node.js** — колбэк `setTimeout` получает `this`, равный объекту `Timeout`. Это наблюдаемо (v22.22.2), но не задокументировано.
- **NestJS** — handler вызывается как `callback.apply(instance, args)` (исходники `RouterExecutionContext`).

Отдельно: глобальный `this` classic script определяет хост.

**Ограничения.** Незадокументированное поведение может измениться в любой версии.

**Уточняющие вопросы.**
- *«Почему не стоит использовать `this` в колбэке таймера?»* — значение не входит в документированный контракт и отличается от браузера, где хост вызывает колбэк иначе.
- *«Как писать колбэк, не зависящий от выбора вызывающего?»* — стрелочной функцией, которая замыкает нужный объект, или передавая данные аргументами.

## Предскажи результат

Каждый фрагмент — отдельный файл. Если не указано иное, это CommonJS-файл (`.cjs`) без `'use strict'`. Сначала ответьте сами, затем сверьтесь.

### P1. var и функция с одним именем

```js
console.log(typeof dup);
var dup = 1;
function dup() {}
console.log(typeof dup);
```

**Ответ:** `function`, затем `number`.
**Почему:** на инстанцировании function declaration записывает функцию в связывание, а повторный `var` не создаёт второго связывания. В рантайме `var dup = 1` присваивает число, строка `function dup() {}` ничего не делает.

### P2. Затенение и TDZ

```js
const port = 3000;
function start() {
  try { console.log(port); } catch (e) { console.log(e.message); }
  const port = 8080;
  return port;
}
console.log(start());
```

**Ответ:** `Cannot access 'port' before initialization`, затем `8080`.
**Почему:** внутренний `port` создан при входе в `start` и затеняет внешний с первой строки тела. Чтение произошло в его TDZ.

### P3. Параметры по умолчанию

```js
function f(a = b, b = 1) { return [a, b]; }
try { f(); } catch (e) { console.log(e.message); }
console.log(f(5));
function g(a, b = a * 2) { return [a, b]; }
console.log(g(3));
```

**Ответ:** `Cannot access 'b' before initialization`, `[ 5, 1 ]`, `[ 3, 6 ]`.
**Почему:** параметры инициализируются слева направо; при вычислении значения `a` параметр `b` ещё в TDZ. При `f(5)` значение по умолчанию для `a` не вычисляется. В `g` параметр `a` уже инициализирован.

### P4. let в цикле с изменением в теле

```js
const hs = [];
for (let k = 0; k < 4; k++) { hs.push(() => k); k++; }
console.log(hs.map((h) => h()));
```

**Ответ:** `[ 1, 3 ]`.
**Почему:** замыкание захватывает окружение итерации, а `k++` в теле меняет значение в этом же окружении. Новое окружение получает копию значения на конец итерации, инкремент заголовка выполняется уже в нём.

### P5. Сохраняется ли Reference

```js
'use strict';
const o = { m() { return this === o; } };
console.log(o.m());
console.log((o.m)());
console.log((0, o.m)());
console.log((o.m = o.m)());
console.log(o.m?.());
const { m } = o;
console.log(m());
```

**Ответ:** `true`, `true`, `false`, `false`, `true`, `false`.
**Почему:** скобки группировки и optional call сохраняют Reference на свойство. Запятая, присваивание и деструктуризация дают значение без базы, `this === undefined`.

### P6. bind, call и new

```js
'use strict';
function who() { return this; }
const obj = { name: 'obj', who };
const bound = who.bind(obj);
console.log(bound.call({}) === obj);
console.log(bound.bind({}).call({}) === obj);
function Point(x) { this.x = x; }
const BoundPoint = Point.bind({ x: 'ignored' });
const p = new BoundPoint(1);
console.log(p.x, p instanceof Point);
```

**Ответ:** `true`, `true`, `1 true`.
**Почему:** связанная функция всегда вызывает цель с `boundThis` — ни `call`, ни повторный `bind` его не меняют. `[[Construct]]` связанной функции игнорирует `boundThis`, поэтому `new` создаёт новый объект с прототипом `Point.prototype`.

### P7. Стрелка в объектном литерале

```js
const svc = {
  name: 'svc',
  regular() { return [1].map(() => this.name)[0]; },
  arrow: () => this,
};
console.log(svc.regular());
console.log(svc.arrow() === module.exports);
```

**Ответ:** `svc`, `true`.
**Почему:** стрелка внутри `regular` берёт `this` из `regular`. Стрелка `arrow` берёт `this` с верхнего уровня модуля, потому что литерал не создаёт scope. В CommonJS это `module.exports`; в ESM `svc.arrow()` вернул бы `undefined`.

### P8. Верхний уровень: CommonJS, ESM и vm

```js
// файл .cjs
var a = 1;
let b = 2;
console.log(globalThis.a, globalThis.b, this === module.exports);
const vm = require('node:vm');
vm.runInThisContext('var sa = 1; let sb = 2; function sf() {}');
console.log(globalThis.sa, globalThis.sb, typeof globalThis.sf);
console.log(vm.runInThisContext('sb'));
```

```js
// файл .mjs
var a = 1;
console.log(this, globalThis.a);
```

**Ответ.** CommonJS: `undefined undefined true`, затем `1 undefined function`, затем `2`. ESM: `undefined undefined`.
**Почему:**
- в CommonJS переменные — локальные переменные обёртки модуля, `this` — `module.exports`;
- код в `runInThisContext` выполняется как classic script: `var` и функции становятся свойствами глобального объекта, `let` — нет, но остаётся виден следующему скрипту;
- в ESM верхнеуровневый `this` — `undefined`.

### P9. Функция в блоке: sloppy и strict

```js
// вариант A — без 'use strict'
console.log(typeof g);
if (true) { function g() {} }
console.log(typeof g);
```

```js
// вариант B — с 'use strict' в начале файла
'use strict';
console.log(typeof g);
if (true) { function g() {} }
console.log(typeof g);
```

**Ответ:** A: `undefined`, `function`. B: `undefined`, `undefined`.
**Почему:** по Annex B в нестрогом коде объявление в блоке создаёт ещё и `var g` в функции. До выполнения блока оно `undefined`, после — функция. В strict mode функция существует только в блоке.

### P10. var в catch

```js
var e = 'outer';
try { throw new Error('boom'); } catch (e) { var e = 'inner-var'; }
console.log(e);
```

**Ответ:** `outer`.
**Почему:** `var e` поднят в область модуля и совпадает с внешней переменной, но присваивание внутри `catch` разрешается к ближайшему связыванию — параметру `e` блока `catch`. Annex B.3.4 разрешает такое повторное объявление.

### P11. switch и TDZ

```js
function handle(kind) {
  switch (kind) {
    case 'a': let msg = 'A'; return msg;
    case 'b': try { return msg; } catch (e) { return `${e.name}`; }
  }
}
console.log(handle('a'), handle('b'));
```

**Ответ:** `A ReferenceError`.
**Почему:** все `case` одного `switch` — один блок, `msg` существует во всём блоке. При `kind = 'b'` объявление не выполнялось, связывание в TDZ.

### P12. Вложенная функция в методе

```js
const timer = {
  start() { function inc() { return this; } return inc(); },
  startArrow() { const inc = () => this; return inc(); },
};
console.log(timer.start() === globalThis, timer.startArrow() === timer);
class T { start() { function inc() { return this; } return inc(); } }
console.log(new T().start());
```

**Ответ:** `true true`, затем `undefined`.
**Почему:**
- `inc()` — обычный вызов: в нестрогом коде `this` — глобальный объект;
- стрелка берёт `this` метода;
- внутри класса код строгий, поэтому обычный вызов даёт `undefined`.

### P13. Лексический или динамический scope

```js
const level = 'module';
function show() { return level; }
function caller() { const level = 'caller'; return show(); }
console.log(caller());
```

**Ответ:** `module`.
**Почему:** цепочка окружений `show` определена местом её объявления, окружение `caller` в неё не входит.

### P14. Getter из прототипа

```js
'use strict';
const base = { get self() { return this; } };
const child = Object.create(base);
console.log(child.self === child);
```

**Ответ:** `true`.
**Почему:** `this` — получатель операции чтения свойства (`child`), а не объект, где объявлен getter.

### P15. Поле-стрелка и метод после деструктуризации

```js
class A { m() { return this; } f = () => this; }
const a1 = new A(), a2 = new A();
console.log(a1.m === a2.m, a1.f === a2.f, 'f' in A.prototype, Object.hasOwn(a1, 'f'));
const { f, m } = a1;
console.log(f() === a1, m());
```

**Ответ:** `true false false true`, затем `true undefined`.
**Почему:**
- `m` — один метод на прототипе;
- `f` — отдельная функция на каждом экземпляре, созданная в конструкторе, где `this` — экземпляр;
- после деструктуризации `f` сохраняет лексический `this`, а `m()` вызывается без базы в строгом теле класса и возвращает `undefined`.

## Как отличить поверхностный ответ от сильного

| Тема | Поверхностный ответ | Сильный ответ |
|---|---|---|
| Hoisting | «объявления переносятся наверх; `let` не поднимается» | «связывания создаются при инстанцировании окружения; разница в инициализации: `undefined`, функция или TDZ»; объясняет затенение с первой строки блока |
| TDZ | «нельзя использовать переменную выше объявления» | «это время до инициализации»; приводит пример, где функция выше объявления работает, и называет неочевидные случаи: `typeof`, параметры по умолчанию, `switch`, циклы ESM |
| Scope | «внутренняя функция видит внешние переменные» | различает лексическую цепочку и стек; объясняет `[[Environment]]` и почему вызванная функция не видит переменные вызывающей |
| `this` | перечисляет четыре правила | выводит правила из Reference и OrdinaryCallBindThis; объясняет `(0, obj.m)()`, getter из прототипа, приоритет `new` над `bind`, разницу strict и sloppy |
| Потеря `this` | «используйте стрелочную функцию» | объясняет, почему передача аргументом теряет Reference; сравнивает четыре исправления с ценой (spy на прототипе, `off` с новой функцией после `bind`) |
