# 1.3 Прототипы и классы — interview

> Вопросы проверяют, понимаете ли вы, что происходит при чтении и записи свойства, при `new` и при наследовании, а не только синтаксис `class`. Схема ответа: **тезис** → **подробно** → **ограничения** → **уточняющие вопросы**. Все фрагменты запущены на Node.js v22.22.2 как файлы `.cjs`; примеры с TypeScript скомпилированы TypeScript 7.0.2.

**Как работать с заданиями.** Ответы спрятаны под раскрывающимися блоками.

1. Прочитайте вопрос или фрагмент кода.
2. Запишите или проговорите ответ: результат **и механизм**.
3. Раскройте эталон и сравните оба пункта.

Вопросы M — Middle, SM — Strong Middle, S — Senior.

## Конспект

- **`prototype` и `[[Prototype]]` — разные вещи.** `F.prototype` — свойство функции, которое станет `[[Prototype]]` экземпляров. Прототип самого объекта — `Object.getPrototypeOf(obj)`.
- **Чтение** идёт по цепочке прототипов, getter вызывается с исходным объектом как `this`.
- **Запись** создаёт собственное свойство только на основном пути. Setter в прототипе перехватывает присваивание, non-writable свойство в прототипе запрещает его (strict — `TypeError`, sloppy — тишина).
- **`new`:** прототип из `newTarget.prototype` (или `Object.prototype`, если там не объект) → новый объект → тело → объект из `return` заменяет экземпляр, примитив игнорируется.
- **`class` — синтаксис над прототипами плюс новое:** строгий режим, TDZ, запрет вызова без `new`, неперечисляемые методы, наследование статики, `this` в наследнике только после `super()`, поля, `#private`, `static {}`.
- **Порядок:** статика — при вычислении класса. Поля базы → тело базы → поля наследника (сразу после `super()`) → тело наследника.
- **Поля определяются, а не присваиваются (DefineField):** затеняют setter базы и перезаписывают то, что записал базовый конструктор. TypeScript включает это по умолчанию с `target` ES2022+.
- **`#private`** — бренд-проверка по `[[PrivateElements]]`, не свойство. Не проходит через Proxy. `private` в TypeScript стирается.
- **`Object.freeze` поверхностный.** Дескрипторы по умолчанию: литерал — всё `true`, `defineProperty` — всё `false`, методы класса — неперечисляемые.
- **Proxy** перехватывает внутренние методы, Reflect пересылает их с receiver. Proxy непрозрачен для `#private`, идентичности и внутренних слотов.
- **`instanceof`** ищет объект `C.prototype` в цепочке. Две копии класса (дубль пакета, другой realm) дают `false`.

## Вопросы уровня Middle

### M1. Что такое прототип и чем prototype отличается от [[Prototype]]?

<details>
<summary>Ответ</summary>

**Тезис.** У каждого объекта есть внутренняя ссылка `[[Prototype]]` на другой объект или `null`, и по этой цепочке ищутся свойства. `prototype` — обычное свойство функции-конструктора: объект, который станет `[[Prototype]]` экземпляров, созданных через `new`.

**Подробно.**
- `Object.getPrototypeOf(new User()) === User.prototype`.
- У самой функции `User` прототип — `Function.prototype`.
- У класса `Admin extends User` прототип — сам `User`: так наследуются статические методы.

**Ограничения.** `obj.__proto__` — accessor на `Object.prototype`. У объекта без прототипа (`Object.create(null)`) его нет. Переносимый способ — `Object.getPrototypeOf` / `Object.setPrototypeOf`.

**Уточняющие вопросы.**
- *«Чьё свойство `constructor` у экземпляра?»* — `User.prototype`. У экземпляра собственного `constructor` нет ([P1](#p1-prototype-и-prototype)).
- *«Где лежат методы класса?»* — на `Class.prototype`, один экземпляр функции на все объекты.

</details>

### M2. Что происходит при new по шагам?

<details>
<summary>Ответ</summary>

**Тезис.** Берётся прототип из `newTarget.prototype`, создаётся объект с этим прототипом, он становится `this`, выполняется тело. Если тело вернуло объект, результатом будет этот объект, иначе — созданный.

**Подробно.**
- Если `F.prototype` не объект, новый экземпляр получит `Object.prototype`.
- `new.target` внутри функции равен конструктору при `new` и `undefined` при обычном вызове.
- У класса перед телом базового конструктора инициализируются поля экземпляра.

**Ограничения.** Для класса-наследника объект создаёт не он сам, а базовый конструктор при вызове `super()` ([SM6](#sm6-почему-в-конструкторе-наследника-нельзя-обратиться-к-this-до-super)).

**Уточняющие вопросы.**
- *«Что будет, если конструктор вернёт объект?»* — `new` вернёт его, экземпляр с прототипом класса потеряется, `instanceof` даст `false`.
- *«А если вернёт число?»* — у базового конструктора возврат игнорируется. У конструктора наследника — `TypeError` ([P5](#p5-конструктор-наследника)).

</details>

### M3. Чем class отличается от функции-конструктора?

<details>
<summary>Ответ</summary>

**Тезис.** Объектная модель та же: `typeof Class === 'function'`, методы на `prototype`, экземпляры связаны через `[[Prototype]]`. Отличия — в конкретном наборе механизмов.

**Подробно.**
- тело класса всегда строгое;
- имя класса в TDZ до объявления;
- вызов без `new` — `TypeError`;
- методы неперечисляемые;
- статика наследуется (`Object.getPrototypeOf(Child) === Parent`);
- у наследника нет `this` до `super()`;
- есть поля, `#private`, `static {}`, `super` в методах.

**Ограничения.** Поэтому «класс — новая объектная модель» — неверно, а «класс — просто сахар» — тоже неточно: `#private`, порядок `super()` и define-семантику полей на функциях не воспроизвести.

**Уточняющие вопросы.**
- *«Почему методы класса не видны в `for…in`?»* — они создаются с `enumerable: false`. Методы, присвоенные `F.prototype.m = …`, перечисляемые.
- *«Можно ли вызвать конструктор класса через `call`?»* — нет, это тот же `[[Call]]`, и он бросает `TypeError` для `[[IsClassConstructor]]`.

</details>

### M4. Как работает поиск свойства и чем in отличается от Object.hasOwn?

<details>
<summary>Ответ</summary>

**Тезис.** Чтение смотрит собственные свойства объекта, затем идёт по цепочке прототипов до `null`. `in` учитывает всю цепочку, `Object.hasOwn` — только сам объект.

**Подробно.**
- `'toString' in {}` — `true` (унаследовано), `Object.hasOwn({}, 'toString')` — `false`.
- `for…in` перечисляет и унаследованные перечисляемые свойства, `Object.keys` и `JSON.stringify` — только собственные перечисляемые.

**Ограничения.** Для ключей из внешнего мира (`req.query`, JSON) проверка `in` или `obj[key]` находит `constructor`, `toString`, `__proto__`. Нужны `Object.hasOwn`, `Map` или `Object.create(null)`.

**Уточняющий вопрос.** *«Зачем `Object.hasOwn`, если есть `obj.hasOwnProperty`?»* — у объекта без прототипа метода `hasOwnProperty` нет, а у объекта из JSON его можно затенить собственным ключом `"hasOwnProperty"`.

</details>

### M5. Делает ли Object.freeze объект неизменяемым?

<details>
<summary>Ответ</summary>

**Тезис.** Только сам объект и только его собственные свойства: нельзя добавлять, удалять и менять. Вложенные объекты остаются изменяемыми.

**Подробно.** `Object.freeze({ db: { host } })` запрещает `cfg.port = 2`, но разрешает `cfg.db.host = 'b'`. Для глубокой неизменяемости нужна рекурсивная заморозка или выдача копий. Нарушение в строгом коде — `TypeError`, в нестрогом — тихое игнорирование.

**Ограничения.** `const` запрещает только переприсвоить связывание (1.1). `readonly` в TypeScript — проверка компилятора, в рантайме её нет.

**Уточняющие вопросы.**
- *«Чем `seal` отличается от `freeze`?»* — `seal` запрещает добавлять и удалять свойства, но разрешает менять значения.
- *«Как заморозка прототипа влияет на наследников?»* — присваивание наследнику свойства с тем же именем перестаёт создавать собственное свойство ([SM11](#sm11-когда-присваивание-objx--v-не-создаёт-собственное-свойство)).

</details>

## Вопросы уровня Strong Middle

### SM6. Почему в конструкторе наследника нельзя обратиться к this до super()?

<details>
<summary>Ответ</summary>

**Тезис.** Конструктор класса с `extends` — «derived»: он не создаёт объект сам. Объект создаёт базовый конструктор при вызове `super()`, и только тогда связывается `this`. До этого `this` не инициализирован, обращение — `ReferenceError`.

**Подробно.** Так устроено, чтобы базовый конструктор мог создать особый объект: `extends Array` получает настоящий массив, `extends Error` — объект ошибки со стеком. Конструктор наследника обязан вызвать `super()` или вернуть объект. Вернуть примитив — `TypeError`.

**Ограничения.** Текст ошибки — V8: «Must call super constructor in derived class before accessing 'this' or returning from derived constructor».

**Уточняющие вопросы.**
- *«Когда инициализируются поля наследника?»* — сразу после возврата из `super()`.
- *«Можно ли вызвать метод до `super()`?»* — статический или внешний — можно, метод экземпляра — нет: для него нужен `this`.

</details>

### SM7. В каком порядке инициализируются поля, статические блоки и конструкторы при наследовании?

<details>
<summary>Ответ</summary>

**Тезис.** Статические поля и блоки — один раз при вычислении класса, в порядке записи. При `new Child()`: код конструктора наследника до `super()` → поля базы → тело конструктора базы → поля наследника → остаток тела наследника.

**Подробно.** Следствие: базовый конструктор не видит поля наследника. Если база вызывает переопределённый метод, он выполнится раньше, чем поля наследника получат значения, и увидит `undefined` ([P4](#p4-метод-из-базового-конструктора)).

**Ограничения.** Это порядок для нативных классов. При старых настройках TypeScript (`useDefineForClassFields: false`) поля выводятся присваиваниями после `super()`, порядок тот же, но семантика присваивания другая (SM8).

**Уточняющий вопрос.** *«Как избежать проблемы с методом в конструкторе базы?»* — не вызывать переопределяемые методы из конструктора; выносить инициализацию в отдельный шаг (`init()` после создания, `onModuleInit` в NestJS).

</details>

### SM8. Почему поле, объявленное в подклассе, затирает значение из базового конструктора?

<details>
<summary>Ответ</summary>

**Тезис.** Поля класса определяются через DefineField сразу после `super()`. Определение перезаписывает собственное свойство, которое создал базовый конструктор, а поле без инициализатора определяется со значением `undefined`.

**Подробно.** `class User extends Base { name; }` при `Base`, делающем `Object.assign(this, data)`, даёт `name === undefined`. В TypeScript это появилось при `target` ES2022+: по документации `useDefineForClassFields` там `true` по умолчанию, и компилятор выводит нативные поля. При ES2021 поле без инициализатора не выводилось, а поле с инициализатором превращалось в присваивание после `super()` и всё равно перезаписывало значение.

**Ограничения.** Поля, объявленные в базовом классе, не страдают: они инициализируются до тела его конструктора ([P6](#p6-поля-и-objectassign-в-базовом-конструкторе)).

**Уточняющие вопросы.**
- *«Как исправить?»* — заполнять экземпляр после конструирования (`Object.assign(new Dto(), data)`, `plainToInstance`), объявлять поля, которые заполняет база, через `declare`, не полагаться на `useDefineForClassFields: false`.
- *«Почему поле затеняет setter базы?»* — определение не ищет по цепочке и не вызывает setter, а создаёт собственное data-свойство.

</details>

### SM9. Чем #private отличается от private в TypeScript и почему #private ломается через Proxy?

<details>
<summary>Ответ</summary>

**Тезис.** `private` — проверка компилятора, после компиляции это обычное свойство. `#x` — элемент во внутреннем списке `[[PrivateElements]]` экземпляра, доступ к нему движок проверяет в рантайме по «бренду» класса. У Proxy такого списка нет, поэтому метод, вызванный с `this = proxy`, падает на `this.#x`.

**Подробно.** `#x in obj` — штатная бренд-проверка. Обход для Proxy — handler, который вызывает методы с `this = target` (`Reflect.get(t, k, t)` и `bind(t)`). Цена: методы перестают видеть Proxy, и перехват внутренних обращений теряется ([P7](#p7-private-и-proxy)).

**Ограничения.** `#private` не попадает в `JSON.stringify`, `Object.keys` и не наследуется через прототип — это тоже отличия от `private`.

**Уточняющие вопросы.**
- *«Что выбрать для NestJS-сервиса?»* — обычно `private readonly` в конструкторе: DI, моки и сериализация работают с обычными свойствами. `#private` — когда нужна защита в рантайме и объект не оборачивают в Proxy.
- *«Почему ошибка не при создании Proxy?»* — Proxy создаётся без проверок. Ошибка возникает при первом обращении к `#`-полю.

</details>

### SM10. Почему instanceof может вернуть false для «правильного» объекта?

<details>
<summary>Ответ</summary>

**Тезис.** `instanceof` ищет в цепочке прототипов объекта конкретный объект `C.prototype`. Если класс существует в двух экземплярах, у объекта в цепочке «чужой» прототип.

**Подробно.** Источники дублей:
- две копии пакета в `node_modules`;
- модуль, выполненный дважды (разные пути, query в ESM URL, очистка `require.cache`);
- другой realm (`vm.runInNewContext`).

Для массивов есть `Array.isArray`, который не зависит от прототипа. Для ошибок надёжнее проверять поле (`code`, `name`).

**Ограничения.** Класс может переопределить проверку через `static [Symbol.hasInstance]`, поэтому `instanceof` — протокол, а не гарантия типа.

**Уточняющий вопрос.** *«Как найти дубль пакета?»* — `npm ls имя-пакета` покажет несколько версий. Лечится выравниванием версий или `overrides`.

</details>

### SM11. Когда присваивание obj.x = v не создаёт собственное свойство?

<details>
<summary>Ответ</summary>

**Тезис.** Когда в цепочке прототипов найден setter для `x` — вызывается он. И когда найдено non-writable data-свойство `x` — присваивание запрещено: `TypeError` в строгом коде, тишина в нестрогом.

**Подробно.** Это шаги OrdinarySetWithOwnDescriptor. Собственное свойство в таких случаях создаёт только `Object.defineProperty`, который по цепочке не ищет. Практическое следствие — «заморозка» встроенных прототипов ради защиты от prototype pollution ломает код, который присваивает `obj.toString = …` или `obj.constructor = …` ([P3](#p3-присваивание-при-setter-и-read-only-в-прототипе)).

**Ограничения.** Поля класса не подчиняются этим правилам: они определяются, а не присваиваются.

**Уточняющий вопрос.** *«Как называют это поведение?»* — неформально «override mistake». Спецификация сохраняет его ради совместимости со старым кодом.

</details>

## Вопросы уровня Senior

### S12. Как устроены Proxy и Reflect и зачем нужен receiver?

<details>
<summary>Ответ</summary>

**Тезис.** Proxy подменяет внутренние методы объекта (`[[Get]]`, `[[Set]]`, `[[Has]]`, `[[DefineOwnProperty]]` и другие) вызовами ловушек handler'а. Reflect даёт те же операции как функции. Receiver — объект, который станет `this` для getter и setter. Ловушка, которая не передаёт его дальше, ломает наследование через Proxy.

**Подробно.**
- `Reflect.get(t, k, receiver)` выполняет getter с исходным объектом, `t[k]` — с target ([P12](#p12-receiver-в-proxy)).
- Инварианты: ловушка не может вернуть другое значение для non-configurable non-writable свойства target — `TypeError`.
- Proxy непрозрачен: `proxy !== target`, `#private` не работает, методы `Map` / `Set` / `Date` на Proxy бросают `TypeError` из-за отсутствия внутренних слотов.

**Ограничения.** Proxy заметно дороже обычного доступа к свойству: каждая операция — вызов функции. Для горячих путей — измерять.

**Уточняющие вопросы.**
- *«Где Proxy уместен в backend?»* — ленивые объекты и прокси к удалённым ресурсам, отслеживание изменений, валидация конфигурации при обращении, моки в тестах.
- *«Почему библиотеки создают Proxy с пустым target?»* — чтобы не упираться в инварианты замороженных или non-configurable свойств и хранить данные отдельно.

</details>

### S13. Как работает super и почему скопированный метод вызывает «чужой» super?

<details>
<summary>Ответ</summary>

**Тезис.** Метод, объявленный синтаксисом метода, получает `[[HomeObject]]` — объект, где он объявлен. `super.m()` ищет `m` в прототипе `[[HomeObject]]`, а не в прототипе `this`. Поэтому `super` статический, а `this` динамический.

**Подробно.** Метод `AuditRepo.prototype.save`, присвоенный другому объекту, продолжает вызывать `Repo.prototype.save` через `super`, хотя у нового объекта другой прототип ([P10](#p10-super-у-скопированного-метода)).

**Ограничения.** Стрелочные функции и функции, присвоенные свойству (`obj.m = function () {}`), `[[HomeObject]]` не получают, и `super` в них — синтаксическая ошибка (кроме стрелок внутри методов, которые берут `super` из метода).

**Уточняющий вопрос.** *«Как это влияет на mixin'ы, которые копируют методы?»* — `super` в скопированных методах указывает в исходную иерархию. Mixin'ы в виде фабрик классов (`(Base) => class extends Base {}`) этой проблемы не имеют: метод объявляется в новом классе.

</details>

### S14. Как устроена prototype pollution на уровне механизма?

<details>
<summary>Ответ</summary>

**Тезис.** `JSON.parse` создаёт собственное свойство с ключом `"__proto__"`. Наивный deep merge читает `target['__proto__']`, а это accessor на `Object.prototype`, который возвращает сам `Object.prototype`. Рекурсия записывает свойства злоумышленника прямо в `Object.prototype`, и они появляются у всех объектов процесса.

**Подробно.** Три смысла `__proto__`:
- accessor на `Object.prototype`;
- специальный синтаксис в литерале `{ __proto__: x }`;
- обычный ключ в `JSON.parse`.

Атака использует разницу между первым и третьим ([P11](#p11-prototype-pollution-через-merge)). Защита на уровне механизма:
- пропускать ключи `__proto__`, `constructor`, `prototype`;
- собирать результат в `Object.create(null)` или `Map`;
- проверять схемой входные данные до слияния.

**Ограничения.** Заморозка `Object.prototype` закрывает атаку, но меняет семантику присваивания для всего кода (SM11). Это решение для процесса целиком, а не для одного модуля.

**Уточняющий вопрос.** *«Почему это опасно на сервере больше, чем в браузере?»* — процесс общий для всех пользователей: загрязнение от одного запроса влияет на проверки (`if (user.isAdmin)`) во всех последующих. Подробно — 8.5.

</details>

### S15. Наследование, композиция или mixin в NestJS: как выбрать?

<details>
<summary>Ответ</summary>

**Тезис.** Композиция через DI — основной способ строить сервисы. Наследование — для общей реализации в узкой иерархии (базовый репозиторий, базовое исключение). Фабрики классов — когда нужно комбинировать поведение и метаданные. Так устроены mapped types NestJS.

**Подробно.**
- Наследование связывает жизненный цикл: порядок `super()` и полей, конструктор базы с зависимостями, которые наследник обязан передать.
- Композиция заменяет «является» на «использует»: зависимость подменяется в тестах и в модуле.
- `PartialType(CreateDto)` по документации NestJS возвращает класс, от которого наследуются через `extends`: так наследуются и поля, и metadata валидации.

**Ограничения.** Фабрики классов сложнее типизировать и отлаживать. Глубокая цепочка mixin'ов даёт тот же хрупкий базовый класс.

**Уточняющий вопрос.** *«Когда наследование провайдеров Nest создаёт проблемы с DI?»* — когда наследник объявляет собственный конструктор. Тогда `design:paramtypes` наследника содержит только его параметры, и зависимости базы он обязан перечислить сам и передать в `super()`. Без собственного конструктора metadata базы находится через цепочку прототипов конструкторов (проверено с TypeScript 7.0.2 и `reflect-metadata`: `getMetadata` у наследника вернул типы базы, `hasOwnMetadata` — `false`). Механика DI — урок 7.1.

</details>

### S16. Что меняет компиляция TypeScript в семантике классов и как это проверить?

<details>
<summary>Ответ</summary>

**Тезис.** Компилятор может выводить классы и поля не так, как их определяет спецификация: поля как присваивания (`useDefineForClassFields: false`), классы как функции (старый `target` ES5). Проверка — смотреть выведенный JavaScript и запускать его.

**Подробно.**
- `useDefineForClassFields` по умолчанию `true` для `target` ES2022+ (документация TSConfig). Это меняет поведение полей наследника (раздел 3 theory).
- При `target` ES5 в TypeScript 5.9.3 наследник `Error` терял прототип: `instanceof HttpError` давал `false`. Отсюда старые `Object.setPrototypeOf(this, new.target.prototype)`. В TypeScript 7.0.2 `target=ES5` удалён (ошибка TS5108).
- Тело класса всегда строгое только в нативном классе. При компиляции в функции строгость задаёт `alwaysStrict`.

**Ограничения.** Значения по умолчанию флагов меняются между версиями TypeScript. Надёжнее явно задавать их в `tsconfig.json` (урок 2.5).

**Уточняющий вопрос.** *«Как поймать такие регрессии?»* — интеграционные тесты на реальных DTO без моков, снапшот выведенного JS для базовых классов, явный `target` и флаги полей в `tsconfig`.

</details>

## Предскажи результат

Каждый фрагмент — отдельный файл `.cjs` без `'use strict'`, если не указано иное. Запишите точный вывод и одну-две фразы о механизме, затем раскройте ответ. P1–P9 — обязательная часть, P10–P12 опираются на углубление.

### P1. prototype и [[Prototype]]

```js
function User() {}
const u = new User();
class Admin extends User {}
const a = new Admin();
console.log(Object.getPrototypeOf(u) === User.prototype, Object.getPrototypeOf(User) === User.prototype);
console.log(Object.getPrototypeOf(Admin) === User, Object.getPrototypeOf(Admin.prototype) === User.prototype);
console.log(a instanceof User, a.constructor === Admin, Object.hasOwn(a, 'constructor'));
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `true false`, `true true`, `true true false`.

**Почему:** прототип экземпляра — `User.prototype`, а прототип функции `User` — `Function.prototype`. `extends` связывает две цепочки: `Admin → User` (статика) и `Admin.prototype → User.prototype` (методы). `constructor` у экземпляра унаследован от `Admin.prototype`.

</details>

### P2. new и возврат из конструктора

```js
function A() { this.v = 1; return { v: 2 }; }
function B() { this.v = 1; return 2; }
function C() { this.v = 1; }
C.prototype = 42;
const a = new A(), b = new B(), c = new C();
console.log(a.v, a instanceof A, b.v, b instanceof B, Object.getPrototypeOf(c) === Object.prototype);
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `2 false 1 true true`.

**Почему:** объект из `return` заменяет экземпляр, примитив игнорируется. `C.prototype` не объект, поэтому экземпляр получает `Object.prototype`.

</details>

### P3. Присваивание при setter и read-only в прототипе

```js
const defaults = Object.freeze({ timeout: 1000 });
const cfg = Object.create(defaults);
cfg.timeout = 5000;
const logger = { set level(v) { this._lvl = v.toUpperCase(); } };
const child = Object.create(logger);
child.level = 'debug';
console.log(cfg.timeout, Object.keys(cfg), Object.keys(child), child.level);
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `1000 [] [ '_lvl' ] undefined`.

**Почему:** замороженный прототип делает `timeout` non-writable, и в нестрогом файле присваивание наследнику молча не выполняется. Setter в прототипе перехватил присваивание и записал `_lvl`. Getter для `level` нет, поэтому чтение даёт `undefined`. В строгом режиме первое присваивание бросило бы `TypeError`.

</details>

### P4. Метод из базового конструктора

```js
class Base {
  constructor() { this.init(); }
  init() {}
}
class Svc extends Base {
  prefix = 'svc';
  init() { console.log('init:', this.prefix); }
}
const s = new Svc();
console.log('after:', s.prefix);
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `init: undefined`, затем `after: svc`.

**Почему:** конструктор базы вызывает переопределённый `init` до того, как `super()` вернул управление. Поля наследника инициализируются только после возврата из `super()`.

</details>

### P5. Конструктор наследника

```js
class A {}
class B extends A { constructor() { super(); return 1; } }
class C extends A { constructor() { return { c: true }; } }
class D { constructor() { return 1; } }
for (const K of [B, C, D]) {
  try { const x = new K(); console.log(K.name, x instanceof K, JSON.stringify(x)); }
  catch (e) { console.log(K.name, e.name); }
}
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `B TypeError`, `C false {"c":true}`, `D true {}`.

**Почему:** конструктор наследника может вернуть только объект или ничего. Возврат объекта без `super()` допустим и заменяет экземпляр. Базовый конструктор игнорирует возвращённый примитив.

</details>

### P6. Поля и Object.assign в базовом конструкторе

```js
class Base {
  id;
  constructor(data) { Object.assign(this, data); }
}
class Order extends Base {
  total;
  status = 'new';
}
const o = new Order({ id: 1, total: 99, status: 'paid' });
console.log(o.id, o.total, o.status);
const o2 = Object.assign(new Order({}), { id: 2, total: 50, status: 'paid' });
console.log(o2.id, o2.total, o2.status);
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `1 undefined new`, затем `2 50 paid`.

**Почему:** поле базы `id` инициализируется до тела её конструктора, и `Object.assign` его перезаписывает. Поля наследника `total` и `status` определяются после `super()` и затирают скопированные значения. Во втором варианте данные копируются после конструирования, когда все поля уже определены.

</details>

### P7. #private и Proxy

```js
class Counter {
  #n = 0;
  inc() { return ++this.#n; }
}
const c = new Counter();
const logged = new Proxy(c, {
  get(t, k, r) { const v = Reflect.get(t, k, r); return typeof v === 'function' ? v.bind(t) : v; },
});
const naive = new Proxy(c, {});
console.log(logged.inc(), logged.inc());
try { naive.inc(); } catch (e) { console.log(e.name); }
console.log(c.inc());
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `1 2`, `TypeError`, `3`.

**Почему:** `logged` привязывает методы к target, и `this.#n` читается у настоящего экземпляра. `naive` вызывает `inc` с `this = proxy`, у которого нет `#n`. Счётчик общий, потому что оба Proxy обёрнуты вокруг одного объекта.

</details>

### P8. Дескрипторы по умолчанию

```js
class Dto { a = 1; get b() { return 2; } m() {} }
const d = new Dto();
Object.defineProperty(d, 'c', { value: 3 });
console.log(Object.keys(d), JSON.stringify(d), d.c);
d.c = 4;
console.log(d.c);
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `[ 'a' ] {"a":1} 3`, затем `3`.

**Почему:** поле `a` — собственное перечисляемое свойство. Getter `b` и метод `m` лежат на прототипе. `c`, созданное через `defineProperty` без атрибутов, неперечисляемое и non-writable. Присваивание в нестрогом коде молча игнорируется.

</details>

### P9. instanceof

```js
const vm = require('node:vm');
const fromCtx = vm.runInNewContext('({ list: [1], when: new Date(0) })');
console.log(fromCtx.list instanceof Array, Array.isArray(fromCtx.list), fromCtx.when instanceof Date);
class NotFound extends Error {}
const e = new NotFound('missing');
console.log(e instanceof NotFound, e.name, `${e}`);
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `false true false`, затем `true Error Error: missing`.

**Почему:** объекты из другого realm связаны с его `Array.prototype` и `Date.prototype`. `Array.isArray` проверяет вид объекта, а не прототип. `name` подкласс унаследовал от `Error.prototype`, его нужно задавать явно.

</details>

### P10. super у скопированного метода

```js
class Repo { save() { return 'Repo.save'; } }
class AuditRepo extends Repo { save() { return `audit > ${super.save()}`; } }
class Other { save() { return 'Other.save'; } }
const borrowed = Object.create(Other.prototype);
borrowed.save = AuditRepo.prototype.save;
console.log(new AuditRepo().save(), borrowed.save());
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `audit > Repo.save audit > Repo.save`.

**Почему:** `super` ищет в прототипе `[[HomeObject]]` метода — `AuditRepo.prototype`, то есть в `Repo.prototype`. Прототип объекта `borrowed` не важен.

</details>

### P11. Prototype pollution через merge

```js
function merge(target, source) {
  for (const key of Object.keys(source)) {
    const v = source[key];
    target[key] = v && typeof v === 'object' ? merge(target[key] || {}, v) : v;
  }
  return target;
}
const input = JSON.parse('{"theme":"dark","__proto__":{"debug":true}}');
const settings = merge({}, input);
console.log(settings.theme, settings.debug, ({}).debug, Object.keys(settings));
delete Object.prototype.debug;
const safe = merge(Object.create(null), input);
console.log(({}).debug, Object.keys(safe), Object.getPrototypeOf(safe));
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `dark true true [ 'theme' ]`, затем `undefined [ 'theme', '__proto__' ] null`.

**Почему:** `JSON.parse` дал собственный ключ `__proto__`. `target['__proto__']` у обычного объекта — accessor, возвращающий `Object.prototype`, и merge записывает `debug` в него: свойство видно у любого объекта. У объекта без прототипа accessor'а нет, `__proto__` становится обычным ключом.

</details>

### P12. receiver в Proxy

```js
const base = { _who: 'base', get who() { return this._who; } };
const p1 = new Proxy(base, { get: (t, k, r) => Reflect.get(t, k, r) });
const p2 = new Proxy(base, { get: (t, k) => t[k] });
const child1 = Object.setPrototypeOf({ _who: 'child' }, p1);
const child2 = Object.setPrototypeOf({ _who: 'child' }, p2);
console.log(child1.who, child2.who, p1.who);
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `child base base`.

**Почему:** при чтении `child1.who` receiver — `child1`, и `Reflect.get` передаёт его getter'у. `t[k]` выполняет чтение заново с receiver = target. При прямом чтении `p1.who` receiver — сам Proxy, а `_who` через него находится в `base`.

</details>

## Задачи на выбор решения

Формат: условия → варианты → выбор → при каких условиях выбор перестаёт быть верным.

### В1. Как создавать DTO из данных запроса

**Условия.** NestJS-сервис, TypeScript 7 с `target` ES2022, `ValidationPipe` с class-validator. Во внутреннем коде DTO создаются вручную: базовый класс `BaseDto` с `constructor(data) { Object.assign(this, data) }`, у наследников поля с декораторами валидации и значениями по умолчанию (`status = 'new'`).

**Варианты:** оставить конструктор базы и выключить `useDefineForClassFields`; объявить поля через `declare`; создавать экземпляр без данных и заполнять после конструирования (`Object.assign(new Dto(), data)` или `plainToInstance`).

<details>
<summary>Разбор</summary>

**Выбор.** Заполнять после конструирования: `plainToInstance(Dto, data)` из class-transformer (его же вызывает `ValidationPipe` в NestJS v12.1.3, исходник `validation.pipe.ts`) или `Object.assign(new Dto(), data)`. Поля и значения по умолчанию определяются конструктором, данные запроса перезаписывают их. Это совпадает со стандартной семантикой полей и не зависит от флагов компилятора.

**Почему не остальные.**
- `useDefineForClassFields: false` возвращает нестандартную семантику. Код начнёт вести себя по-разному в TypeScript и в нативном JS, а значения по умолчанию в наследнике всё равно затрут данные (присваивание после `super()`).
- `declare` решает проблему только для полей без значения по умолчанию и без декораторов, которым нужна реальная property. Значение по умолчанию с `declare` объявить нельзя.

**Когда выбор перестаёт быть верным.**
- DTO неизменяемые, и данные должны попадать в конструктор (`readonly` поля, явный конструктор с параметрами). Тогда конструктор наследника принимает данные и присваивает поля после `super()` явно.
- Нужна максимальная производительность создания миллионов объектов. `plainToInstance` дорог, а ручной конструктор с параметрами быстрее.

</details>

### В2. Как распознавать тип ошибки в exception filter

**Условия.** Монорепозиторий, общий пакет `@company/errors` с классами `NotFoundError`, `ConflictError`. Сервисы подключают его через свои `package.json`, версии иногда расходятся. Глобальный exception filter NestJS переводит доменные ошибки в HTTP-ответы.

**Варианты:** `err instanceof NotFoundError`; проверка поля `err.code` (строковый код); `static [Symbol.hasInstance]` в базовом классе, проверяющий `code`.

<details>
<summary>Разбор</summary>

**Выбор.** Проверка по полю-дискриминатору: у базового класса `DomainError` есть `code`, filter делает `switch (err.code)`. Это не зависит от того, сколько копий пакета в дереве и из какого модуля пришёл объект. Для TypeScript поле удобно описать union-типом кодов.

**Почему не `instanceof`.** При двух версиях пакета в `node_modules` классы — разные объекты, и `instanceof` из filter молча возвращает `false`. Ошибка превращается в 500 вместо 404, и это видно только в production после обновления зависимостей.

**Почему не `Symbol.hasInstance`.** Он сохраняет привычный синтаксис, но прячет нестандартную проверку. Читатель ожидает от `instanceof` проверку прототипа. И метод должен быть в той копии класса, с которой сравнивают, поэтому проблема с версиями остаётся.

**Когда выбор перестаёт быть верным.** Если пакет ошибок гарантированно один (монолит, одна версия через `overrides`, проверка `npm ls` в CI), `instanceof` проще и даёт сужение типа в TypeScript без ручных type guards.

</details>

## Как отличить поверхностный ответ от сильного

| Тема | Поверхностный ответ | Сильный ответ |
|---|---|---|
| Прототипы | «объекты наследуют от прототипа» | различает `prototype` и `[[Prototype]]`, рисует обе цепочки `extends` |
| Запись свойства | «присваивание создаёт свойство» | называет setter и read-only в прототипе, разницу strict и sloppy, `defineProperty` как обход |
| `class` | «сахар над функциями» или «новая модель» | перечисляет конкретные отличия и показывает, что модель та же |
| Порядок инициализации | не знает | объясняет поля базы → тело базы → поля наследника и последствия для методов из конструктора |
| Поля | «то же, что `this.x =`» | DefineField, затенение setter, затирание данных базы, связь с `useDefineForClassFields` и `target` |
| `#private` | «приватное поле» | бренд-проверка, `#x in obj`, Proxy, отличие от `private` в TypeScript |
| `instanceof` | «проверяет класс» | ищет `C.prototype` в цепочке; дубли пакетов и realm; `Array.isArray`; проверка по полю |
| Безопасность | не связывает с темой | объясняет prototype pollution через три смысла `__proto__` и защиту `Object.create(null)` / `Map` |
