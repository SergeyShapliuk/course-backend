## Ключевая формулировка урока

**Куча V8 делится на поколения: молодое собирает копирующий Scavenge, цена которого пропорциональна живым объектам, старое — Mark-Sweep-Compact, который благодаря Orinoco маркирует в основном конкурентно и останавливает поток только на короткую финальную фазу. GC освобождает лишь недостижимое, поэтому утечка — всегда забытая ссылка, и доказывают её растущим полом кучи после полных сборок и сравнением heap snapshot. Лимит кучи по умолчанию — около половины доступной памяти, но учитывает ли Node.js лимит контейнера, зависит от версии libuv: лимит кучи нужно явно ставить ниже лимита контейнера с запасом на внешнюю память, иначе процесс убивает ядро без единого следа.**

## Как проверялись примеры

Каждый пример с выводом запущен на **Node.js v22.22.2** (V8 12.4, Windows 10 x64, 16 ГБ RAM) как файл `.cjs`. Поведение в контейнере проверено в **Docker Desktop** (Linux 6.18, cgroup v2, VM на 8 ГБ и 12 CPU) на официальных образах `node:18.18.0-slim`, `node:18.20.8-slim`, `node:20.2.0-slim`, `node:20.3.0-slim`, `node:22.22.2-slim` и `node:24.22.0-slim`; размеры пространств кучи — также на v24.22.0 и v26.12.0 под Windows. Время, паузы GC и память — одного запуска; повторы отличались не больше чем на 10 %. Формулы лимита кучи сверены с исходниками Node.js v22.22.2 (`src/api/environment.cc`) и V8 12.4 (`deps/v8/src/heap/heap.cc`, `heap.h`), история версий — с CHANGELOG_V18, V22, V24 и ChangeLog libuv, механизмы GC — с блогом V8, API — с документацией Node.js latest-v22.x и latest-v24.x — 2026-10-16.
