# 3.4 Streams и backpressure — interview

> Вопросы проверяют, понимаете ли вы, когда стрим действительно ограничивает память, как работает backpressure, чем `pipeline` отличается от `pipe`, и умеете ли обработать большие данные и загрузки файлов, не держа их в памяти. Схема ответа: **тезис** → **подробно** → **ограничения** → **уточняющие вопросы**. Все фрагменты запущены на Node.js v22.22.2 (Windows 10 x64) как файлы `.cjs`; значения по умолчанию сверены с v18.20.8 и v24.22.0. Загрузки — multer 2.4.0, busboy 1.6.0, Express 5.3.0. Что блокирует цикл — [3.2](../02-event-loop/), пул потоков — [3.3](../03-thread-pool-workers-cluster/), память вне кучи — 3.5.

**Как работать с заданиями.** Ответы спрятаны под раскрывающимися блоками.

1. Прочитайте вопрос или фрагмент кода.
2. Запишите или проговорите ответ: результат **и механизм**.
3. Раскройте эталон и сравните оба пункта.

Вопросы M — Middle, SM — Strong Middle, S — Senior.

## Конспект

- **Типы:** Readable, Writable, Duplex (две независимые стороны, `net.Socket`), Transform (`zlib`, `crypto`). `req` — Readable, `res` — Writable, `fetch().body` — Web `ReadableStream`.
- **`highWaterMark`** — порог, а не лимит. Байты; в object mode — объекты (16); для строк — кодовые единицы UTF-16. По умолчанию: v18 — 16 КиБ; v22+ — 64 КиБ, **на Windows 16 КиБ**; `fs.createReadStream` — 64 КиБ.
- **Backpressure:** `write()` → `false` = «подожди `'drain'`», данные при этом приняты. Игнорирование `false` копит всё в буфере приёмника (250 МБ в эксперименте).
- **`on('data', c => dst.write(c))`** теряет backpressure. **`pipeline`** и **`for await`** соблюдают его.
- **`pipe`** не закрывает приёмник при ошибке источника. **`pipeline`** уничтожает все звенья и даёт одну точку обработки ошибки; генератор может быть звеном.
- **`for await` + `break`** уничтожает стрим. Стрим читает с опережением на `highWaterMark`.
- **Buffer:** `alloc` — нули, `allocUnsafe` — неинициализированная память; маленькие Buffer делят 8-килобайтный пул. Buffer — вне кучи V8: `--max-old-space-size` его не ограничивает.
- **UTF-8 на границе чанков** — `setEncoding` или `StringDecoder`. Строка не длиннее 0x1fffffe8 кодовых единиц.
- **Большие файлы:** 146 МБ целиком — 423 МБ RSS и OOM при куче 100 МБ; потоком — 64–67 МБ.
- **Загрузки:** multer без опций держит файл в `file.buffer` (300 МБ → 332 МБ RSS); потоком через busboy — 77 МБ; лимиты `fileSize`.

## Вопросы уровня Middle

### M1. Какие бывают стримы в Node.js и где они встречаются в backend?

<details>
<summary>Ответ</summary>

**Тезис.** Readable (источник), Writable (приёмник), Duplex (обе стороны, независимые), Transform (Duplex, где выход вычисляется из входа). В backend: тело входящего запроса — Readable, ответ — Writable, сокет — Duplex, `zlib` и `crypto` — Transform, файлы — `fs.createReadStream`/`createWriteStream`, курсоры баз данных — Readable.

**Подробно.** Все стримы — EventEmitter: `'data'`, `'end'`, `'error'`, `'close'` у Readable; `'drain'`, `'finish'`, `'error'`, `'close'` у Writable. У Duplex и Transform два внутренних буфера. Ответ `fetch` — Web `ReadableStream`, другой API того же назначения.

**Ограничения.** Стрим не гарантирует экономию памяти: многие API поверх стримов собирают данные целиком (`res.json()` у `fetch`, multer без настроек).

**Уточняющий вопрос.** *«Зачем вообще стримы, если можно прочитать файл целиком?»* — память не зависит от объёма данных, работа делится на маленькие колбэки, и цикл остаётся отзывчивым; обработка начинается до получения всех данных.

</details>

### M2. Что такое backpressure и как его соблюсти при ручной записи?

<details>
<summary>Ответ</summary>

**Тезис.** Backpressure — механизм, который заставляет быстрый источник ждать медленный приёмник. Writable сообщает о заполненном буфере, возвращая `false` из `write()`, а о готовности — событием `'drain'`. При ручной записи после `false` нужно дождаться `'drain'`.

**Подробно.**

```js
for (const chunk of chunks) {
  if (!writable.write(chunk)) await once(writable, 'drain');
}
writable.end();
```

Без ожидания 4000 чанков по 64 КиБ оказались в буфере приёмника целиком: `writableLength` 250 МБ, RSS 286 МБ. С ожиданием — не больше одного чанка, 64 КБ ([P2](#p2-игнорирование-false)).

**Ограничения.** `write()` после `false` всё равно принимает данные: это просьба, а не отказ.

**Уточняющие вопросы.**
- *«Как сделать то же без ручного кода?»* — `pipeline(source, destination)` или `for await` по источнику с ожиданием записи.
- *«Где backpressure в HTTP?»* — `res.write()` тоже возвращает `false`, когда клиент читает медленнее, чем пишет сервер.

</details>

### M3. Чем pipe отличается от stream.pipeline?

<details>
<summary>Ответ</summary>

**Тезис.** Оба соблюдают backpressure. `pipe` не обрабатывает ошибки: при ошибке источника приёмник остаётся открытым, а ошибку нужно ловить на каждом стриме. `pipeline` при ошибке в любом звене вызывает `destroy(err)` на всех и передаёт ошибку в колбэк или отклоняет Promise.

**Подробно.** Документация `pipe`: «the Writable destination is not closed automatically… it will be necessary to manually close each stream in order to prevent memory leaks». В эксперименте после ошибки источника с `pipe` приёмник остался `destroyed: false`, с `pipeline` — уничтожен, а колбэк получил `upstream failed` ([P3](#p3-ошибка-источника-pipe-и-pipeline)).

**Ограничения.** `pipeline` оставляет обработчики событий на стримах; стримы после неё повторно не используют.

**Уточняющие вопросы.**
- *«Что будет с `a.pipe(b).pipe(c).on('error', …)`?»* — обработчик стоит только на `c`; ошибка `a` или `b` станет необработанной и уронит процесс.
- *«Какую версию `pipeline` использовать?»* — `pipeline` из `node:stream/promises` с `await` и `try/catch`.

</details>

### M4. Чем Buffer.alloc отличается от Buffer.allocUnsafe?

<details>
<summary>Ответ</summary>

**Тезис.** `Buffer.alloc(n)` выделяет память и заполняет её нулями. `Buffer.allocUnsafe(n)` не инициализирует память: «The contents of the newly created Buffer are unknown and may contain sensitive data». Он быстрее, но буфер нужно полностью перезаписать перед чтением.

**Подробно.**
- Маленькие `allocUnsafe` и `Buffer.from` берутся из общего пула 8 КиБ: несколько Buffer делят один `ArrayBuffer` ([P7](#p7-buffer-из-общего-пула)).
- `Buffer.from(string)` кодирует строку (по умолчанию UTF-8), `buf.toString(encoding)` декодирует.
- Buffer — подкласс `Uint8Array`, память находится вне кучи V8.

**Ограничения.** `--zero-fill-buffers` заставляет `allocUnsafe` обнулять память, ценой производительности.

**Уточняющий вопрос.** *«Когда `allocUnsafe` оправдан?»* — когда буфер сразу целиком перезаписывается (чтение из файла в него, копирование), и аллокаций много.

</details>

### M5. Почему при чтении файла по чанкам портится кириллица?

<details>
<summary>Ответ</summary>

**Тезис.** В UTF-8 кириллическая буква занимает 2 байта, а чанк может закончиться посреди символа. `chunk.toString()` на неполной последовательности подставляет символ замены `�`. Нужно декодировать с учётом хвоста предыдущего чанка: `readable.setEncoding('utf8')` или `StringDecoder`.

**Подробно.** «привет» (12 байт), разбитое на 5 + 7 байт: по отдельности — `пр��вет`, через `StringDecoder` или `setEncoding` — `привет` ([P5](#p5-граница-посреди-символа)).

**Ограничения.** Ошибка проявляется, только если граница попала на многобайтовый символ: тесты на латинице её не ловят.

**Уточняющий вопрос.** *«А если склеить Buffer-ы, а потом декодировать?»* — корректно, но тогда весь объём в памяти; для потоковой обработки — декодер.

</details>

## Вопросы уровня Strong Middle

### SM6. Что такое highWaterMark и почему это порог, а не лимит?

<details>
<summary>Ответ</summary>

**Тезис.** `highWaterMark` — объём внутреннего буфера, после которого стрим просит остановиться: Readable перестаёт читать из источника, Writable возвращает `false` из `write()`. Документация: «a threshold, not a limit… It does not enforce a strict memory limitation». Если источник игнорирует сигнал, буфер растёт.

**Подробно.**
- Единицы: байты; объекты в object mode; кодовые единицы UTF-16 для строковых стримов.
- По умолчанию в v22.22.2: 64 КиБ, но на Windows 16 КиБ (`lib/internal/streams/state.js`), 16 объектов в object mode, 64 КиБ у `fs.createReadStream`. В v18 — 16 КиБ везде ([P10](#p10-highwatermark-по-умолчанию)).
- Документация v22 пишет 64 КиБ без оговорки про Windows — расхождение с исходником.

**Ограничения.** В object mode порог не зависит от размера объектов: 16 объектов по 10 МБ — 160 МБ.

**Уточняющие вопросы.**
- *«Сколько памяти держит цепочка из трёх Transform?»* — порядка суммы порогов всех буферов (у Transform их два) плюс внутреннее состояние звеньев.
- *«Стоит ли увеличивать порог?»* — для пропускной способности при больших чанках иногда да; это меняет память на число системных вызовов. Измерять.

</details>

### SM7. Почему обработчик data с write внутри приводит к росту памяти?

<details>
<summary>Ответ</summary>

**Тезис.** Подписка на `'data'` переводит Readable в режим потока: данные идут так быстро, как их отдаёт источник. Возвращаемое значение `write()` в обработчике никто не проверяет, и всё, что приёмник не успел записать, копится в его буфере.

**Подробно.** `source.on('data', (c) => dst.write(c))` — типичная ошибка проксирования загрузок и копирования между сокетами. Исправления: `pipeline(source, dst)`; `for await (const c of source) { if (!dst.write(c)) await once(dst, 'drain'); }`; или ручные `pause()`/`resume()` по сигналам.

**Ограничения.** На быстром приёмнике и малых данных проблема незаметна — она проявляется при медленном клиенте или диске и больших объёмах.

**Уточняющий вопрос.** *«Как это обнаружить?»* — память растёт во время передачи и падает после; `writableLength` приёмника растёт; в heap snapshot — много Buffer в очереди Writable (3.5).

</details>

### SM8. Как работает for await по стриму и что происходит при break?

<details>
<summary>Ответ</summary>

**Тезис.** Readable — асинхронно итерируемый объект: `for await` берёт чанки по одному и соблюдает backpressure — стрим дочитывает, только когда буфер ниже порога. `break`, `return` или исключение в цикле уничтожают стрим.

**Подробно.** Object mode, `highWaterMark: 4`, источник на 1000 объектов, `break` на третьем: произведено 7 объектов (опережающее чтение), стрим `destroyed === true` ([P4](#p4-break-в-for-await)). Для курсора базы это значит, что выход из цикла закрывает курсор, если драйвер реализует `destroy`.

**Ограничения.** Асинхронная работа внутри цикла выполняется последовательно: одна запись за раз. Для параллельной обработки — пачки с ограничением concurrency ([3.3](../03-thread-pool-workers-cluster/)).

**Уточняющий вопрос.** *«Чем `for await` удобнее `pipeline`?»* — для обработки записей с асинхронной логикой (запись в базу, вызовы API) без написания Transform; `pipeline` удобнее для цепочек стримов и гарантированной очистки при ошибке.

</details>

### SM9. Чем Web Streams отличаются от стримов Node.js и когда какие использовать?

<details>
<summary>Ответ</summary>

**Тезис.** Web Streams — реализация стандарта WHATWG (`ReadableStream`, `WritableStream`, `TransformStream`), та же, что в браузере. Backpressure выражен через `desiredSize` и Promise, ошибки — через отклонённые Promise. Классические стримы — EventEmitter. В Node.js оба вида совместимы через `Readable.fromWeb`/`toWeb` и `pipeline`.

**Подробно.**
- `fetch().body` — Web `ReadableStream`; `pipeline(res.body, fs.createWriteStream(...))` работает напрямую.
- Web Streams API не экспериментальный с v21.0.0; `fromWeb`/`toWeb` стабильны с v22.17.0; `pipeline` принимает Web Streams с v19.7.0 / v18.16.0.
- Экосистема Node.js (fs, zlib, драйверы, multer) — классические стримы.

**Ограничения.** Переход между видами стоит небольших накладных расходов на обёртку.

**Уточняющий вопрос.** *«Что выбрать для библиотеки, которая работает и в Node.js, и в edge-рантайме?»* — Web Streams: они есть везде, классические стримы — только в Node.js.

</details>

### SM10. Как обработать файл на 10 ГБ в 100 МБ памяти?

<details>
<summary>Ответ</summary>

**Тезис.** Читать потоком, разбирать на записи по мере поступления, агрегировать или писать результат тоже потоком с backpressure. Память определяется размером чанка и состоянием обработки, а не размером файла.

**Подробно.**
- CSV на 146 МБ: `readFile` + `split` — пик RSS 423 МБ и падение при `--max-old-space-size=100`; `readline` поверх `fs.createReadStream` с `for await` — 64–67 МБ ([P6](#p6-readfile-против-потока-при-лимите-кучи)).
- Строку больше 0x1fffffe8 кодовых единиц (~512 МБ) V8 не создаст вовсе: `ERR_STRING_TOO_LONG`.
- Запись в базу — пачками с ожиданием каждой пачки, а не `Promise.all` по всем строкам.

**Ограничения.** Потоковый вариант немного медленнее (2,1 с против 1,9 с) из-за накладных расходов на чанки.

**Уточняющие вопросы.**
- *«А если нужна сортировка всего файла?»* — внешняя сортировка: отсортированные куски во временные файлы, затем слияние потоком; или загрузить в базу и сортировать там.
- *«Как распараллелить?»* — разбить файл на диапазоны байтов с выравниванием по концу строки и обрабатывать в Worker Threads; или параллельная обработка пачек с ограничением concurrency.

</details>

### SM11. Как принять загрузку файла, не держа её в памяти?

<details>
<summary>Ответ</summary>

**Тезис.** Разбирать `multipart/form-data` потоково (busboy) и передавать каждый файл через `pipeline` в приёмник — диск или объектное хранилище — с лимитами на размер и число файлов. Не использовать хранение в памяти для больших файлов.

**Подробно.**
- multer без опций хранит файл в `file.buffer`: «files will be kept in memory and never written to disk». Файл 300 МБ — 332 МБ RSS. В NestJS `FileInterceptor` построен на multer.
- busboy с записью потоком — 77 МБ на тот же файл; с `limits.fileSize` 50 МБ — 413, на диске ровно 50 МБ.
- В NestJS: свой storage engine для multer или обработчик на busboy; на Fastify — `@fastify/multipart` со стримом файла.

**Ограничения.** После срабатывания лимита busboy дочитывает тело запроса, прежде чем можно ответить; лишний трафик отсекают проверкой `Content-Length` и закрытием соединения.

**Уточняющий вопрос.** *«Как вообще не пропускать файлы через сервис?»* — presigned URL объектного хранилища: клиент загружает напрямую, сервис выдаёт ссылку и обрабатывает уведомление о загрузке.

</details>

## Вопросы уровня Senior

### S12. Поды сервиса загрузки файлов перезапускаются с OOMKilled, хотя куча V8 маленькая. Что происходит?

<details>
<summary>Ответ</summary>

**Тезис.** Память занимают Buffer-ы с содержимым файлов — они вне кучи V8, поэтому `heapUsed` маленький, а RSS достигает лимита контейнера. Причина — буферизация загрузок целиком: multer с memory storage, `Buffer.concat` тела, отправка в хранилище из Buffer.

**Подробно.**
1. `process.memoryUsage()`: `arrayBuffers` и `external` растут, `heapUsed` нет. С `--max-old-space-size=50` процесс держал 300 МБ Buffer-ов: `heapUsed` 4 МБ, RSS 325 МБ ([P9](#p9-buffer-и---max-old-space-size)).
2. Корреляция пиков с одновременными загрузками больших файлов.
3. Проверка конфигурации загрузки: `FileInterceptor` без `storage`, отсутствие `limits.fileSize`.

**Ограничения.** Те же симптомы дают утечки Buffer-ов (кеш, незакрытые стримы при ошибках) — их отличают heap snapshot и рост памяти между загрузками, а не во время (3.5).

**Уточняющие вопросы.**
- *«Исправление?»* — потоковый приём и отправка в хранилище, лимиты размера, ограничение одновременных загрузок, presigned URL для больших файлов.
- *«Почему не поднять лимит памяти пода?»* — память по-прежнему пропорциональна размеру и числу одновременных загрузок; следующий всплеск снова её превысит.

</details>

### S13. Как отдать выгрузку на миллион строк из базы медленному клиенту?

<details>
<summary>Ответ</summary>

**Тезис.** Курсор базы → Transform сериализации по одной записи → `res` через `pipeline`. Backpressure от медленного клиента останавливает чтение из базы, память ограничена порогами буферов. Нужны таймауты на сокете и ограничение одновременных выгрузок, потому что каждая держит соединение с базой.

**Подробно.**
- Без потоковой отдачи — сериализация 19 МБ блокирует цикл на ~100 мс и держит всё в памяти ([3.2, раздел 3](../02-event-loop/theory.md#3-сценарий-экспорт-в-json-замедляет-все-эндпоинты)).
- Формат: NDJSON или CSV удобнее потоково, чем один JSON-массив (его можно писать вручную: `[`, записи через запятую, `]`).
- Ошибка посреди выгрузки: статус уже отправлен, поэтому `pipeline` закрывает соединение, и клиент видит обрыв, а не 500.
- Медленный клиент держит курсор и соединение базы: таймаут на неактивный сокет (4.6), ограничение одновременных выгрузок (3.3), для долгих — фоновая задача и ссылка на файл (10.2).

**Ограничения.** Курсор в транзакции держит snapshot и может мешать VACUUM при долгой выгрузке (5.x).

**Уточняющий вопрос.** *«Как клиент узнает, что выгрузка оборвалась?»* — по отсутствию корректного завершения формата (закрывающая `]`, финальная строка-маркер) или по trailer; поэтому формат должен иметь явный конец.

</details>

### S14. Как написать свой Transform-парсер, который корректно работает на границе чанков?

<details>
<summary>Ответ</summary>

**Тезис.** Хранить неполный хвост предыдущего чанка, разбирать только полные записи, остаток дописывать к следующему чанку, а в `flush` обработать последний хвост. Для текста — декодировать через `StringDecoder` или работать с байтами и искать разделитель в Buffer.

**Подробно.**
- В `transform(chunk, enc, cb)`: `buf = tail + chunk`, найти последний разделитель, всё до него разобрать и `push` по записи (object mode), остаток сохранить в `tail`.
- В `flush(cb)`: обработать `tail`, если он не пуст, или сообщить об ошибке формата.
- Ограничить размер `tail`: запись без разделителя на сотни МБ — признак мусора или атаки, должна давать ошибку, а не рост памяти.
- Object mode на выходе: порог в объектах; если объекты крупные, снизить `readableHighWaterMark`.

**Ограничения.** Разделитель внутри кавычек (CSV) требует конечного автомата, а не поиска символа; лучше готовая библиотека.

**Уточняющий вопрос.** *«Где ещё нужна та же техника?»* — разбор многобайтовых символов, протоколов поверх TCP (сообщения с длиной в заголовке), multipart.

</details>

---

### S15. Как гарантировать очистку ресурсов при ошибке в цепочке стримов?

<details>
<summary>Ответ</summary>

**Тезис.** Использовать `pipeline` (или `stream/promises`) с одним обработчиком ошибки; реализовать `destroy` (`_destroy`) у своих стримов так, чтобы они освобождали ресурсы; передавать `AbortSignal` для отмены всей цепочки; удалять частично записанные результаты в обработчике ошибки.

**Подробно.**
- `pipeline` вызывает `destroy(err)` на всех стримах, кроме уже завершённых: закрываются файловые дескрипторы и сокеты.
- Частичный результат (половина файла на диске, незавершённая multipart-загрузка в хранилище) `pipeline` не убирает: это делает код в `catch` — удаление файла, abort загрузки.
- Отключение клиента посреди загрузки: `req` получает `'close'` (событие `'aborted'` устарело с v17.0.0: «Listen for 'close' event instead»), `pipeline` с участием `req` завершится ошибкой.
- `stream.finished(stream)` — дождаться завершения или ошибки одного стрима.

**Ограничения.** Сторонние стримы не всегда корректно реализуют `destroy`; утечки ищут по числу открытых дескрипторов и сокетов под нагрузкой с ошибками.

**Уточняющий вопрос.** *«Почему нельзя переиспользовать стрим после ошибки `pipeline`?»* — документация предупреждает об оставшихся обработчиках событий: «this can cause event listener leaks and swallowed errors».

</details>

---

### S16. Когда буферизация целиком лучше стримов?

<details>
<summary>Ответ</summary>

**Тезис.** Когда данные малы и их размер ограничен на входе, а обработке нужен весь объём сразу: валидация JSON-тела по схеме, подпись или хеш всего содержимого с проверкой до сохранения, маленькие файлы, которые обрабатываются библиотекой, принимающей только Buffer.

**Подробно.**
- JSON API: тело запроса парсится целиком; защита — лимит размера тела. У `express.json()` (body-parser 2.3.0) он по умолчанию 100 КБ (`102400` байт); NestJS на Express регистрирует тот же `express.json()` без своего лимита, если его не задать (8.6).
- Проверка подписи вебхука по всему телу — тело нужно целиком (небольшое).
- Обработка изображения библиотекой без потокового API — Buffer, но с лимитом и ограничением одновременных обработок.

**Ограничения.** Буферизация безопасна только вместе с жёстким лимитом размера и учётом одновременности: N запросов × лимит должны помещаться в память пода.

**Уточняющий вопрос.** *«Почему JSON не парсят потоково?»* — для обычных размеров накладные расходы потокового парсера больше выигрыша, а проверка схемы требует всего документа; потоковый JSON (NDJSON, потоковые парсеры) нужен для больших массивов.

</details>

### P1. Что возвращает write

### P2. Игнорирование false

Источник 4000 раз вызывает `w.write(Buffer.alloc(64 * 1024, 1))` в синхронном цикле; приёмник обрабатывает один чанк примерно за миллисекунду. Чему равны `w.writableLength` и RSS сразу после цикла? А если ждать `'drain'` после каждого `false`?

<details>
<summary>Ответ и объяснение</summary>

</details>

### P3. Ошибка источника: pipe и pipeline

```js
const { Readable, Writable, pipeline } = require('stream');
const makeSource = () => new Readable({
  read() {
    if (!this.sent) { this.sent = true; this.push('first chunk'); }
    else this.destroy(new Error('upstream failed'));
  },
});
const makeDest = (name) => new Writable({
  write(chunk, enc, cb) { cb(); },
  destroy(err, cb) { console.log(`${name}: destination destroyed, err = ${err && err.message}`); cb(err); },
});
const src1 = makeSource(), dst1 = makeDest('pipe');
src1.on('error', (e) => console.log('pipe: source error:', e.message));
src1.pipe(dst1);
setTimeout(() => {
  console.log('pipe: destination destroyed?', dst1.destroyed, 'writableFinished?', dst1.writableFinished);
  pipeline(makeSource(), makeDest('pipeline'), (err) => console.log('pipeline callback:', err && err.message));
}, 50);
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:**
```
pipe: source error: upstream failed
pipe: destination destroyed? false writableFinished? false
pipeline: destination destroyed, err = upstream failed
pipeline callback: upstream failed
```

**Почему:** `pipe` отсоединяется от источника при ошибке, но приёмник не закрывает: он висит открытым и незавершённым. `pipeline` вызывает `destroy(err)` на приёмнике и сообщает ошибку в колбэк. Без обработчика `'error'` на `src1` ошибка уронила бы процесс.

</details>

### P4. break в for await

```js
const { Readable } = require('stream');

const src = new Readable({
  objectMode: true,
  highWaterMark: 4,
  read() { this.push({ n: ++produced }); if (produced === 1000) this.push(null); },
});
src.on('close', () => console.log('source closed, destroyed =', src.destroyed));
(async () => {
  for await (const row of src) {
    if (row.n === 3) break;
  }
  console.log('produced before break', produced);
})();
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `produced before break 7`, `source closed, destroyed = true`.

**Почему:** стрим читает с опережением до порога 4 объекта, поэтому произведено больше, чем потреблено. `break` вызывает `return()` итератора, и стрим уничтожается — остальные 993 объекта не производятся.

</details>

### P6. readFile против потока при лимите кучи

### P7. Buffer из общего пула

### P8. Генератор в pipeline

## Задачи на выбор решения

Формат: условия → варианты → выбор → при каких условиях выбор перестаёт быть верным.

### В1. Импорт CSV от клиентов

**Условия.** Клиенты загружают CSV до 2 ГБ для импорта в PostgreSQL. Сервис на NestJS, под с лимитом 1 ГБ, 3 реплики. Импорт должен проверить каждую строку и сообщить клиенту о результате; загрузок одновременно — до 10.

**Варианты:** multer в памяти и разбор `file.buffer`; multer `diskStorage`, затем фоновая обработка файла; потоковый разбор при загрузке и запись в базу пачками; presigned URL в объектное хранилище и фоновая обработка потоком из хранилища.

<details>
<summary>Разбор</summary>

**Выбор.** Presigned URL в объектное хранилище и фоновая задача (10.2), которая читает файл из хранилища потоком, разбирает построчно и пишет в базу пачками с ожиданием каждой. Загрузка 2 ГБ не идёт через под, импорт не зависит от соединения с клиентом и переживает перезапуск, результат клиент получает статусом задачи.

**Почему не остальные.**
- Память: 10 файлов по 2 ГБ не помещаются; строку из файла больше 512 МБ V8 не создаст вовсе.
- `diskStorage`: нужен диск пода на 20 ГБ, файл на локальном диске пропадёт при перезапуске, а повторное чтение удваивает работу.
- Потоковый разбор при загрузке: память в норме, но импорт длиной в минуты привязан к HTTP-соединению — обрыв или деплой посреди импорта оставляет половину данных в базе; ответ клиенту приходит только в конце.

**Когда выбор перестаёт быть верным.**
- Файлы маленькие (до нескольких МБ) и нужен синхронный ответ с ошибками — потоковый разбор при загрузке с лимитом размера.
- Объектного хранилища нет — потоковый приём с записью в постоянное хранилище и фоновая задача.
- Нужна атомарность «всё или ничего» — загрузка во временную таблицу потоком (`COPY`) и перенос одной транзакцией (5.x).

</details>

### В2. Проксирование файлов из хранилища клиенту

**Условия.** Сервис отдаёт клиентам файлы из объектного хранилища после проверки прав. Файлы от 1 МБ до 5 ГБ, клиенты бывают на медленной мобильной сети. Сейчас код делает `const data = await (await fetch(storageUrl)).arrayBuffer(); res.end(Buffer.from(data));`.

**Варианты:** оставить как есть с лимитом памяти побольше; `pipeline(storageResponse.body, res)`; редирект клиента на presigned URL хранилища.

<details>
<summary>Разбор</summary>

**Выбор.** Редирект (302) на presigned URL с коротким сроком действия после проверки прав: сервис не пропускает трафик через себя, медленные клиенты не держат его ресурсы, хранилище само поддерживает `Range` и докачку.

**Почему не остальные.**
- Текущий код держит весь файл в памяти: 5 ГБ не поместятся в под, а `arrayBuffer` ждёт полной загрузки до первого байта клиенту.
- `pipeline(storageResponse.body, res)` решает память: backpressure от медленного клиента останавливает чтение из хранилища. Но каждое скачивание держит соединение с хранилищем и сокет клиента минутами; при тысячах медленных клиентов это соединения, таймауты и CPU на копирование.

**Когда выбор перестаёт быть верным.**
- Содержимое нужно менять на лету (водяной знак, расшифровка, фильтрация) — `pipeline` через Transform с ограничением одновременных скачиваний и таймаутами.
- Хранилище не должно быть доступно клиенту напрямую (сетевые ограничения, аудит каждого байта) — `pipeline` и поддержка `Range` на стороне сервиса.
- Файлы маленькие — проксирование через `pipeline` проще и не раскрывает структуру хранилища.

</details>

- [ ] Обработка файла больше памяти и запись результата пачками.
- [ ] Приём загрузок: multer memory storage, потоковый разбор, лимиты, presigned URL.

## Как отличить поверхностный ответ от сильного

| Тема | Поверхностный ответ | Сильный ответ |
|---|---|---|
| Зачем стримы | «экономят память» | только с backpressure; показывает, как ручной `write` без `'drain'` копит всё в буфере |
| `highWaterMark` | «размер буфера, 16 КБ» | порог, а не лимит; единицы по режимам; 64 КиБ с v22, но 16 КиБ на Windows |
| Ошибки | «вешаю `.on('error')`» | `pipeline` уничтожает все звенья; знает про незакрытый приёмник при `pipe` и частичные результаты |
| Async iteration | «удобный синтаксис» | backpressure, опережающее чтение, уничтожение при `break` |
| Buffer | «бинарные данные» | `allocUnsafe` и неинициализированная память, пул и `byteOffset`, память вне кучи |
| Кодировки | «`toString()`» | граница чанков посреди символа, `StringDecoder`, предел длины строки |
| Загрузки | «multer» | memory storage по умолчанию, потоковый разбор, лимиты, presigned URL; считает память на одновременные загрузки |
