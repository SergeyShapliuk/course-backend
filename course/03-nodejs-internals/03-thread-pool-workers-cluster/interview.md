# 3.3 Thread Pool, Worker Threads, cluster — interview

> Вопросы проверяют, понимаете ли вы, где в Node.js на самом деле есть параллельность, умеете ли найти перегруженный уровень (поток JavaScript, пул libuv, процесс) и выбрать инструмент: Worker, дочерний процесс, `cluster`, реплики, ограничение concurrency. Схема ответа: **тезис** → **подробно** → **ограничения** → **уточняющие вопросы**. Все фрагменты запущены на Node.js v22.22.2 (Windows 10 x64, 12 логических ядер) как файлы `.cjs`; версионные отличия — на v18.20.8, v24.22.0, v26.12.0. Время — одного запуска, при повторах отличалось на 5–25 %. Слои Node.js — [3.1](../01-nodejs-architecture-v8/), фазы цикла — [3.2](../02-event-loop/).

**Как работать с заданиями.** Ответы спрятаны под раскрывающимися блоками.

1. Прочитайте вопрос или фрагмент кода.
2. Запишите или проговорите ответ: результат **и механизм**.
3. Раскройте эталон и сравните оба пункта.

Вопросы M — Middle, SM — Strong Middle, S — Senior.

## Конспект

- **Через ОС, в потоке цикла:** TCP, HTTP, pipes, `dns.resolve*`. **В пуле libuv:** `fs` (кроме `watch` и `*Sync`), `dns.lookup` (и значит, большинство исходящих соединений по имени), `pbkdf2`, `scrypt`, `randomBytes`, `generateKeyPair`, `crypto.subtle`, `zlib`.
- **Пул:** 4 потока по умолчанию, максимум 1024, создаётся при первом использовании, **общий на процесс**, включая Worker. Голодание пула не видно в задержке цикла.
- **`UV_THREADPOOL_SIZE`** задают снаружи процесса. Из кода — только до первой операции пула, и на Windows в Node.js 22 (libuv 1.51) не работает; работает с Node.js 24.16 (libuv 1.52).
- **Worker Threads:** свой isolate, куча, event loop; общие процесс, память, CPU, пул libuv. Для CPU-работы, не для I/O. Запуск ~35 мс → пул Worker.
- **Данные в Worker:** `postMessage` — копия (structured clone, синхронно, 200 МБ ≈ 63 мс), `transferList` — передача владения (~0 мс), `SharedArrayBuffer` + `Atomics` — общая память; без `Atomics` теряются обновления.
- **`child_process`:** `spawn` (потоки), `execFile` (без shell), `exec` (через shell — не для пользовательских данных, `maxBuffer` 1 МБ), `fork` (Node.js + IPC).
- **`cluster`:** процессы с общим портом; round-robin по умолчанию везде, кроме Windows. Память не общая. В Kubernetes обычно — один процесс на контейнер и реплики.
- **Concurrency limit** — сколько одновременно; **rate limit** — сколько за время. Ограничения умножаются на число инстансов.
- **Отмена:** `AbortSignal.timeout`, `AbortSignal.any`; отмена закрывает запрос клиента, но не останавливает работу на сервере, если сигнал не передан дальше.

## Вопросы уровня Middle

### M1. Какие операции Node.js выполняет в пуле потоков libuv, а какие нет?

<details>
<summary>Ответ</summary>

**Тезис.** В пуле — операции без неблокирующего интерфейса ОС и тяжёлые вычисления: файловая система, `dns.lookup`, часть `crypto` (`pbkdf2`, `scrypt`, `randomBytes` с колбэком, `generateKeyPair`, `crypto.subtle`) и `zlib`. Сеть (TCP, HTTP, pipes) и `dns.resolve*` обслуживаются в потоке event loop через epoll, kqueue или IOCP.

**Подробно.**
- Файлы: «All file system APIs except `fs.FSWatcher()` and those that are explicitly synchronous use libuv's threadpool».
- `dns.lookup` вызывает `getaddrinfo` в пуле, а его неявно вызывают HTTP-клиенты и драйверы при подключении по имени хоста.
- `*Sync`-версии и `crypto.createHash` выполняются в потоке JavaScript и блокируют цикл.

**Ограничения.** Нативные аддоны тоже могут ставить работу в пул (`napi_create_async_work`). На Linux в libuv 1.45–1.48 часть файловых операций шла через io_uring; с 1.49 по умолчанию снова пул.

**Уточняющие вопросы.**
- *«Почему файлы не через epoll?»* — для обычных файлов нет общего для всех ОС неблокирующего интерфейса; libuv выполняет блокирующие вызовы в потоках.
- *«Как резолвить имена, не занимая пул?»* — `dns.resolve*()` (c-ares, сетевые DNS-запросы без пула), но они не читают `/etc/hosts` и настройки ОС так, как `getaddrinfo`.

</details>

### M2. «Асинхронный fs ничего не нагружает». Так ли это?

<details>
<summary>Ответ</summary>

**Тезис.** Нет. Каждая асинхронная файловая операция занимает поток пула libuv на время системного вызова, а потоков по умолчанию четыре. Если пул занят, операции ждут в очереди, хотя event loop свободен.

**Подробно.** Четыре долгих `pbkdf2` заняли пул: `setTimeout(10)` сработал через 13 мс, сервер начал слушать порт через 5 мс, а `fs.readFile` маленького файла завершился через 359 мс ([P2](#p2-цикл-свободен-файл-ждёт)). Большой `fs.readFile` к тому же делится на чтения по 512 КиБ, каждое — отдельная задача пула.

**Ограничения.** На быстром локальном диске одна операция занимает поток ненадолго; проблема появляется, когда в том же пуле есть долгие задачи (хеширование, сжатие, медленный DNS, сетевой диск).

**Уточняющий вопрос.** *«Как это заметить в production?»* — по времени операций пула, а не по задержке цикла: канареечный `fs.stat` или `dns.lookup` с замером, этапы исходящих запросов ([SM6](#sm6-что-такое-голодание-пула-потоков-и-как-его-обнаружить)).

</details>

### M3. Чем Worker Threads отличаются от асинхронного кода и когда их использовать?

<details>
<summary>Ответ</summary>

**Тезис.** Асинхронный код выполняется в одном потоке и не делает вычисления параллельными, он только не ждёт I/O. Worker Thread — отдельный поток со своим isolate V8 и event loop, в котором JavaScript выполняется **параллельно** с основным. Использовать — для CPU-работы на JavaScript, которая иначе блокирует цикл.

**Подробно.** `fib(38)` в основном потоке: 367 мс, задержка цикла 377 мс. В Worker: 397 мс вместе с запуском, задержка цикла 12 мс ([P9](#p9-fib-в-основном-потоке-и-в-worker)). Документация: «They do not help much with I/O-intensive work».

**Ограничения.** Worker не ускоряет само вычисление, а освобождает основной поток. Запуск — десятки миллисекунд, плюс память на кучу; поэтому используют пул Worker.

**Уточняющие вопросы.**
- *«Что общего у Worker с основным потоком?»* — процесс, память процесса, CPU, файловые дескрипторы и пул libuv.
- *«Что будет при исключении в Worker?»* — Worker завершится, у объекта `Worker` сработает `'error'`; без обработчика — `uncaughtException` в основном потоке.

</details>

### M4. Что делает модуль cluster и зачем он нужен?

<details>
<summary>Ответ</summary>

**Тезис.** `cluster` запускает несколько процессов Node.js через `fork()` и даёт им общий порт, чтобы один сервис использовал несколько ядер. Primary-процесс либо раздаёт соединения по кругу (round-robin), либо отдаёт слушающий сокет воркерам.

**Подробно.**
- Round-robin — по умолчанию везде, кроме Windows; на Windows по умолчанию `SCHED_NONE`, и в эксперименте все 200 соединений достались одному воркеру ([P6](#p6-распределение-соединений-в-cluster)).
- У каждого воркера своя память: сессии, кеши и счётчики в памяти не общие.
- PM2 cluster mode использует тот же модуль.

**Ограничения.** В Kubernetes несколько процессов в одном контейнере скрывают их от оркестратора; обычно масштабируют репликами ([SM10](#sm10-cluster-или-несколько-реплик-в-kubernetes)).

**Уточняющий вопрос.** *«Почему пользователь иногда разлогинивается при `cluster`?»* — сессия хранится в памяти одного воркера, а следующий запрос попал в другой. Хранилище сессий выносят в Redis или используют stateless-токены (8.1, 8.2).

</details>

### M5. Чем I/O-bound нагрузка отличается от CPU-bound и что это меняет в выборе решения?

<details>
<summary>Ответ</summary>

**Тезис.** I/O-bound — время уходит на ожидание сети, диска, базы; в Node.js оно почти ничего не стоит потоку JavaScript. CPU-bound — время уходит на вычисления; в потоке JavaScript они блокируют цикл для всех запросов.

**Подробно.**
- I/O-bound: асинхронный код, ограничение concurrency к зависимостям, масштабирование под нагрузку зависимостей.
- CPU-bound на JavaScript: Worker Threads (пул), порции с `setImmediate`, вынос в очередь или сервис.
- CPU-bound во встроенных API (хеширование, сжатие): пул libuv, ограничение одновременных задач.
- Один процесс использует одно ядро для JavaScript: для всех ядер — несколько процессов.

**Ограничения.** Реальная нагрузка смешанная; узкое место находят метриками: задержка цикла (поток JavaScript), время операций пула (пул), CPU процесса и квота контейнера.

**Уточняющий вопрос.** *«Как понять, какая нагрузка у сервиса?»* — CPU процесса около 100 % одного ядра и растущая задержка цикла — CPU-bound; низкий CPU и долгие ответы — ожидание зависимостей или пула.

</details>

## Вопросы уровня Strong Middle

### SM6. Что такое голодание пула потоков и как его обнаружить?

<details>
<summary>Ответ</summary>

**Тезис.** Голодание пула — все потоки пула заняты долгими задачами, а короткие (`fs.stat`, `dns.lookup`) ждут в общей очереди FIFO. Event loop при этом свободен, поэтому метрика задержки цикла молчит; видны только медленные операции пула.

**Подробно.**
- 20 одновременных `scrypt` по ~110 мс: `dns.lookup('localhost')` вырос с 6,6 мс до 656 мс, задержка цикла — 25 мс ([theory, раздел 3](./theory.md#3-сценарий-логины-замедляют-исходящие-запросы)).
- Признаки: таймауты соединения исходящих запросов (DNS до соединения), медленные файловые операции, при этом CPU основного потока низкий.
- Обнаружение: канареечная метрика (периодический `fs.stat` с замером), тайминги этапов исходящих запросов. CPU-профиль V8 потоки пула не показывает: основной поток в нём «простаивает» (`(idle) 97%` при 8 `scrypt`), и это само по себе подсказка.

**Ограничения.** Прямой метрики очереди пула Node.js не даёт.

**Уточняющие вопросы.**
- *«Как исправить?»* — ограничить concurrency тяжёлых задач пула (bulkhead), увеличить пул с учётом ядер, убрать DNS из горячего пути (keep-alive), вынести тяжёлую работу.
- *«Почему не сделать пул на 128 потоков?»* — для CPU-задач лишние потоки делят те же ядра: при 12 потоках на 6 ядрах `dns.lookup` всё равно ждал 217 мс.

</details>

### SM7. Как выбрать UV_THREADPOOL_SIZE?

<details>
<summary>Ответ</summary>

**Тезис.** По характеру задач пула и числу ядер, доступных процессу. Для CPU-задач (хеширование, сжатие) — не больше ядер квоты, для ожидающих (медленный DNS, сетевой диск) — больше. Задавать переменной окружения процесса, а не из кода.

**Подробно.**
- По умолчанию 4, максимум 1024; читается один раз при создании пула.
- Восемь `pbkdf2`: с 4 потоками — две волны (~380 мс), с 8 — одна (~240 мс) на 6 физических ядрах ([P1](#p1-восемь-pbkdf2)).
- Пул общий для процесса и всех Worker.
- Число ядер в контейнере — `os.availableParallelism()`, а не `os.cpus().length` (учитывает квоту cgroup на Linux).

**Ограничения.** `process.env.UV_THREADPOOL_SIZE = '8'` в коде: на Unix работает до первой операции пула; на Windows в Node.js 22 (libuv 1.51, `getenv`) игнорируется, с Node.js 24.16 (libuv 1.52, `uv_os_getenv`) работает ([P8](#p8-uv_threadpool_size-из-кода)).

**Уточняющие вопросы.**
- *«Где задать в NestJS-сервисе?»* — в Dockerfile (`ENV UV_THREADPOOL_SIZE=…`) или в манифесте пода; не в `main.ts`.
- *«Помогает ли увеличение пула, если тормозит основной поток?»* — нет: пул и поток JavaScript — разные ресурсы.

</details>

### SM8. Как передавать данные в Worker и сколько это стоит?

<details>
<summary>Ответ</summary>

**Тезис.** Три способа: копия через `postMessage` (structured clone), передача владения `ArrayBuffer` через `transferList`, общая память `SharedArrayBuffer`. Копия стоит пропорционально объёму и выполняется синхронно в потоке отправителя; передача почти бесплатна; общая память требует синхронизации.

**Подробно.**
- Копия 200 МБ `ArrayBuffer` — 63 мс блокировки отправителя; передача — 0,02 мс, после неё у отправителя `byteLength === 0` ([P5](#p5-передача-arraybuffer)).
- Structured clone не переносит функции (`DataCloneError`) и прототипы: экземпляр класса приходит как обычный объект.
- `SharedArrayBuffer` без `Atomics` теряет обновления: из 4 000 000 инкрементов дошло около 3,5 млн ([P4](#p4-счётчик-в-sharedarraybuffer)).

**Ограничения.** Массив из сотен тысяч объектов копируется дороже плоского буфера; большие структурированные данные лучше передавать в бинарном виде или не передавать вовсе — пусть Worker читает их сам.

**Уточняющий вопрос.** *«Можно ли передать в Worker соединение с базой?»* — нет: объект соединения не клонируется, а сокет принадлежит основному потоку. Worker открывает свои соединения, и пул соединений базы делится между ними.

</details>

### SM9. Чем различаются spawn, exec, execFile и fork?

<details>
<summary>Ответ</summary>

**Тезис.** `spawn` запускает процесс и даёт stdio как потоки. `execFile` запускает исполняемый файл без shell и буферизует вывод. `exec` запускает команду через shell и буферизует вывод. `fork` — `spawn` процесса Node.js с IPC-каналом.

**Подробно.**
- `exec` с пользовательскими данными — command injection: «Never pass unsanitized user input to this function». Для аргументов из данных — `execFile` или `spawn` без `shell: true`.
- `exec` и `execFile` хранят вывод в памяти; при превышении `maxBuffer` (по умолчанию 1 МБ) процесс завершается. Для большого вывода — `spawn` и потоки.
- `execSync`/`spawnSync` блокируют event loop на всё время работы дочернего процесса.

**Ограничения.** Запуск процесса стоит десятки–сотни миллисекунд и память на новый процесс; для частых коротких задач на JavaScript лучше пул Worker.

**Уточняющий вопрос.** *«Когда дочерний процесс лучше Worker?»* — когда нужна чужая программа (ffmpeg, ImageMagick) или изоляция: падение или утечка памяти в дочернем процессе не роняет сервис.

</details>

### SM10. cluster или несколько реплик в Kubernetes?

<details>
<summary>Ответ</summary>

**Тезис.** В Kubernetes — обычно один процесс Node.js на контейнер и масштабирование репликами: оркестратор видит каждый процесс, управляет его перезапуском, лимитами, probes и rolling update. `cluster` или PM2 оправданы на виртуальной машине без оркестратора.

**Подробно.**
- При `cluster` внутри пода падение одного воркера не видно Kubernetes; память и CPU воркеров суммируются в лимит пода; graceful shutdown нужно реализовать в primary.
- Реплики: балансировку делает Service/Ingress, метрики и перезапуск — по процессу.
- Число процессов и потоков считают от квоты CPU: `os.availableParallelism()`, а не `os.cpus().length`.

**Ограничения.** Если под получает несколько ядер (крупные поды ради экономии на sidecar и памяти), несколько процессов в поде могут быть оправданы; тогда нужен корректный shutdown всех воркеров и учёт памяти.

**Уточняющие вопросы.**
- *«Что общего у реплик и воркеров `cluster`?»* — ничего в памяти: сессии, кеши, rate limits выносят в Redis или базу.
- *«Нужен ли PM2 в Docker?»* — для перезапуска и логов в Kubernetes — нет, это делает платформа; у PM2 есть `pm2-runtime` для контейнеров, но он дублирует функции оркестратора.

</details>

### SM11. Чем ограничение concurrency отличается от rate limiting?

<details>
<summary>Ответ</summary>

**Тезис.** Concurrency limit ограничивает число операций, выполняющихся **одновременно**; rate limit — число операций **за интервал времени**. Первый защищает ёмкость зависимости (соединения, потоки), второй — квоту и пропускную способность.

**Подробно.**
- Семафор на 10: из 100 запросов по 20 мс одновременно выполняется не больше 10, порядок результатов сохраняется ([P10](#p10-семафор-и-порядок-результатов)).
- Rate limit 100 в секунду пропустит 100 запросов, которые висят по 5 секунд, и одновременно их станет 500.
- Concurrency limit 10 при запросах по 10 мс даёт 1000 запросов в секунду и нарушит квоту «60 в минуту».

**Ограничения.** Оба лимита, заданные на процесс, умножаются на число процессов и подов. Глобальный лимит требует общего хранилища (Redis, 8.6, 9.4).

**Уточняющий вопрос.** *«Как выбрать N для concurrency?»* — по ёмкости зависимости: размер пула соединений базы, лимиты API, размер пула libuv для задач пула; с учётом числа инстансов.

</details>

## Вопросы уровня Senior

### S12. Event loop lag в норме, CPU 40 %, а исходящие HTTP-запросы падают по таймауту соединения. Что проверить?

<details>
<summary>Ответ</summary>

**Тезис.** Голодание пула libuv: резолв имени хоста через `dns.lookup` стоит в очереди пула за долгими задачами — хешированием, сжатием, файловыми операциями. Проверить, какие задачи пула идут одновременно с исходящими запросами, и время этапа DNS.

**Подробно.**
1. Тайминги этапов исходящего запроса: DNS, TCP connect, TLS, первый байт. Долгий DNS при быстром соединении после него — признак очереди пула.
2. Какие задачи пула есть в процессе: `scrypt`/`pbkdf2`/`bcrypt` при логине, `zlib` при сжатии ответов, файлы, аддоны.
3. Канареечная метрика пула и её корреляция с пиками логинов.

**Ограничения.** Те же симптомы даёт медленный DNS-сервер или лимит соединений на стороне получателя; канарейка `fs.stat` различает: если она тоже медленная, дело в пуле.

**Уточняющие вопросы.**
- *«Исправление?»* — семафор на тяжёлые задачи пула, keep-alive агент (нет повторного резолва), увеличение пула с учётом ядер, вынос хеширования.
- *«Почему не `dns.resolve` вместо `lookup`?»* — можно передать свой `lookup` в агент, но `resolve` не учитывает `/etc/hosts` и настройки ОС; это меняет поведение резолва, а не только производительность.

</details>

### S13. Когда SharedArrayBuffer и Atomics оправданы на backend?

<details>
<summary>Ответ</summary>

**Тезис.** Редко: когда несколько Worker обрабатывают большой бинарный или числовой массив и копирование неприемлемо, или нужен кольцевой буфер между потоками. Для обычного обмена задачами и результатами проще и безопаснее `postMessage` с передачей буферов.

**Подробно.**
- Без `Atomics` обычные операции неупорядочены между агентами, и инкременты теряются ([P4](#p4-счётчик-в-sharedarraybuffer)).
- Модель памяти ECMAScript: «Atomic accesses are sequentially consistent»; для гонок определены возможные значения, «there is no undefined behaviour».
- `Atomics.wait`/`notify` позволяют строить мьютексы и семафоры между Worker; в основном потоке `Atomics.wait` блокирует event loop.

**Ограничения.** Данные в `SharedArrayBuffer` — только байты: объекты и строки нужно сериализовать вручную. Ошибки синхронизации трудно воспроизвести.

**Уточняющий вопрос.** *«Можно ли так сделать общий кеш между воркерами `cluster`?»* — нет: `cluster` — это процессы, `SharedArrayBuffer` работает только между потоками одного процесса. Для процессов — Redis или другое внешнее хранилище.

</details>

### S14. Как сделать таймауты и отмену сквозными через сервис?

<details>
<summary>Ответ</summary>

**Тезис.** Каждая операция получает `AbortSignal`, который сработает либо по общему дедлайну запроса, либо при отключении клиента; сигнал передаётся во все вложенные вызовы — исходящие `fetch`, запросы к базе, таймеры. `Promise.race` с таймером не отменяет работу.

**Подробно.**
- `AbortSignal.timeout(ms)` — таймаут, причина `TimeoutError`; `AbortSignal.any([...])` — объединение сигналов клиента и дедлайна.
- Отключение клиента сервер видит как `'close'` у запроса; из него создают `AbortController` и прерывают вложенную работу.
- В эксперименте отмена `fetch` закрыла соединение, сервер увидел `close`, но его таймер всё равно сработал: без передачи сигнала работа продолжается ([P7](#p7-timeouterror-и-aborterror)).
- Запрос к базе отменяется только средствами драйвера и базы (`statement_timeout`, cancel request).

**Ограничения.** Операция пула libuv, уже взятая потоком, не прерывается. Таймауты на уровне HTTP-сервера и балансировщика — 4.6; deadline propagation между сервисами — 11.5.

**Уточняющий вопрос.** *«Почему таймаут исходящего запроса должен быть меньше таймаута входящего?»* — иначе входящий запрос завершится по таймауту раньше, а исходящий продолжит тратить ресурсы впустую.

</details>

### S15. Сколько процессов, Worker и потоков пула запускать в контейнере с лимитом 2 CPU?

<details>
<summary>Ответ</summary>

**Тезис.** Считать от квоты, а не от ядер хоста. Для типичного HTTP-сервиса — один процесс на контейнер; пул Worker для CPU-задач — 1–2 Worker; `UV_THREADPOOL_SIZE` для CPU-задач пула — около квоты, для ожидающих — больше.

**Подробно.**
- `os.cpus().length` на 32-ядерном хосте вернёт 32; `os.availableParallelism()` в Node.js 22 (libuv 1.51) на Linux учитывает квоту cgroup (`cpu.max`) и вернёт около 2.
- 32 процесса или Worker на 2 CPU — троттлинг CFS: все потоки получают кванты по очереди, растёт задержка цикла каждого (11.3).
- Основному потоку нужна доля CPU для обработки запросов: Worker на все ядра квоты отнимут её.

**Ограничения.** Проверено в Docker с `--cpus=2` на v22.22.2 и v24.22.0 (`cpus().length` 12, `availableParallelism()` 2). Учёт квоты cgroup в `uv_available_parallelism` исправлен в libuv 1.49; на более старых версиях Node.js поведение отличалось. Проверяйте на целевой версии в целевом окружении.

**Уточняющий вопрос.** *«Что делать, если CPU-задачам нужно больше 2 ядер?»* — выносить их в отдельный деплой с собственными лимитами и масштабированием (очередь, 10.2), а не раздувать HTTP-под.

</details>

### S16. Как спроектировать вынос CPU-задач в пул Worker?

<details>
<summary>Ответ</summary>

**Тезис.** Фиксированный пул Worker по числу доступных ядер минус основной поток, очередь задач с лимитом длины и таймаутом, передача данных без копирования, отмена и наблюдаемость. Готовые реализации (piscina) закрывают большую часть.

**Подробно.**
- Создавать Worker заранее: запуск ~35 мс и память на кучу.
- Очередь с лимитом: при переполнении — 503 или отказ, иначе память растёт без границ.
- Данные: `transferList`, `SharedArrayBuffer`, или Worker сам читает данные по идентификатору.
- Отмена: синхронное вычисление прерывается только `terminate()`; длинные задачи режут на шаги или проверяют флаг.
- `resourceLimits` ограничивают кучу Worker; падение Worker — пересоздать.
- Метрики: длина очереди, время ожидания и выполнения, `eventLoopUtilization` Worker.

**Ограничения.** Если задачи долгие (секунды) или пиковые, пул в HTTP-процессе делит CPU с запросами; лучше отдельный сервис или очередь.

**Уточняющий вопрос.** *«Почему не создавать Worker на каждый запрос?»* — цена запуска сопоставима с самой задачей, а при всплеске сотни Worker исчерпают память и CPU.

</details>

## Задачи на выбор решения

Формат: условия → варианты → выбор → при каких условиях выбор перестаёт быть верным.

### В1. Куда вынести генерацию PDF-отчётов

**Условия.** NestJS-сервис по запросу пользователя строит PDF-отчёт: данные из базы (100–300 мс), генерация PDF чистой JavaScript-библиотекой (0,5–3 с CPU). Пользователь ждёт файл в ответе. Нагрузка — до 5 отчётов одновременно в пике, остальной трафик — лёгкие запросы с SLO p99 200 мс. Под с лимитом 2 CPU, 4 реплики.

**Варианты:** генерировать в основном потоке; пул Worker (piscina) в том же сервисе; дочерний процесс на каждый отчёт; отдельный сервис генерации с очередью и асинхронной выдачей (ссылка по готовности).

<details>
<summary>Разбор</summary>

**Выбор.** Пул Worker на 1 Worker на под с очередью ограниченной длины: генерация не блокирует цикл, лёгкие запросы укладываются в SLO, а пользователь получает файл в ответе, как требует контракт. Один Worker, потому что квота пода 2 CPU, и второе ядро нужно основному потоку. При переполнении очереди — 503 с `Retry-After`.

**Почему не остальные.**
- Основной поток: 0,5–3 с блокировки на каждый отчёт — p99 лёгких запросов вырастет до секунд.
- Дочерний процесс на каждый отчёт: запуск процесса и загрузка библиотеки на каждый запрос; при 5 одновременных — 5 процессов на 2 CPU.
- Отдельный сервис с очередью меняет контракт (асинхронная выдача) и добавляет инфраструктуру; при 5 одновременных отчётах это избыточно.

**Когда выбор перестаёт быть верным.**
- Отчётов становится много или они дольше 10 секунд — отдельный сервис с очередью (10.2) и асинхронной выдачей: генерация не должна делить квоту с API.
- Генерация требует больших данных (сотни МБ) — копирование в Worker дорого; Worker читает данные из базы сам, или генерация уходит в отдельный сервис.
- Библиотека нативная и сама работает в пуле libuv — Worker не нужен, но нужен семафор на число одновременных генераций (пул общий).

</details>

### В2. Массовая рассылка через внешний API

**Условия.** Нужно отправить 50 000 уведомлений через внешний API. Лимиты провайдера: не больше 100 запросов в секунду и не больше 20 одновременных соединений с аккаунта. Время ответа API — 50–400 мс. Рассылку запускают 3 инстанса воркера.

**Варианты:** `Promise.all` по всем; ограничение concurrency 20 на инстанс; rate limiter 100/с на инстанс; глобальные лимиты в Redis; очередь с rate limiting на уровне очереди.

<details>
<summary>Разбор</summary>

**Выбор.** Очередь задач с глобальными лимитами (10.2): в BullMQ (6.3.15 на дату проверки) опция `limiter: { max, duration }` воркера общая для всей очереди — «The rate limiter is global, so if you have for example 10 workers for one queue with the above settings, still only 10 jobs will be processed by second» ([BullMQ: Rate limiting](https://docs.bullmq.io/guide/rate-limiting)), а `concurrency` воркера задаёт число одновременных задач на процесс. Нужны **оба** ограничения: около 6 одновременных на инстанс (3 × 6 = 18 < 20) и 100 в секунду суммарно.

**Почему не остальные.**
- `Promise.all` по 50 000 — 50 000 одновременных запросов: мгновенное нарушение обоих лимитов, `429`, а также очередь в пуле libuv на `dns.lookup` при новых соединениях.
- Concurrency 20 на инстанс — 60 одновременных на три инстанса; и при ответах по 50 мс — до 400 запросов в секунду на инстанс.
- Rate limiter 100/с на инстанс — 300/с суммарно; одновременных при ответах по 400 мс — до 40 на инстанс.
- Глобальные лимиты в Redis без очереди решают задачу, но повторы, отложенные задачи и учёт отправленных придётся писать самим.

**Когда выбор перестаёт быть верным.**
- Рассылка разовая и маленькая (сотни сообщений) — один процесс с семафором и простым rate limiter.
- Провайдер даёт пакетный API — отправка пачками меняет все расчёты.
- Нужна гарантия «ровно одно уведомление» — идемпотентность на стороне провайдера или учёт отправленных (10.5); лимиты эту проблему не решают.

</details>

## Как отличить поверхностный ответ от сильного

| Тема | Поверхностный ответ | Сильный ответ |
|---|---|---|
| Пул потоков | «в Node.js есть пул из 4 потоков» | перечисляет, что в нём выполняется, включая неявный `dns.lookup`; знает, что пул общий на процесс и создаётся лениво |
| Голодание | «увеличить `UV_THREADPOOL_SIZE`» | объясняет, почему задержка цикла молчит; ограничивает тяжёлые задачи, учитывает ядра, убирает DNS из горячего пути |
| Worker Threads | «для тяжёлых задач» | для CPU-работы на JavaScript; знает цену запуска и копирования, использует пул и `transferList` |
| Общая память | «нельзя, это разные потоки» | `SharedArrayBuffer` + `Atomics`, потерянные обновления без них, модель памяти без undefined behaviour |
| `cluster` | «запускает процессы на все ядра» | знает round-robin и `SCHED_NONE`, проблему состояния в памяти, сравнивает с репликами в Kubernetes |
| Лимиты | «поставим rate limit» | различает concurrency и rate, считает лимиты с учётом инстансов, выносит глобальный лимит в общее хранилище |
| Отмена | «`Promise.race` с таймаутом» | `AbortSignal` в каждый вложенный вызов, знает, что серверная работа продолжается без явной передачи сигнала |
