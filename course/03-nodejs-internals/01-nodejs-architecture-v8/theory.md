## 1. Определения и назначение

| Понятие | Коротко | Где живёт |
|---|---|---|
| Node.js | runtime: хост для V8 плюс системные API (файлы, сеть, процессы, криптография) | процесс `node` |
| V8 | JavaScript-движок: парсер, интерпретатор, JIT-компиляторы, куча и GC, очередь микрозадач | библиотека внутри процесса `node` (тот же движок, что в Chrome) |
| libuv | C-библиотека: event loop, неблокирующий сетевой I/O через механизм ОС, пул потоков для блокирующих операций, таймеры, сигналы, процессы | библиотека внутри процесса `node` |
| C++ bindings | код Node.js на C++, который связывает JavaScript API с V8, libuv и другими библиотеками | `src/` в репозитории Node.js |
| JavaScript API | публичные модули `node:fs`, `node:http`, `node:crypto` и другие, написанные в основном на JavaScript | `lib/` в репозитории Node.js |
| JIT | компиляция в машинный код во время выполнения, с учётом того, как код реально выполняется | V8 |

**Node.js — не язык и не движок.** Язык — ECMAScript, движок — V8. Node.js встраивает V8 так же, как браузер, но вместо DOM и отрисовки даёт файлы, сокеты, процессы и свой event loop на libuv `[runtime]`. Именно поэтому [1.5](../../01-javascript/05-event-loop-spec/) называет Node.js **хостом**: спецификация языка требует от хоста выполнять jobs, а как устроен цикл, решает хост.

**Зачем это backend-разработчику.** На собеседовании вопрос «как устроен Node.js» проверяет, понимает ли кандидат, **где** выполняется работа: в потоке JavaScript, в ядре ОС или в пуле потоков. От этого зависят ответы на практические вопросы:

- почему 10 000 открытых соединений не требуют 10 000 потоков, а один `JSON.parse` на 50 МБ останавливает весь сервис;
- почему `fs.readFile` может стать узким местом, хотя «он же асинхронный» (3.3);
- почему один и тот же код после обновления Node.js работает быстрее или медленнее: вместе с Node.js меняется V8.

**Главная мысль урока.** JavaScript в Node.js выполняется в одном потоке на event loop, но процесс Node.js многопоточный. Скорость JavaScript в V8 — результат **спекуляции**: движок наблюдает за кодом, делает ставку на формы объектов и типы значений и откатывается, если ставка не сыграла. Для backend-кода из этого следуют две практические вещи: стабильные формы объектов и проверка данных на границе сервиса. Всё остальное — только по результатам профилирования.

## 2. Внутренний механизм

### 2.1 Слои Node.js

**Что это.** Node.js состоит из четырёх слоёв и набора встроенных библиотек `[runtime]`:

```
  Ваш код, npm-пакеты
        │
  JavaScript API Node.js  (lib/: fs, http, net, crypto, stream, …)
        │   internalBinding('fs'), internalBinding('tcp_wrap'), …
  C++ bindings            (src/: node_file.cc, tcp_wrap.cc, …)
        │                        │                         │
       V8                      libuv              llhttp, OpenSSL, zlib,
  (JS, куча, GC,        (event loop, сокеты,      c-ares, ICU, simdjson,
   микрозадачи)          пул потоков, таймеры)    undici, nghttp2, …
        │                        │
                  Операционная система
```

**Как распределены обязанности** `[runtime]`:

- **V8** исполняет JavaScript и WebAssembly, выделяет память под объекты и собирает мусор, хранит очередь микрозадач. Ввода-вывода, таймеров и цикла событий в V8 нет.
- **libuv** даёт цикл событий и абстракцию над механизмом ОС для неблокирующего сетевого ввода-вывода: «epoll on Linux, kqueue on OSX and other BSDs, event ports on SunOS and IOCP on Windows» ([libuv: Design overview](https://docs.libuv.org/en/v1.x/design.html)). Файловые операции и `getaddrinfo` выполняются в пуле потоков libuv.
- **C++ bindings** превращают вызов JavaScript в вызов libuv или библиотеки, а результат — обратно в значения JavaScript и вызов колбэка.
- **Встроенные библиотеки**: llhttp разбирает HTTP/1.1, OpenSSL реализует TLS и `node:crypto`, zlib, brotli и zstd — сжатие, c-ares — `dns.resolve*()`, undici — глобальный `fetch` («The implementation is based upon undici», [Globals: fetch](https://nodejs.org/docs/latest-v22.x/api/globals.html#fetch)).

**Пример: версии слоёв видны из процесса.**

```js
const { node, v8, uv, llhttp, openssl, undici, napi } = process.versions;
console.log({ node, v8, uv, llhttp, openssl, undici, napi });
// {
//   node: '22.22.2',
//   v8: '12.4.254.21-node.39',
//   uv: '1.51.0',
//   llhttp: '9.3.0',
//   openssl: '3.5.5',
//   undici: '6.24.1',
//   napi: '10'
// }
```

Суффикс `-node.39` у версии V8 означает патчи, которые Node.js накладывает на свою копию движка.

**Что зависит от версии.** Начиная с v20 каждая мажорная линия Node.js держится на одной версии V8: v20 — 11.3, v22 — 12.4, v24 — 13.6, v26 — 14.6 (по `process.versions` и [списку релизов](https://nodejs.org/dist/index.json) на 2026-10-16). Раньше V8 обновляли внутри линии, иногда уже после перехода в LTS: v16 — с 9.0 до 9.4, v18 — с 10.1 до 10.2, а в v12.16.0, когда линия уже была LTS, — с 7.7 до 7.8. Это практика проекта, а не гарантия. Поэтому новые оптимизации движка обычно приходят с переходом на новую мажорную версию Node.js, а версию V8 конкретного релиза смотрят в `process.versions.v8`.

**Типичная ошибка.** Считать, что «Node.js написан на JavaScript», или что «Node.js — это V8». Публичные модули действительно написаны на JavaScript, но всё, что касается ОС, выполняет C++ и libuv, а сам JavaScript исполняет V8.

**Как спрашивают.** Вопросы [M1](./interview.md#m1-из-чего-состоит-nodejs-и-за-что-отвечает-каждый-слой), [M2](./interview.md#m2-чем-nodejs-отличается-от-v8-и-от-javascript-в-браузере).

### 2.2 Путь вызова: от `fs.stat` до системного вызова и обратно

**Что это.** Любой асинхронный API Node.js проходит одинаковый путь: JavaScript → binding → libuv → ОС → libuv → binding → колбэк в JavaScript. Различается только то, где ждёт операция: в ядре ОС (сеть) или в потоке пула (файлы).

**Как работает по шагам** на примере `fs.stat(path, cb)` в Node.js v22.22.2 `[runtime]`:

1. **JavaScript.** `lib/fs.js` проверяет аргументы, создаёт объект запроса `FSReqCallback`, кладёт в него колбэк и вызывает `binding.stat(path, bigint, req)`. Здесь `binding` — это `internalBinding('fs')`, объект с функциями, реализованными на C++.
2. **C++.** `Stat` в `src/node_file.cc` преобразует путь в строку C и вызывает `uv_fs_stat(loop, req, path, AfterStat)`. Управление сразу возвращается в JavaScript: `fs.stat` вернул `undefined`, поток JavaScript свободен.
3. **libuv.** Файловых примитивов с неблокирующим интерфейсом, общих для всех ОС, нет, поэтому libuv ставит задачу в пул потоков: «Unlike network I/O, there are no platform-specific file I/O primitives libuv could rely on, so the current approach is to run blocking file I/O operations in a thread pool» ([libuv: File I/O](https://docs.libuv.org/en/v1.x/design.html#file-i-o)).
4. **Поток пула** выполняет блокирующий системный вызов `stat` и сообщает циклу событий о завершении.
5. **Поток event loop**, дойдя до фазы poll (3.2), вызывает `AfterStat` в C++. Тот собирает результат и вызывает `req.oncomplete`, то есть ваш колбэк.
6. **После колбэка** Node.js выполняет очередь `process.nextTick` и микрозадачи V8 (`InternalCallbackScope::Close` в `src/api/callback.cc`), и только потом цикл продолжает работу ([1.5, раздел 2.4](../../01-javascript/05-event-loop-spec/theory.md#24-как-хост-встраивает-jobs-в-свой-цикл)).

**Сеть устроена иначе** `[runtime]`. Сокет регистрируется в механизме ОС (epoll, kqueue, IOCP). Поток event loop блокируется в ожидании событий сразу на всех сокетах и, когда сокет готов, читает данные и вызывает обработчики. Пул потоков для этого не нужен: «network I/O is always performed in a single thread, each loop's thread» ([libuv: Design overview](https://docs.libuv.org/en/v1.x/design.html)). Поэтому 10 000 простаивающих keep-alive соединений стоят памяти на буферы и объекты, но не потоков.

**Пример: binding виден, но не предназначен для вас.**

```js
console.log(typeof internalBinding);                         // undefined
console.log(typeof process.binding('fs').stat);              // function
console.log(require('fs').stat.toString().includes('binding.stat')); // true
```

`internalBinding` недоступен пользовательскому коду. `process.binding()` — устаревший доступ к тем же объектам: «process.binding() is for use by Node.js internal code only» ([DEP0111](https://nodejs.org/docs/latest-v22.x/api/deprecations.html#DEP0111)). С флагом `--pending-deprecation` он печатает `DeprecationWarning`, а при включённой модели разрешений недоступен. Пакеты, которые на него опираются, ломаются при обновлении Node.js.

**Типичная ошибка и диагностика.** «Асинхронный вызов выполняется в фоне бесплатно». Сетевое ожидание действительно почти бесплатно, а файловые операции, `dns.lookup`, часть `crypto` и `zlib` занимают поток пула, которых по умолчанию четыре. Когда пул занят, новые операции ждут в очереди, хотя event loop свободен (3.3).

**Как спрашивают.** Вопрос [SM6](./interview.md#sm6-опишите-путь-вызова-fsstat-от-javascript-до-ос-и-обратно), фрагмент [P9](./interview.md#p9-binding-и-пользовательский-код).

### 2.3 Event loop, I/O и потоки: где выполняется работа

**Что это.** Модель Node.js — один поток JavaScript на event loop плюс ОС, которая ждёт сетевые события, плюс пул потоков для того, что нельзя сделать неблокирующим. Это противопоставляют модели **thread-per-request**, где на каждое соединение или запрос выделяется поток, который блокируется на вводе-выводе.

**Пять уровней параллельности.** Блок 03 строит одну модель, к которой сводятся все вопросы о потоках `[runtime]` + `[arch]`:

| Уровень | Что выполняется | Параллельно ли с JavaScript | Где разобрано |
|---|---|---|---|
| Ожидание I/O | сокеты ждут данных в ядре ОС | да, это работа ядра | 3.1, 3.2 |
| Основной поток | весь ваш JavaScript, колбэки, микрозадачи | нет, по одному | 1.5, 3.2 |
| Пул потоков libuv | `fs`, `dns.lookup`, часть `crypto`, `zlib` | да | 3.3 |
| Worker Threads | отдельный JavaScript в отдельном isolate V8 | да | 3.3 |
| Процессы и инстансы | `cluster`, `child_process`, реплики за балансировщиком | да | 3.3, 11.3 |

Кроме них, у V8 есть свои фоновые потоки: конкурентная компиляция оптимизированного кода и параллельная и конкурентная сборка мусора (3.5). Их число задаёт `--v8-pool-size`, по умолчанию 4 (`v8_thread_pool_size = 4` в `src/node_options.h` v22.22.2).

**Пример: сколько потоков у «однопоточного» процесса.** Скрипт печатает число потоков своего процесса (на Windows через `Get-Process`), затем один раз читает файл:

```js
const { execSync } = require('child_process');
const fs = require('fs');
const count = () => Number(execSync(
  `powershell -NoProfile -Command "(Get-Process -Id ${process.pid}).Threads.Count"`).toString().trim());
console.log('at start:', count());
fs.readFile(__filename, () => console.log('after first fs.readFile:', count()));
```

| Запуск (Windows 10, v22.22.2) | at start | after first fs.readFile |
|---|---|---|
| `node threads.cjs` | 13 | 17 |
| `node --v8-pool-size=1 threads.cjs` | 10 | 14 |
| `UV_THREADPOOL_SIZE=8 node threads.cjs` | 13 | 21 |
| Linux, Docker `node:22.22.2-slim` (счёт по `/proc/self/status`) | 7 | 11 |

**Как это читать.**

1. Процесс многопоточный уже на старте: основной поток, четыре потока платформы V8, служебные потоки Node.js и ОС. `--v8-pool-size=1` убирает три из них.
2. Пул libuv создаётся **лениво**, при первой операции, которой он нужен: первый `fs.readFile` добавил четыре потока, а с `UV_THREADPOOL_SIZE=8` — восемь.
3. Точное число зависит от ОС и версии: на Linux в контейнере процесс стартует с 7 потоками, а не с 13, но первая файловая операция так же добавляет 4. Устойчив вывод, а не цифра.

**Почему так спроектировано** `[arch]`. Поток с собственным стеком стоит памяти и переключений контекста. Пока соединения в основном ждут сеть или базу, один поток с мультиплексированием ввода-вывода обслуживает тысячи соединений дешевле, чем тысячи потоков. Цена — всё, что выполняется в потоке JavaScript, выполняется **по очереди**: долгое вычисление задерживает все соединения сразу.

**Что зависит от среды.** Модель thread-per-request тоже эволюционирует: в Java 21 появились виртуальные потоки, в Go горутины изначально дешёвые. Эти платформы решают проблему стоимости потоков иначе: планировщик runtime переключает лёгкие потоки на ожидании ввода-вывода. Поэтому аргумент «Node.js быстрее, потому что неблокирующий» без уточнения нагрузки — слабый (вопрос [M3](./interview.md#m3-что-значит-неблокирующий-ввод-вывод-и-чем-модель-nodejs-отличается-от-thread-per-request)).

**Типичная ошибка.** «Node.js однопоточный, поэтому в нём нет гонок и не нужны блокировки». В одном процессе синхронный участок действительно атомарен, но между `await` состояние меняют другие обработчики ([1.5, SM11](../../01-javascript/05-event-loop-spec/interview.md#sm11-гарантирует-ли-run-to-completion-отсутствие-гонок-в-nodejs)), а между инстансами сервиса общей памяти нет вовсе.

**Как спрашивают.** Вопросы [M3](./interview.md#m3-что-значит-неблокирующий-ввод-вывод-и-чем-модель-nodejs-отличается-от-thread-per-request), [M4](./interview.md#m4-nodejs-однопоточный), фрагмент [P8](./interview.md#p8-сколько-потоков-добавит-первый-fsreadfile).

### 2.4 Конвейер V8: от исходного текста к машинному коду

**Что это.** V8 не компилирует весь код заранее. Он начинает с дешёвого исполнения и тратит время на оптимизацию только там, где код выполняется часто. Это **многоуровневая компиляция** (tiering) `[runtime]`.

**Уровни V8 12.4** (Node.js 22):

| Уровень | Что делает | Скорость компиляции | Скорость кода |
|---|---|---|---|
| Парсер | строит AST; тела функций по умолчанию только предразбирает и полностью компилирует при первом вызове (`--lazy`, по умолчанию включён) | — | — |
| **Ignition** | интерпретатор байткода; собирает обратную связь о типах и формах объектов в feedback vector | быстрая | низкая |
| **Sparkplug** | baseline-компилятор: переводит байткод в машинный код за один проход, без оптимизаций | очень быстрая | выше интерпретатора |
| **Maglev** | быстрый оптимизирующий компилятор на SSA, использует обратную связь | средняя | высокая |
| **TurboFan** | оптимизирующий компилятор верхнего уровня, агрессивные спекулятивные оптимизации, inlining | медленная, в фоновом потоке | максимальная |

Порядок появления: Ignition и TurboFan стали единственным конвейером в V8 5.9 (2017), Sparkplug появился в V8 9.1 (2021), Maglev — в Chrome M117 (2023) ([V8: Sparkplug](https://v8.dev/blog/sparkplug), [V8: Maglev](https://v8.dev/blog/maglev), [V8: Launching Ignition and TurboFan](https://v8.dev/blog/launching-ignition-and-turbofan)).

**Как работает по шагам** для функции, которую вызывают всё чаще:

1. Первый вызов: функция компилируется в байткод и выполняется Ignition. После нескольких вызовов (порог `--invocation-count-for-feedback-allocation=8` в V8 12.4) ей выделяется feedback vector, и каждая операция записывает, что она видела: формы объектов, типы операндов, цели вызовов.
2. Функция становится «тёплой» — её компилирует Sparkplug. Он не использует обратную связь и не меняет семантику, только убирает накладные расходы интерпретатора.
3. Функция становится «горячей» и обратная связь стабильна — V8 ставит её в очередь на оптимизацию. Оптимизирующий компилятор работает в фоновом потоке (в выводе `--trace-opt` это `ConcurrencyMode::kConcurrent`), основной поток продолжает выполнять неоптимизированный код.
4. Оптимизированный код **спекулирует**: «здесь всегда объект с такой формой», «здесь всегда малое целое». Каждое допущение защищено проверкой.
5. Если проверка не прошла, происходит **деоптимизация**: выполнение возвращается в интерпретатор с восстановленным состоянием кадра (2.7). Позже функция может быть оптимизирована снова, уже с учётом новой обратной связи.
6. Горячий цикл внутри функции, которая вызвана один раз, оптимизируется через **OSR** (on-stack replacement): код подменяется прямо во время выполнения цикла.

**Что зависит от версии: Maglev в Node.js** `[runtime]`. Это пример того, как один и тот же код идёт по разным уровням в разных версиях:

- Node.js 22.0–22.8 — Maglev включён на поддерживаемых архитектурах.
- **Node.js 22.9.0 и новее в линии 22** — Maglev отключён по умолчанию. Причина из changelog: «We have seen several crashes/unexpected JS behaviors with maglev on v22 (which ships V8 v12.4)… So disable it by default on v22» ([CHANGELOG_V22, 22.9.0](https://github.com/nodejs/node/blob/v22.22.2/doc/changelogs/CHANGELOG_V22.md#22.9.0)). В сборке v22.22.2 `process.config.variables.v8_enable_maglev === 0`, и флаг `--maglev` ничего не меняет: движок собран без него.
- Node.js 24 и 26 — Maglev включён (`v8_enable_maglev === 1`, проверено на v24.22.0 и v26.12.0).

```js
function add(a, b) { return a + b; }
let s = 0;
for (let i = 0; i < 1e6; i++) s = add(s, i);
```

```
# node --trace-opt tier.cjs   (v22.22.2, фрагмент)
[marking … <JSFunction add …> for optimization to TURBOFAN, ConcurrencyMode::kConcurrent, reason: hot and stable]
[completed optimizing … <JSFunction add …> (target TURBOFAN)]

# node --trace-opt tier.cjs   (v24.22.0, фрагмент)
[marking … <JSFunction add …> for optimization to MAGLEV, ConcurrencyMode::kConcurrent, reason: hot and stable]
[marking … <JSFunction add …> for optimization to TURBOFAN_JS, ConcurrencyMode::kConcurrent, reason: hot and stable]
[completed optimizing … <JSFunction add …> (target TURBOFAN_JS)]
```

На v22.22.2 функция идёт сразу из Sparkplug в TurboFan, на v24 — сначала в Maglev, затем в TurboFan.

**Что гарантирует спецификация.** Ничего из этого: ECMAScript описывает наблюдаемое поведение, а не способ исполнения `[spec]`. Любая оптимизация V8 обязана сохранить семантику: оптимизированный и неоптимизированный код дают одинаковый результат. Поэтому деоптимизация влияет только на скорость, а не на результат.

**Типичная ошибка.** «V8 оптимизирует по типам TypeScript». Типы стёрты до запуска ([2.5](../../02-typescript/05-variance-erasure-decorators-tsconfig/)). V8 видит только JavaScript и опирается на то, какие значения реально проходили через код.

**Как спрашивают.** Вопросы [M5](./interview.md#m5-что-такое-jit-компиляция-и-зачем-v8-интерпретатор-если-есть-компилятор), [SM7](./interview.md#sm7-какие-уровни-компиляции-есть-в-v8-и-какие-из-них-работают-в-nodejs-22), фрагмент [P10](./interview.md#p10-maglev-в-разных-версиях-nodejs).

### 2.5 Hidden classes (maps): формы объектов

**Что это.** Объект JavaScript — словарь свойств, и наивная реализация искала бы каждое свойство по имени. V8 вместо этого связывает с каждым объектом **hidden class**, во внутренних терминах — **map**. Map описывает форму объекта: какие свойства есть, в каком порядке они добавлены, где лежат значения и какое у них представление ([V8: Fast properties](https://v8.dev/blog/fast-properties), [V8: Maps (Hidden Classes)](https://v8.dev/docs/hidden-classes)) `[runtime]`.

**Как работает по шагам.**

1. Пустой объект получает начальную map.
2. Добавление свойства `id` переводит объект в новую map «есть `id`, смещение 0». Переход запоминается в дереве переходов (transition tree).
3. Следующий объект, которому добавят `id`, пройдёт по уже существующему переходу и получит **ту же** map.
4. Добавление `name` — ещё один переход. Объекты, которым свойства добавляли в одном порядке и одним способом, разделяют одну map, а значит, одну таблицу смещений.
5. Если свойства добавлены в другом порядке, объект уходит в другую ветку дерева и получает другую map.

**Пример: когда формы совпадают.**

```js
// node --allow-natives-syntax shapes.cjs
const a = { id: 1, name: 'a' };
const b = { id: 2, name: 'b' };
const c = { name: 'c', id: 3 };
console.log('a~b', %HaveSameMap(a, b));   // a~b true
console.log('a~c', %HaveSameMap(a, c));   // a~c false — другой порядок
const d = { id: 4 }; d.name = 'd';
console.log('a~d', %HaveSameMap(a, d));   // a~d false — другой способ создания
class User { constructor(id, name) { this.id = id; this.name = name; } }
const u1 = new User(1, 'x'), u2 = new User(2, 'y');
console.log('u1~u2', %HaveSameMap(u1, u2));  // u1~u2 true
const p = JSON.parse('{"id":1,"name":"a"}');
const q = JSON.parse('{"id":2,"name":"b"}');
console.log('p~q', %HaveSameMap(p, q), 'p~a', %HaveSameMap(p, a)); // p~q true p~a true
```

**Как работает по шагам.**

- `a` и `b` созданы одним литералом — одна map.
- `c` содержит те же свойства, но в другом порядке — другая ветка переходов.
- `d` в итоге имеет те же свойства в том же порядке, что и `a`, но map другая: литерал `{ id, name }` сразу создаёт объект с местом под два свойства, а `{ id }` с последующим добавлением идёт по другой цепочке. Одинаковый набор и порядок свойств **не гарантирует** одну map.
- Экземпляры класса, конструктор которого всегда присваивает поля в одном порядке, разделяют map.
- Объекты из `JSON.parse` с одинаковыми ключами в одном порядке в V8 12.4 разделяют map, и даже совпадают с литералом. Это наблюдение для конкретной версии, а не гарантия.

**Где формы расходятся в backend-коде.** Условное добавление свойств:

```js
// node --allow-natives-syntax optional.cjs
function toDtoA(row) {
  const dto = { id: row.id };
  if (row.email) dto.email = row.email;
  dto.name = row.name;
  return dto;
}
function toDtoB(row) {
  return { id: row.id, email: row.email ?? null, name: row.name };
}
const r1 = { id: 1, name: 'a', email: 'a@x' }, r2 = { id: 2, name: 'b' };
console.log('A', %HaveSameMap(toDtoA(r1), toDtoA(r2)));  // A false
console.log('B', %HaveSameMap(toDtoB(r1), toDtoB(r2)));  // B true
```

`toDtoA` порождает две формы: с `email` и без. `toDtoB` всегда создаёт одну. Обратите внимание: это меняет и контракт API — `toDtoA` не отдаёт поле `email`, `toDtoB` отдаёт `"email": null`. Решение о форме ответа принимается по контракту (4.3), а не ради V8.

**Dictionary mode.** Если объект используют как словарь, V8 переводит его в медленный режим: свойства хранятся в собственной хеш-таблице объекта, а map больше не описывает их расположение. «Since inline caches don't work with dictionary properties, the latter, are typically slower than fast properties» ([V8: Fast properties](https://v8.dev/blog/fast-properties)).

```js
// node --allow-natives-syntax del.cjs  (v22.22.2; так же на v24.22.0 и v26.12.0)
const f = { id: 6, name: 'f' };
delete f.name;
console.log(%HasFastProperties(f));          // false — dictionary mode
const g = { id: 7, name: 'g' };
g.name = undefined;
console.log(%HasFastProperties(g));          // true — форма не изменилась
const m = {};
for (let i = 0; i < 20; i++) m['k' + i] = i;
console.log(%HasFastProperties(m));          // false — объект как словарь
```

`delete` перевёл объект в dictionary mode во всех проверенных вариантах: литерал, класс, удаление первого и последнего свойства. Объект, которому через вычисляемые ключи добавили 20 свойств, в V8 12.4 тоже стал словарём. Порог — эвристика движка, он не документирован и может измениться.

**Что зависит от версии.** Всё в этом разделе — поведение V8, а не JavaScript `[runtime]`. Конкретные правила (когда объект переходит в dictionary mode, сколько места резервирует литерал) меняются между версиями.

**Типичная ошибка и диагностика.**

- «`delete` медленный, поэтому никогда его не используйте». Медленным становится не сам `delete`, а последующий доступ к этому объекту в горячем коде. Для объекта, который живёт один запрос, разницы не видно. Для словаря с часто меняющимися ключами правильный инструмент — `Map`, а не объект с `delete`.
- «У объектов с одинаковыми полями одна форма». Форма зависит от порядка и способа добавления свойств.

**Как спрашивают.** Вопросы [SM8](./interview.md#sm8-что-такое-hidden-classes-и-когда-у-двух-объектов-разные-формы), [SM11](./interview.md#sm11-почему-delete-считают-вредным-для-производительности-и-чем-его-заменить), фрагменты [P1](./interview.md#p1-формы-объектов), [P2](./interview.md#p2-литерал-и-добавление-свойства), [P3](./interview.md#p3-delete-и-присваивание-undefined).

### 2.6 Inline caches: мономорфный, полиморфный, мегаморфный доступ

**Что это.** Inline cache (IC) — запомненный в feedback vector результат поиска для конкретного места в коде, например для `item.price` в строке 3. IC хранит пары «map → где лежит свойство». Если в этом месте снова встретится объект с известной map, поиск не нужен: значение читается по смещению `[runtime]`.

**Состояния IC** в V8 12.4:

| Состояние | Сколько map видело место | Что делает оптимизирующий компилятор |
|---|---|---|
| uninitialized | ни одной | — |
| monomorphic | одну | проверка map + чтение по смещению; можно встроить |
| polymorphic | от 2 до 4 | цепочка проверок map |
| megamorphic | больше 4 | общий поиск через глобальный кеш, без специализации |

Граница 4 задана флагом `max_valid_polymorphic_map_count` со значением 4 (`deps/v8/src/flags/flag-definitions.h` в Node.js v22.22.2).

**Пример: цена мегаморфного места.** Функция суммирует `arr[i].x` для 10⁵ объектов; объекты имеют от 1 до 32 разных форм `{ x, f<k> }`. Каждый замер — новая функция со своим feedback vector, 500 проходов (5·10⁷ чтений свойства):

```
shapes=1   38 ms
shapes=2   62 ms
shapes=4   111 ms
shapes=5   233 ms
shapes=8   215 ms
shapes=32  218 ms
```

Числа одного запуска на v22.22.2 (Windows 10 x64), при повторном запуске отличались на 10–25 %, но форма кривой сохранялась: рост с числом форм до 4 и скачок при переходе к 5 — месту становится мегаморфным.

**Как это переводить на backend.** Худший случай здесь — около 4 нс на чтение свойства против менее 1 нс. Запрос к базе длится миллисекунды, то есть в миллион раз дольше. Мегаморфность важна в коде, который выполняет миллионы операций на запрос: сериализация, парсинг, расчёты по большим массивам. В коде фреймворка (middleware, DI, роутинг) места доступа неизбежно мегаморфные, и бороться с этим бессмысленно.

**Типичная ошибка.** Делать выводы из микробенчмарка без профиля реального сервиса (раздел 7.6).

**Как спрашивают.** Вопрос [SM9](./interview.md#sm9-что-такое-inline-cache-и-чем-мономорфный-доступ-отличается-от-мегаморфного), фрагмент [P7](./interview.md#p7-четыре-формы-или-пять).

### 2.7 Деоптимизация

**Что это.** Оптимизированный код опирается на допущения из обратной связи. Если допущение нарушено, V8 выбрасывает оптимизированный кадр, восстанавливает состояние интерпретатора и продолжает выполнение в Ignition `[runtime]`. Maglev использует тот же механизм, что и TurboFan: «This builds on the same deoptimization mechanism as used by TurboFan» ([V8: Maglev](https://v8.dev/blog/maglev)).

**Виды** (по выводу `--trace-deopt`):

- **eager** — проверка внутри оптимизированного кода не прошла прямо сейчас: «wrong map», «not a Smi»;
- **lazy** и **code dependencies** — оптимизированный код зависел от факта о куче (например, «у полей объектов этой формы всегда малые целые»), и факт перестал быть верным. Код помечается к деоптимизации и выбрасывается при следующем входе.

**Пример: строка в массиве чисел.**

```js
// node --trace-deopt deopt2.cjs
function total(items) {
  let sum = 0;
  for (let i = 0; i < items.length; i++) sum += items[i];
  return sum;
}
const nums = Array.from({ length: 100 }, (_, i) => i);
for (let i = 0; i < 20000; i++) total(nums);
console.log('numbers', total(nums));
const mixed = nums.slice(); mixed[50] = '7';
console.log('mixed', total(mixed));
// numbers 4950
// mixed 1225751525354555657585960616263646566676869707172737475767778798081828384858687888990919293949596979899
// [bailout (kind: deopt-eager, reason: wrong map): begin. deoptimizing … <JSFunction total …>, … <Code TURBOFAN> …]
```

**Как работает по шагам.**

1. 20 000 вызовов с массивом малых целых: TurboFan скомпилировал `total` с допущением «элементы — малые целые, сумма — число».
2. `mixed[50] = '7'` меняет вид элементов массива на «произвольные значения», а значит, и map массива (раздел 7.2).
3. Проверка map на входе в цикл не проходит — eager-деоптимизация, выполнение продолжается в интерпретаторе.
4. Результат по семантике JavaScript: после `'7'` сложение становится конкатенацией строк. V8 сохранил семантику, и результат «правильный» с точки зрения языка, но бессмысленный с точки зрения задачи.

Главный вывод: деоптимизация — **симптом**, а проблема — данные неожиданного типа. Исправлять нужно данные на границе, а не «помогать V8».

**Повторные деоптимизации.** После каждой деоптимизации функция снова собирает обратную связь в интерпретаторе и оптимизируется заново — уже с более общими допущениями. Функция, через которую по очереди проходили объекты шести разных форм, на v22.22.2 была оптимизирована 5 раз и деоптимизирована 4 раза (`--trace-opt --trace-deopt`), после чего осталась в оптимизированном, но обобщённом коде с мегаморфным доступом (2.6). Цена — время на перекомпиляцию, периоды в интерпретаторе и более медленный итоговый код; в CPU-профиле это выглядит как функция, которая «внезапно» стала медленнее после изменения входных данных.

**Типичная ошибка и диагностика.** Искать деоптимизации в production без причины. Сначала CPU-профиль (`--cpu-prof`, 3.7, 9.5) показывает, что функция занимает заметную долю времени. Затем `--trace-deopt` на стенде с теми же данными объясняет почему.

**Как спрашивают.** Вопрос [SM10](./interview.md#sm10-что-такое-деоптимизация-и-что-её-вызывает), фрагменты [P4](./interview.md#p4-элементы-массива-после-push-и-перезаписи), [P5](./interview.md#p5-цена-строкой).

### 2.8 Что из этого реально влияет на backend-код

Большая часть времени backend-сервиса уходит на ожидание сети и базы, сериализацию и код фреймворка. Поэтому правила V8 применяются выборочно `[arch]`:

| Правило | Когда важно | Когда не важно |
|---|---|---|
| Не блокировать поток JavaScript | всегда: это общий ресурс всех запросов | — |
| Проверять и нормализовать данные на границе | всегда: это прежде всего корректность | — |
| Стабильная форма объектов (все поля в конструкторе, без условного добавления) | горячие циклы над большими массивами, свои парсеры и сериализаторы | DTO одного запроса, код фреймворка |
| `Map` вместо объекта-словаря с `delete` | кеши в памяти, индексы по ключу, частые добавления и удаления | объект живёт один запрос |
| Мономорфные горячие места | профиль показывает функцию в топе и мегаморфный доступ в ней | всё остальное |
| Не смешивать числа и строки в одном поле | расчёты по большим массивам | — (но это всё равно ошибка данных) |

**Порядок действий при проблеме с производительностью** `[arch]`:

1. Метрики: растёт latency или event loop lag (3.2)?
2. CPU-профиль под нагрузкой (`--cpu-prof`, flamegraph — 9.5): какие функции занимают время?
3. Если в топе собственный код без ввода-вывода — алгоритм и объём данных. Чаще всего проблема в них, а не в V8.
4. Только если функция горячая и алгоритм уже разумный — `--trace-deopt`, формы объектов, мегаморфные места.

**Как спрашивают.** Вопрос [S12](./interview.md#s12-что-из-устройства-v8-реально-влияет-на-backend-код-и-как-это-доказать), задача [В1](./interview.md#в1-оптимизировать-горячую-функцию-под-v8-или-нет).

## 3. Сценарий: цена строкой ломает расчёт заказа

**Условие.** Сервис заказов на NestJS принимает корзину от фронтенда и от партнёрской интеграции и считает итог:

```js
function orderTotal(order) {
  let sum = 0;
  for (const item of order.items) sum += item.price * item.qty;
  return sum + order.shipping;
}
```

DTO описан в TypeScript как `{ items: { price: number; qty: number }[]; shipping: number }`, валидации тела запроса нет. Партнёр после обновления своей системы начинает присылать `"shipping": "10"`. Одновременно мониторинг показывает, что CPU на инстансах вырос, а итоговые суммы части заказов стали огромными.

**Что происходит по шагам.**

```js
// node --trace-deopt scen.cjs (сжато)
const body = (shipping) => JSON.stringify({ items: [{ price: 100, qty: 2 }, { price: 50, qty: 1 }], shipping });
for (let i = 0; i < 50000; i++) orderTotal(JSON.parse(body(10)));
console.log('number shipping:', orderTotal(JSON.parse(body(10))));   // number shipping: 260
console.log('string shipping:', orderTotal(JSON.parse(body('10')))); // string shipping: 25010
// [marking dependent code … <SharedFunctionInfo orderTotal> … for deoptimization, reason: code dependencies]
```

1. **Типы стёрты** `[lib]`. Аннотация `shipping: number` не существует в рантайме, NestJS без `ValidationPipe` передаёт в обработчик результат `JSON.parse` как есть ([2.5](../../02-typescript/05-variance-erasure-decorators-tsconfig/)).
2. **Обратная связь** `[runtime]`. Пока все заказы приходили с числами, Ignition записал: у объектов этой формы поле `shipping` — малое целое, сложение — числовое. TurboFan скомпилировал `orderTotal` с этими допущениями.
3. **Изменение формы.** `JSON.parse` создаёт объект, где `shipping` — строка. Map с полем «только малые целые» больше не подходит для всех объектов, V8 обобщает представление поля, и код, зависевший от старого допущения, помечается к деоптимизации (`reason: code dependencies`).
4. **Семантика.** `250 + "10"` по правилам JavaScript — конкатенация: `"25010"` ([1.6](../../01-javascript/06-iterators-weakrefs-numbers/)). Оптимизация здесь ни при чём, интерпретатор дал бы тот же результат `[spec]`.
5. **Нагрузка.** Пока поток заказов смешанный, функция деоптимизируется и переоптимизируется под новую обратную связь. Это видно как рост CPU, но не это главный ущерб: главный ущерб — неверные суммы в заказах.

**Диагностика.**

- Неверные суммы находят по данным: логирование тела запросов партнёра, сравнение с ожидаемым итогом, алерты на аномальные суммы.
- Рост CPU объясняет CPU-профиль: `orderTotal` и вызывающий код в топе, на стенде с теми же данными `--trace-deopt` показывает деоптимизации `orderTotal`.

**Решение** `[arch]`.

- Валидация и преобразование на границе: `ValidationPipe` с `class-validator` и `transform` (7.5) или схема zod ([2.5](../../02-typescript/05-variance-erasure-decorators-tsconfig/)). Строка либо отклоняется с 400, либо явно приводится к числу по правилам контракта.
- Деньги не считают в `number` с дробями: целые копейки или decimal-библиотека ([1.6](../../01-javascript/06-iterators-weakrefs-numbers/)).
- Отдельно для V8 делать ничего не нужно: после валидации в функцию снова приходят данные одной формы и одного типа.

**Что изменится, если валидация есть, но преобразует `"10"` в число в одном месте, а в другом пропускает?** Функция будет видеть оба варианта. Корректность сломается там, где число не приведено, а V8 будет держать функцию в обобщённом (более медленном) коде. Правило одно: тип поля определяется на границе один раз.

## 4. Причины и следствия для backend

**Поток JavaScript — общий ресурс всех запросов** `[runtime]`. Всё, что выполняется в JavaScript, выполняется по очереди. Долгая синхронная работа одного запроса увеличивает задержку всех остальных и задерживает health-check (3.2).

**Асинхронность не равна бесплатности** `[runtime]`. Сетевое ожидание почти ничего не стоит потоку JavaScript. Файловые операции, `dns.lookup`, `crypto.pbkdf2`, `zlib` занимают ограниченный пул потоков (3.3).

**Производительность JavaScript зависит от данных, а не только от кода** `[runtime]`. Одна и та же функция работает быстро или медленно в зависимости от того, какие формы и типы через неё проходят. Неожиданные данные дают и ошибку корректности, и деоптимизацию.

**Обновление Node.js — это обновление движка** `[runtime]`. Переход 22 → 24 меняет V8 с 12.4 на 13.6 и включает Maglev. Производительность горячего кода может измениться в обе стороны, поэтому обновление мажорной версии проверяют нагрузочным тестом (9.5, 11.3).

**Нативные зависимости привязаны к платформе** `[runtime]`. Пакеты с C++ (bcrypt, sharp, драйверы) собираются под ОС, архитектуру и libc. Это влияет на выбор базового образа Docker (11.3) и на обновления Node.js (раздел 7.4).

## 5. Альтернативы и компромиссы

**Модели конкурентности сервера** `[arch]`:

| Модель | Сильная сторона | Слабая сторона |
|---|---|---|
| Event loop + неблокирующий I/O (Node.js, Nginx) | тысячи соединений на одном потоке, нет гонок внутри синхронного участка | CPU-работа блокирует всех; один процесс использует одно ядро для JavaScript |
| Thread-per-request (классический Java servlet, Apache prefork) | простой последовательный код, CPU-работа не блокирует другие запросы | потоки дороги, общая память требует синхронизации |
| Лёгкие потоки runtime (горутины Go, виртуальные потоки Java 21) | последовательный код и дешёвое ожидание I/O, все ядра | общая память требует синхронизации; другой стек технологий |

**Как Node.js использует несколько ядер** `[arch]`: несколько процессов (`cluster`, реплики в Kubernetes), Worker Threads для CPU-задач, пул libuv для блокирующих операций (3.3).

**Где выполнять CPU-тяжёлый код** `[arch]`:

| Вариант | Когда уместен | Цена |
|---|---|---|
| Чистый JavaScript в основном потоке | короткие вычисления, миллисекунды | блокирует цикл |
| Worker Thread | вычисление на сотни миллисекунд и больше | копирование данных, отдельная куча (3.3) |
| Нативный аддон (Node-API) | готовая библиотека на C/C++/Rust: sharp, bcrypt, argon2 | сборка под платформу, падение аддона роняет процесс |
| WebAssembly | переносимый код из C/C++/Rust без сборки под платформу | обычно медленнее нативного кода, выполняется в потоке JavaScript, если не вынесен в Worker |
| Отдельный сервис или очередь | долгие задачи, независимое масштабирование | сеть, инфраструктура (10.2) |

## 6. Ошибки и заблуждения

- **«Node.js однопоточный».** JavaScript выполняется в одном потоке на event loop, но процесс многопоточный: потоки платформы V8 для компиляции и GC (по умолчанию 4), пул libuv (по умолчанию 4, создаётся при первом использовании), служебные потоки, а также Worker Threads, если их создать. На Windows 10 процесс v22.22.2 стартует с 13 потоками (2.3).
- **«Асинхронный код выполняется параллельно».** Асинхронность — это ожидание без блокировки потока. Сам JavaScript выполняется по очереди. Параллельно работают ядро ОС (сетевое ожидание), пул libuv, Worker Threads и процессы (2.3).
- **«Node.js — это V8» или «Node.js написан на JavaScript».** V8 — движок, Node.js — хост. Публичные модули написаны на JavaScript, системная часть — на C++ и в libuv (2.1).
- **«V8 оптимизирует код по типам TypeScript».** Типы стёрты, V8 использует обратную связь о реальных значениях (2.4).
- **«Оптимизированный код остаётся оптимизированным».** Допущения проверяются, и при нарушении код деоптимизируется (2.7).
- **«Деоптимизация меняет результат».** Нет: семантика сохраняется, меняется только скорость. Неверный результат при смешанных типах даёт сам JavaScript (2.7, раздел 3).
- **«Объекты с одинаковыми полями имеют одну форму».** Map зависит от порядка и способа добавления свойств (2.5).
- **«`delete` всегда медленный» и обратное «`delete` безвреден».** `delete` переводит объект в dictionary mode, и это важно только для объектов в горячем коде. Для словарей правильный инструмент — `Map` (2.5).
- **«В Node.js 22 есть Maglev».** Только в 22.0–22.8; с 22.9.0 он отключён по умолчанию, в официальной сборке v22.22.2 не собран. В Node.js 24 и 26 включён (2.4).
- **«Микрооптимизации под V8 — главный способ ускорить сервис».** Время backend-сервиса уходит на ввод-вывод, алгоритмы и объём данных. Оптимизация под V8 оправдана только для функции, которую профиль показал горячей (2.8).

## 7. Углубление для Strong Middle / Senior

Обязательная часть урока — разделы 1–6. Здесь — представление чисел, виды элементов массивов, isolate и context, нативные аддоны, время старта и методология измерений.

### 7.1 Smi, HeapNumber и pointer compression

V8 хранит малые целые как **Smi** (small integer) прямо в слове-указателе с битом-меткой, без выделения памяти. Остальные числа — объекты **HeapNumber** в куче (оптимизирующий компилятор может держать их «распакованными» в регистрах). Пост о Maglev говорит о «31-bit tagged integers… (32bit due to pointer compression)» ([V8: Maglev](https://v8.dev/blog/maglev)) — это верно для Chrome, где включено **pointer compression**: указатели в куче занимают 32 бита ([V8: Pointer compression](https://v8.dev/blog/pointer-compression)).

Официальные сборки Node.js собираются **без** pointer compression: `process.config.variables.v8_enable_pointer_compression === 0` на v22.22.2 и v24.22.0. Поэтому Smi в Node.js шире:

```js
// node --allow-natives-syntax ek.cjs  (v22.22.2 и v24.22.0)
console.log(%IsSmi(2 ** 31 - 1), %IsSmi(2 ** 31), %IsSmi(1.5), %IsSmi(-0));
// true false false false
```

Следствие для памяти (без pointer compression каждый указатель — 8 байт) и для лимита кучи — тема 3.5. На собеседовании полезно знать, что «одинаковый V8» в Chrome и Node.js собран с разными опциями.

### 7.2 Elements kinds

Индексированные свойства (элементы массивов) V8 хранит отдельно от именованных и различает **виды элементов**: `PACKED_SMI_ELEMENTS` → `PACKED_DOUBLE_ELEMENTS` → `PACKED_ELEMENTS` и их варианты `HOLEY_*` для массивов с дырами ([V8: Elements kinds](https://v8.dev/blog/elements-kinds)). Переходы идут только в сторону обобщения: «Once a single floating-point number is added to an array of Smis, it is marked as DOUBLE, even if you later overwrite the float with a Smi. Similarly, once a hole is created in an array, it's marked as holey forever».

```js
// node --allow-natives-syntax
const c = [1, 2, 3]; c.push(4.5); c[3] = 4;
console.log(%HasDoubleElements(c));      // true — назад к SMI не вернётся
const d = new Array(3); d[0] = 1; d[1] = 2; d[2] = 3;
console.log(%HasHoleyElements(d));       // true — new Array(n) создаёт дыры
```

Тот же пост предупреждает: «For real-world coding patterns, the performance difference between accessing holey or packed arrays is usually too small to matter or even be measurable». Для backend это знание нужно, чтобы объяснить вывод `--trace-deopt` (как в 2.7: «wrong map» после записи строки в массив чисел), а не для переписывания кода.

### 7.3 Isolate, context и потоки

- **Isolate** — независимый экземпляр V8 со своей кучей и сборщиком мусора. Объекты одного isolate недоступны другому. Основной поток Node.js — один isolate, каждый Worker Thread — отдельный isolate со своей кучей и своим event loop (3.3). Отсюда цена Worker: память на кучу и копирование данных при передаче.
- **Context** — глобальный объект и встроенные объекты внутри isolate. Модуль `node:vm` создаёт новые context в том же isolate: код выполняется в том же потоке и делит кучу. Поэтому `vm` — не песочница для недоверенного кода: документация Node.js прямо говорит «The node:vm module is not a security mechanism».
- В терминах спецификации isolate с потоком соответствует **agent**, а context — **realm** ([1.5, 7.2](../../01-javascript/05-event-loop-spec/theory.md#72-агенты-потоки-и-блокировка)).

### 7.4 Нативные аддоны и Node-API

Нативный аддон — динамическая библиотека (`.node`), которую загружает `require`. Исторически аддоны писали прямо на API V8 и Node.js (`nan`), и их приходилось пересобирать под каждую мажорную версию Node.js: значение `process.versions.modules` (ABI, `127` для v22) менялось. **Node-API** решает это: «This API will be Application Binary Interface (ABI) stable across versions of Node.js… allow modules compiled for one major version to run on later major versions of Node.js without recompilation» ([Node-API](https://nodejs.org/docs/latest-v22.x/api/n-api.html)) `[runtime]`.

Что остаётся проблемой `[arch]`:

- бинарник собран под ОС, архитектуру и libc: собранный на glibc не загрузится на Alpine (musl), собранный на x64 — на arm64. Пакеты публикуют prebuilt-бинарники под платформы, при их отсутствии нужна сборка через `node-gyp` и компилятор в образе (11.3);
- ошибка в аддоне (обращение к освобождённой памяти) роняет весь процесс, а не бросает исключение;
- аддон, который делает тяжёлую работу синхронно в основном потоке, блокирует event loop так же, как JavaScript. Хорошие аддоны выносят работу в пул libuv (`napi_create_async_work`).

### 7.5 Время старта: ленивая компиляция, compile cache, snapshot

Время старта важно при автомасштабировании, в serverless и для CLI. Что на него влияет `[runtime]`:

- **Ленивая компиляция.** V8 полностью компилирует функцию при первом вызове, поэтому большой граф зависимостей стоит в основном разбора и выполнения кода модулей на верхнем уровне (3.6).
- **Module compile cache** (Node.js 22.1+): `module.enableCompileCache()` или `NODE_COMPILE_CACHE=dir` сохраняет код-кеш V8 на диск, и следующие запуски с тем же кодом пропускают компиляцию. Кеш одной версии Node.js не используется другой. В v22 API помечен «Stability: 1.1 - Active Development» ([Module compile cache](https://nodejs.org/docs/latest-v22.x/api/module.html#module-compile-cache)).
- **Startup snapshot** (`--build-snapshot`, `node:v8.startupSnapshot`) сохраняет состояние кучи после инициализации приложения, и следующий запуск начинается с готового состояния. В v22 флаг `--build-snapshot` имеет статус «Stability: 1 - Experimental», и документация перечисляет ограничения: «User-land modules are not yet supported in the snapshot, so only one single file can be snapshotted» (приложение собирают бандлером в один файл), и в снимке работает только часть встроенных модулей ([CLI: --build-snapshot](https://nodejs.org/docs/latest-v22.x/api/cli.html#--build-snapshot)). API `v8.startupSnapshot` помечен стабильным в v22.17.0.

### 7.6 Почему микробенчмарки врут

- **Прогрев.** Первые итерации идут в интерпретаторе, затем оптимизированный код. Замер без прогрева измеряет компилятор.
- **Удаление мёртвого кода.** Если результат не используется, оптимизирующий компилятор может выбросить вычисление целиком, и бенчмарк покажет «бесконечную» скорость.
- **Обратная связь от бенчмарка, а не от продукта.** Функция, которая в тесте видит одну форму объекта, мономорфна; в сервисе она может видеть десять.
- **Версия движка.** Результат на v22 без Maglev не переносится на v24 с Maglev.
- **Доля в общем времени.** Ускорить функцию в 5 раз бессмысленно, если она занимает 1 % времени запроса (закон Амдала, 9.5).

Надёжный порядок: профиль реальной нагрузки → гипотеза → изменение → повторный профиль и нагрузочный тест (9.5). Микробенчмарк уместен только для проверки гипотезы о конкретной функции, и то с прогревом и использованием результата, как в 2.6.
