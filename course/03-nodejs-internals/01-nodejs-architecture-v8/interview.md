# 3.1 Архитектура Node.js и V8 — interview

> Вопросы проверяют, понимаете ли вы, где в Node.js выполняется работа (поток JavaScript, ядро ОС, пул потоков) и как V8 делает JavaScript быстрым, и умеете ли отделить полезное для backend от микрооптимизаций. Схема ответа: **тезис** → **подробно** → **ограничения** → **уточняющие вопросы**. Все фрагменты запущены на Node.js v22.22.2 (Windows 10 x64) как файлы `.cjs`; версионные отличия проверены на v24.22.0 и v26.12.0. Фрагменты с `%` запускаются с флагом `--allow-natives-syntax`: это внутренний API V8 для исследования, а не для production. Фазы event loop — 3.2, пул потоков и Worker Threads — 3.3, GC — 3.5.

**Как работать с заданиями.** Ответы спрятаны под раскрывающимися блоками.

1. Прочитайте вопрос или фрагмент кода.
2. Запишите или проговорите ответ: результат **и механизм**.
3. Раскройте эталон и сравните оба пункта.

Вопросы M — Middle, SM — Strong Middle, S — Senior.

## Конспект

- **Слои:** JavaScript API (`lib/`) → C++ bindings (`internalBinding`) → V8 (JavaScript, куча, GC, микрозадачи) и libuv (event loop, сокеты через epoll/kqueue/IOCP, пул потоков) → ОС. Плюс llhttp, OpenSSL, zlib, c-ares, undici и другие.
- **Node.js — хост для V8.** V8 не знает ни о файлах, ни о сети, ни о цикле событий.
- **Сеть** ждёт в ядре ОС, поток цикла обслуживает тысячи сокетов. **Файлы, `dns.lookup`, часть `crypto` и `zlib`** — в пуле libuv (по умолчанию 4 потока, создаётся лениво).
- **Процесс многопоточный:** основной поток JavaScript, 4 потока платформы V8 (`--v8-pool-size`), пул libuv, служебные потоки. Однопоточен только JavaScript на одном event loop.
- **Конвейер V8:** Ignition (байткод + обратная связь) → Sparkplug (baseline, без оптимизаций) → Maglev (быстрый оптимизирующий) → TurboFan (максимальная оптимизация). **В Node.js 22.9+ Maglev отключён**, в 24 и 26 включён.
- **Hidden class (map)** — форма объекта; зависит от порядка и способа добавления свойств. `delete` и объект-словарь → dictionary mode.
- **Inline cache:** monomorphic (1 map) → polymorphic (до 4) → megamorphic (больше 4, общий поиск).
- **Деоптимизация:** нарушено допущение → возврат в интерпретатор. Семантика не меняется, меняется скорость. Чаще всего причина — данные неожиданного типа.
- **Для backend:** не блокировать поток, валидировать данные на границе, стабильные формы в горячем коде, `Map` для словарей. Остальное — только по профилю.

## Вопросы уровня Middle

### M1. Из чего состоит Node.js и за что отвечает каждый слой?

<details>
<summary>Ответ</summary>

**Тезис.** Node.js — runtime, который встраивает движок V8 и библиотеку libuv и связывает их C++-кодом с JavaScript API. V8 исполняет JavaScript, libuv даёт event loop и ввод-вывод, bindings переводят вызовы между ними.

**Подробно.**
- **JavaScript API** (`lib/`): `fs`, `http`, `net`, `stream`, `crypto` — в основном JavaScript, проверка аргументов и удобный интерфейс.
- **C++ bindings** (`src/`): `internalBinding('fs')` и другие, превращают вызов в вызов libuv или библиотеки и вызывают колбэк с результатом.
- **V8:** парсер, интерпретатор, JIT, куча и GC, очередь микрозадач.
- **libuv:** цикл событий, неблокирующие сокеты через механизм ОС, пул потоков для файлов и `getaddrinfo`, таймеры, сигналы, дочерние процессы.
- **Библиотеки:** llhttp (HTTP/1.1), OpenSSL (TLS, crypto), zlib, c-ares (`dns.resolve*`), undici (`fetch`), ICU (Intl).

**Ограничения.** Версии всех слоёв видны в `process.versions`. Каждая мажорная линия Node.js держится на одной мажорной версии V8 (22 — 12.4, 24 — 13.6).

**Уточняющие вопросы.**
- *«Где в этой схеме event loop?»* — в libuv. V8 своего цикла не имеет, он только выполняет JavaScript, когда его вызывают.
- *«Где очередь микрозадач?»* — в V8. Очередь `process.nextTick` — в Node.js. Node.js выполняет обе после каждого колбэка ([1.5](../../01-javascript/05-event-loop-spec/)).
- *«Можно ли из своего кода вызвать binding напрямую?»* — `internalBinding` недоступен, `process.binding()` устарел (DEP0111) и недоступен при включённой модели разрешений ([P9](#p9-binding-и-пользовательский-код)).

</details>

### M2. Чем Node.js отличается от V8 и от JavaScript в браузере?

<details>
<summary>Ответ</summary>

**Тезис.** V8 — движок, Node.js и Chrome — два разных хоста для него. Язык один и тот же, различаются API хоста и устройство цикла событий.

**Подробно.**
- В браузере есть DOM, отрисовка, `window`, Web API. В Node.js — файлы, сокеты, процессы, `process`, `Buffer`, модули CommonJS.
- Event loop браузера описан стандартом HTML (task queues, microtask checkpoint, отрисовка). Event loop Node.js — фазы libuv плюс очередь `process.nextTick` (3.2).
- Даже V8 собран по-разному: в Chrome включено pointer compression, в официальных сборках Node.js нет ([P6](#p6-smi-в-nodejs-и-в-chrome)).

**Ограничения.** Часть Web API есть и в Node.js: `fetch`, `URL`, `AbortController`, Web Streams, `structuredClone`. Это реализации Node.js, а не браузерные.

**Уточняющий вопрос.** *«Что одинаково везде?»* — семантика языка: порядок promise jobs, run-to-completion, правила приведения типов. Это ECMAScript.

</details>

### M3. Что значит «неблокирующий ввод-вывод» и чем модель Node.js отличается от thread-per-request?

<details>
<summary>Ответ</summary>

**Тезис.** Неблокирующий ввод-вывод: поток не ждёт результата операции, а регистрирует интерес к событию и продолжает работу. Node.js обслуживает все соединения одним потоком JavaScript: ядро ОС сообщает, какие сокеты готовы, и цикл вызывает их обработчики. В модели thread-per-request на каждый запрос выделяется поток, который блокируется на вводе-выводе.

**Подробно.**
- В Node.js 10 000 ожидающих соединений стоят памяти на объекты и буферы, но не 10 000 потоков со стеками.
- Обратная сторона: JavaScript всех запросов выполняется по очереди. Долгое синхронное вычисление одного запроса задерживает все.
- В thread-per-request долгая работа одного запроса не мешает другим, но потоки дороги, а общая память требует синхронизации.

**Ограничения.** Аргумент «Node.js быстрее» без условий неверен. Для I/O-bound нагрузки модель Node.js эффективна. Для CPU-bound — нужны Worker Threads или процессы. Кроме того, Go (горутины) и Java 21 (виртуальные потоки) дают дешёвое ожидание при последовательном коде.

**Уточняющие вопросы.**
- *«Файловый I/O тоже неблокирующий?»* — для потока JavaScript да, но внутри libuv выполняет блокирующие вызовы в пуле потоков: общего неблокирующего файлового API в ОС нет.
- *«Как Node.js использует несколько ядер?»* — несколькими процессами (`cluster`, реплики), Worker Threads и пулом libuv (3.3).

</details>

### M4. Node.js однопоточный?

<details>
<summary>Ответ</summary>

**Тезис.** Нет. Однопоточно выполняется JavaScript на одном event loop. Сам процесс многопоточный: потоки V8 для фоновой компиляции и GC, пул потоков libuv, служебные потоки, Worker Threads, если их создать.

**Подробно.** На Windows 10 процесс v22.22.2 стартует с 13 потоками. `--v8-pool-size=1` уменьшает это число на 3 (по умолчанию потоков платформы V8 четыре). Первая файловая операция добавляет 4 потока пула libuv, с `UV_THREADPOOL_SIZE=8` — 8 ([P8](#p8-сколько-потоков-добавит-первый-fsreadfile)).

**Ограничения.** Точные числа зависят от ОС и версии. Устойчиво то, что пул libuv создаётся лениво и его размер задаётся переменной окружения до первого использования.

**Уточняющие вопросы.**
- *«Значит, в Node.js нужны мьютексы?»* — для обычного JavaScript нет: синхронный участок атомарен. Но между `await` состояние меняют другие обработчики, поэтому проверку и запись, разделённые `await`, защищают на уровне базы или явной сериализацией ([1.5](../../01-javascript/05-event-loop-spec/)).
- *«Когда появляются настоящие гонки по памяти?»* — при `SharedArrayBuffer` между Worker Threads, там нужен `Atomics` (3.3).

</details>

### M5. Что такое JIT-компиляция и зачем V8 интерпретатор, если есть компилятор?

<details>
<summary>Ответ</summary>

**Тезис.** JIT — компиляция в машинный код во время выполнения. V8 сначала исполняет байткод интерпретатором, потому что компиляция дорогая и для большинства функций не окупается. Оптимизирующие компиляторы тратят время только на горячий код и используют обратную связь, которую собрал интерпретатор.

**Подробно.**
- Ignition выполняет байткод и записывает, какие формы объектов и типы значений видела каждая операция.
- Sparkplug быстро переводит байткод в машинный код без оптимизаций.
- Maglev и TurboFan компилируют горячие функции с допущениями из обратной связи, в фоновом потоке.

**Ограничения.** Без обратной связи оптимизировать JavaScript сложно: тип значения заранее неизвестен. Поэтому оптимизированный код спекулятивный и может деоптимизироваться.

**Уточняющий вопрос.** *«Можно ли запустить V8 без JIT?»* — да, `--jitless` («Disable runtime allocation of executable memory»): только интерпретатор. Применяется там, где JIT запрещён политикой безопасности, ценой заметно меньшей скорости; WebAssembly в этом режиме недоступен (`typeof WebAssembly` — `undefined` на v22.22.2).

</details>

## Вопросы уровня Strong Middle

### SM6. Опишите путь вызова fs.stat от JavaScript до ОС и обратно

<details>
<summary>Ответ</summary>

**Тезис.** JavaScript создаёт объект запроса и вызывает binding, binding вызывает `uv_fs_stat`, libuv выполняет блокирующий `stat` в потоке пула, по завершении поток цикла вызывает C++-обработчик, тот — ваш колбэк, после чего выполняются `nextTick` и микрозадачи.

**Подробно** (v22.22.2).
1. `lib/fs.js`: проверка пути, `new FSReqCallback()`, `req.oncomplete = callback`, `binding.stat(path, bigint, req)`, где `binding = internalBinding('fs')`.
2. `src/node_file.cc`, `Stat`: `AsyncCall(…, uv_fs_stat, path)`. Возврат в JavaScript сразу.
3. libuv ставит работу в пул; поток пула вызывает `stat(2)` и сообщает циклу о завершении.
4. Поток цикла вызывает `AfterStat`, тот вызывает `oncomplete` через `MakeCallback`.
5. `InternalCallbackScope::Close` выполняет очередь `nextTick` и микрозадачи.

**Ограничения.** Для сети шаг 3 другой: сокет зарегистрирован в epoll/kqueue/IOCP, поток цикла сам читает данные, когда ОС сообщила о готовности; пул не участвует.

**Уточняющие вопросы.**
- *«Что будет, если запустить 100 `fs.stat` одновременно?»* — 4 выполняются в потоках пула, остальные ждут в очереди libuv. Event loop при этом свободен (3.3).
- *«А `fs.statSync`?»* — тот же `uv_fs_stat`, но без колбэка, прямо в потоке JavaScript: поток ждёт ОС.
- *«Почему колбэк не может выполниться раньше, чем закончится текущий синхронный код?»* — его вызывает поток цикла, а он занят вашим кодом до возврата управления (run-to-completion, [1.5](../../01-javascript/05-event-loop-spec/)).

</details>

### SM7. Какие уровни компиляции есть в V8 и какие из них работают в Node.js 22?

<details>
<summary>Ответ</summary>

**Тезис.** Четыре уровня: Ignition (интерпретатор), Sparkplug (baseline-компилятор), Maglev (быстрый оптимизирующий), TurboFan (оптимизирующий верхнего уровня). В Node.js 22 начиная с 22.9.0 Maglev отключён, функции идут из Sparkplug сразу в TurboFan. В Node.js 24 и 26 работают все четыре.

**Подробно.**
- Sparkplug компилирует байткод за один проход без промежуточного представления, работает очень быстро и не спекулирует.
- Maglev строит SSA-граф, использует обратную связь, компилирует примерно в 10 раз медленнее Sparkplug и в 10 раз быстрее TurboFan (по данным V8 для JetStream).
- TurboFan даёт максимальную скорость кода ценой долгой компиляции.
- Причина отключения Maglev в v22 из changelog: сбои и неожиданное поведение JavaScript в Maglev V8 12.4, исправления которых трудно переносить в LTS.

**Ограничения.** Пороги перехода между уровнями — флаги V8 (`--invocation-count-for-turbofan=3000` в V8 12.4) и зависят от размера байткода. Это деталь реализации.

**Уточняющие вопросы.**
- *«Как проверить, что Maglev в сборке есть?»* — `process.config.variables.v8_enable_maglev` и вывод `--trace-opt` ([P10](#p10-maglev-в-разных-версиях-nodejs)).
- *«Что это значит при обновлении с 22 на 24?»* — изменится путь оптимизации горячего кода, производительность может сдвинуться в обе стороны; обновление проверяют нагрузочным тестом ([S14](#s14-что-проверить-при-переходе-на-новую-мажорную-версию-nodejs-с-точки-зрения-производительности)).
- *«Где выполняется оптимизирующая компиляция?»* — в фоновом потоке (`ConcurrencyMode::kConcurrent` в `--trace-opt`), основной поток продолжает выполнять неоптимизированный код.

</details>

### SM8. Что такое hidden classes и когда у двух объектов разные формы?

<details>
<summary>Ответ</summary>

**Тезис.** Hidden class, во внутренних терминах V8 map, описывает форму объекта: набор свойств, порядок их добавления и расположение значений. Объекты, построенные одинаково, разделяют map, и доступ к свойству сводится к проверке map и чтению по смещению.

**Подробно.** Формы расходятся, если:
- свойства добавлены в другом порядке: `{ id, name }` и `{ name, id }`;
- объект создан другим способом: литерал `{ id, name }` и `{ id }` с последующим `o.name = …` в V8 12.4 имеют разные map ([P2](#p2-литерал-и-добавление-свойства));
- свойство добавляется условно: `if (x) o.email = x`;
- объект ушёл в dictionary mode: `delete`, много свойств с вычисляемыми ключами.

Одну форму дают класс с присваиванием всех полей в конструкторе и литерал с полным набором полей (отсутствующее значение — `null`, а не отсутствующий ключ).

**Ограничения.** Это поведение V8, а не языка. Правила создания и разделения map меняются между версиями.

**Уточняющие вопросы.**
- *«Почему это важно?»* — inline cache в месте доступа помнит map. Одна форма — быстрый мономорфный доступ, много форм — медленный общий поиск.
- *«Объекты из `JSON.parse` с одинаковыми ключами — одна форма?»* — в V8 12.4 да, если ключи идут в том же порядке ([P1](#p1-формы-объектов)).
- *«Поля класса (`class A { x = 1 }`) влияют на форму?»* — да, они определяются в порядке объявления до тела конструктора, и все экземпляры получают одинаковую начальную форму ([1.3](../../01-javascript/03-prototypes-classes/)).

</details>

### SM9. Что такое inline cache и чем мономорфный доступ отличается от мегаморфного?

<details>
<summary>Ответ</summary>

**Тезис.** Inline cache запоминает для конкретного места в коде, какие map там встречались и где у них лежит свойство. Мономорфное место видело одну map, полиморфное — до четырёх, мегаморфное — больше четырёх и переходит на общий поиск без специализации.

**Подробно.** В эксперименте с 5·10⁷ чтений `arr[i].x` на v22.22.2: 1 форма — 38 мс, 4 формы — 111 мс, 5 форм — 233 мс. Скачок между 4 и 5 — граница `max_valid_polymorphic_map_count = 4` ([P7](#p7-четыре-формы-или-пять)).

**Ограничения.** Худший случай — единицы наносекунд на доступ. Это важно для циклов на миллионы элементов и не важно для кода, который ждёт базу миллисекунды. Код фреймворков мегаморфен по природе.

**Уточняющие вопросы.**
- *«Как узнать, что место мегаморфное?»* — профиль показывает функцию горячей; дальше — исследование с `--allow-natives-syntax` или трассировкой IC на стенде. В production это не диагностируют напрямую.
- *«Как сделать место мономорфным?»* — нормализовать данные в одну форму до горячего цикла (класс или фабрика с полным набором полей) или разделить функцию по типам входа.

</details>

### SM10. Что такое деоптимизация и что её вызывает?

<details>
<summary>Ответ</summary>

**Тезис.** Оптимизированный код делает допущения по обратной связи и проверяет их. Если проверка не прошла или факт, на который код опирался, изменился, V8 восстанавливает состояние интерпретатора и продолжает выполнение в нём. Это деоптимизация.

**Подробно.**
- **Eager:** проверка не прошла сейчас: «wrong map» (другая форма или вид элементов массива), «not a Smi» (пришло не малое целое).
- **Lazy / code dependencies:** изменился факт о куче, например представление поля у объектов какой-то map, и зависимый код помечается к выбросу.
- Типичные причины в backend: строка вместо числа из внешнего JSON, объекты разных форм в одной функции, `undefined` в поле, где раньше всегда было число.

**Ограничения.** Деоптимизация не меняет результат, только скорость. После деоптимизации функция оптимизируется заново с более общими допущениями: при шести формах объекта — 5 оптимизаций и 4 деоптимизации, затем стабильный, но обобщённый код.

**Уточняющие вопросы.**
- *«Как увидеть деоптимизации?»* — `--trace-deopt` на стенде с теми же данными ([P5](#p5-цена-строкой)).
- *«Что исправлять: функцию или данные?»* — почти всегда данные: неожиданный тип — это ошибка контракта, которую закрывают валидацией на границе.
- *«Может ли деоптимизация объяснить неверный результат?»* — нет. Неверный результат при смешанных типах даёт сама семантика JavaScript, например `250 + "10"`.

</details>

### SM11. Почему delete считают вредным для производительности и чем его заменить?

<details>
<summary>Ответ</summary>

**Тезис.** `delete` переводит объект в dictionary mode: свойства хранятся в собственной хеш-таблице объекта, inline caches с ним не работают. Медленным становится последующий доступ к этому объекту в горячем коде.

**Подробно.** На v22.22.2, v24.22.0 и v26.12.0 `delete` любого свойства (первого, последнего, у литерала, у экземпляра класса) дал `%HasFastProperties === false`. Присваивание `undefined` форму сохраняет ([P3](#p3-delete-и-присваивание-undefined)).

Замены по задаче:
- словарь с добавлением и удалением ключей — `Map`;
- убрать поле из ответа API — построить новый объект без поля (деструктуризация `const { password, ...rest } = user`) или явный DTO;
- «сбросить» значение — присвоить `undefined` или `null`, если контракт это допускает.

**Ограничения.** Для объекта, который живёт один запрос, разница неизмерима. `obj.x = undefined` и `delete obj.x` различаются семантически: `'x' in obj`, `Object.keys` и `JSON.stringify` дают разный результат.

**Уточняющий вопрос.** *«Почему объект с 20 вычисляемыми ключами тоже стал словарём?»* — V8 считает объект, которому много свойств добавляют по динамическим именам, словарём. Порог — эвристика, в V8 12.4 он сработал на 20 свойствах, документации на него нет.

</details>

### S12. Что из устройства V8 реально влияет на backend-код и как это доказать?

<details>
<summary>Ответ</summary>

**Тезис.** Безусловно важны две вещи: не блокировать поток JavaScript и проверять данные на границе. Формы объектов, мономорфность и отказ от `delete` важны только в горячих местах, которые показал профиль. Доказательство — CPU-профиль под реальной нагрузкой, а не микробенчмарк.

**Подробно.**
1. Метрики: latency, event loop lag (3.2), CPU.
2. CPU-профиль (`--cpu-prof`, flamegraph — 9.5): доля функции в общем времени.
3. Если в топе собственный код без ввода-вывода — сначала алгоритм и объём данных.
4. Если функция горячая и алгоритм разумный — `--trace-deopt` и формы объектов на стенде.
5. Изменение подтверждают повторным профилем и нагрузочным тестом.

**Ограничения.** Ускорение функции, которая занимает 1 % времени запроса, ничего не даёт (закон Амдала). Результаты привязаны к версии V8.

**Уточняющие вопросы.**
- *«Пример, где V8-оптимизация действительно окупилась?»* — свой парсер или сериализатор, обработка массивов на сотни тысяч элементов, расчёты в цикле: там формы и типы данных видны в профиле.
- *«А что в типичном CRUD?»* — время уходит на базу, сеть, сериализацию JSON и код фреймворка. Оптимизация под V8 там почти никогда не первая задача.

</details>

### S13. Что такое Node-API и какие проблемы нативных аддонов оно не решает?

<details>
<summary>Ответ</summary>

**Тезис.** Node-API — C API для нативных аддонов с ABI-стабильностью между мажорными версиями Node.js: аддон, собранный для одной версии, работает на следующих без пересборки. Оно не решает привязку бинарника к ОС, архитектуре и libc, не защищает процесс от ошибок памяти в аддоне и не делает синхронный код аддона асинхронным.

**Подробно.**
- До Node-API аддоны писали на API V8 (`nan`) и пересобирали под каждое значение `process.versions.modules` (127 для v22).
- Бинарник для glibc не загрузится в Alpine (musl), для x64 — на arm64. Пакеты публикуют prebuilt-сборки; при их отсутствии сборка идёт через `node-gyp`, и в образе нужен компилятор (11.3).
- Ошибка памяти в аддоне — падение процесса, а не исключение.
- Тяжёлую работу аддон должен выносить в пул libuv (`napi_create_async_work`), иначе блокирует цикл.

**Ограничения.** Альтернатива — WebAssembly: переносимый бинарник без сборки под платформу, но обычно медленнее нативного кода и выполняется в потоке JavaScript, если не вынесен в Worker.

**Уточняющие вопросы.**
- *«bcrypt или bcryptjs?»* — `bcrypt` (6.0.0) нативный, его асинхронный API считает хеш в пуле потоков: «The async version uses a thread pool which does not block the main event loop». `bcryptjs` (3.0.3) — чистый JavaScript: синхронная версия блокирует цикл, асинхронная «split an operation into small chunks» и уступает между порциями, но вычисляет всё равно в основном потоке. Встроенный `crypto.scrypt` с колбэком тоже работает в пуле libuv и не требует аддона (выбор алгоритма — 8.1, пул — 3.3).
- *«Почему после смены базового образа сервис не стартует с ошибкой загрузки `.node`?»* — бинарник собран под другую libc или архитектуру.

</details>

### S14. Что проверить при переходе на новую мажорную версию Node.js с точки зрения производительности?

<details>
<summary>Ответ</summary>

**Тезис.** Новая мажорная версия Node.js — это новая мажорная версия V8 и, возможно, другой набор уровней компиляции, другой GC и другие значения по умолчанию. Производительность проверяют нагрузочным тестом на реальном сценарии до и после, а не по changelog.

**Подробно.**
- V8: 22 → 12.4, 24 → 13.6, 26 → 14.6. С 24 включён Maglev.
- libuv: меняется поведение цикла и таймеров (3.2).
- Значения по умолчанию, связанные с памятью и контейнером (3.5, 11.3).
- Нативные аддоны: работают ли prebuilt-бинарники (Node-API стабилен, аддоны на `nan` — нет).
- Метрики после выкатки: p95/p99, event loop lag, CPU, RSS, частота и длительность GC.

**Ограничения.** Внутри LTS-линии мажорная версия V8 не меняется, но патчи Node.js могут менять поведение: пример — отключение Maglev в 22.9.0.

**Уточняющие вопросы.**
- *«Как откатиться, если стало хуже?»* — canary-выкатка и сравнение метрик с текущей версией (11.3); версия Node.js фиксируется в образе, а не берётся «последней».
- *«Почему в одной LTS-линии могут быть разные уровни компиляции?»* — Node.js может включать и отключать возможности V8 на уровне сборки, как было с Maglev.

</details>

### S15. Как сократить время старта Node.js-сервиса?

<details>
<summary>Ответ</summary>

**Тезис.** Старт складывается из загрузки и компиляции модулей, выполнения их верхнего уровня и инициализации приложения (подключения к базе, DI). Сокращают объём загружаемого кода, кешируют компиляцию и откладывают необязательную инициализацию.

**Подробно.**
- Меньше зависимостей и ленивый `require`/`import()` для редко используемых модулей (3.6).
- Module compile cache (Node.js 22.1+): `module.enableCompileCache()` или `NODE_COMPILE_CACHE` хранит код-кеш V8 на диске; кеш не переносится между версиями Node.js.
- Сборка в один файл бандлером уменьшает число операций с файлами при разрешении модулей.
- Startup snapshot (`--build-snapshot`) — сохранённое состояние кучи после инициализации; в v22 экспериментальный, работает с одним файлом (приложение собирают бандлером) и с частью встроенных модулей.
- Инициализация, которую можно отложить (прогрев кешей), — после того, как readiness probe сообщила о готовности, или в фоне.

**Ограничения.** Compile cache в v22 — «Active Development». `--build-snapshot` в v22 — «Experimental»: «User-land modules are not yet supported in the snapshot, so only one single file can be snapshotted».

**Уточняющий вопрос.** *«Когда это вообще важно?»* — serverless с холодными стартами, быстрое автомасштабирование, CLI. Для долгоживущего сервиса за балансировщиком важнее корректная readiness probe (11.5).

</details>

### S16. Почему микробенчмарки JavaScript часто вводят в заблуждение?

<details>
<summary>Ответ</summary>

**Тезис.** Микробенчмарк измеряет поведение JIT на искусственных данных: прогрев, удаление мёртвого кода, обратная связь от одной формы объектов. На реальной нагрузке функция видит другие данные, другую версию V8 и занимает другую долю времени.

**Подробно.**
- Без прогрева измеряется компилятор, а не код.
- Неиспользованный результат оптимизатор может выбросить.
- В бенчмарке функция мономорфна, в сервисе — нет.
- Результат v22 (без Maglev) не переносится на v24.
- Ускорение функции, которая занимает 1 % времени, незаметно.

**Ограничения.** Микробенчмарк полезен для проверки гипотезы о конкретной функции, которую профиль уже показал горячей. Тогда нужны прогрев, использование результата, новая функция на каждый вариант (свой feedback vector) и несколько запусков.

**Уточняющий вопрос.** *«Как тогда доказать эффект оптимизации?»* — повторный CPU-профиль и нагрузочный тест реального сценария с перцентилями (9.5).

</details>

## Предскажи результат

Каждый фрагмент — отдельный файл `.cjs`. Фрагменты с `%` запускаются с `--allow-natives-syntax`. Запишите точный вывод и одну-две фразы о механизме, затем раскройте ответ. P1–P5 — обязательная часть, P6–P10 сложнее или зависят от версии.

### P1. Формы объектов

```js
const a = { id: 1, name: 'a' };
const b = { id: 2, name: 'b' };
const c = { name: 'c', id: 3 };
class User { constructor(id, name) { this.id = id; this.name = name; } }
const p = JSON.parse('{"id":1,"name":"a"}');
const q = JSON.parse('{"id":2,"name":"b"}');
console.log(%HaveSameMap(a, b), %HaveSameMap(a, c));
console.log(%HaveSameMap(new User(1, 'x'), new User(2, 'y')), %HaveSameMap(new User(1, 'x'), a));
console.log(%HaveSameMap(p, q));
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:**
```
true false
true false
true
```

**Почему:** `a` и `b` — один литерал; `c` — другой порядок свойств, другая ветка переходов. Экземпляры класса разделяют map друг с другом, но не с литералом: у них другой конструктор и прототип. Объекты из `JSON.parse` с одинаковыми ключами в том же порядке в V8 12.4 разделяют map.

</details>

### P2. Литерал и добавление свойства

```js
const a = { id: 1, name: 'a' };
const d = { id: 4 }; d.name = 'd';
function toDto(row) {
  const dto = { id: row.id };
  if (row.email) dto.email = row.email;
  dto.name = row.name;
  return dto;
}
console.log(%HaveSameMap(a, d));
console.log(%HaveSameMap(toDto({ id: 1, name: 'a', email: 'a@x' }), toDto({ id: 2, name: 'b' })));
console.log(%HaveSameMap(toDto({ id: 1, name: 'a' }), toDto({ id: 2, name: 'b' })));
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `false`, `false`, `true`.

**Почему:** `d` пришёл к тем же свойствам в том же порядке, но другим путём: литерал с одним свойством и последующее добавление. Формы различаются. `toDto` с `email` и без даёт две формы. Два вызова без `email` идут по одной цепочке переходов — одна форма.

</details>

### P3. delete и присваивание undefined

```js
const f = { id: 6, name: 'f' };
delete f.name;
const g = { id: 7, name: 'g' };
g.name = undefined;
console.log(%HasFastProperties(f), %HasFastProperties(g));
console.log(Object.keys(f), Object.keys(g), JSON.stringify(g));
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:**
```
false true
[ 'id' ] [ 'id', 'name' ] {"id":7}
```

**Почему:** `delete` перевёл `f` в dictionary mode. Присваивание `undefined` сохранило форму `g`, но ключ `name` остался: `Object.keys` его видит, а `JSON.stringify` пропускает свойства со значением `undefined`. Выбор между `delete` и `undefined` — это прежде всего выбор семантики.

</details>

### P4. Элементы массива после push и перезаписи

```js
const a = [1, 2, 3];
const c = [1, 2, 3]; c.push(4.5); c[3] = 4;
const d = new Array(3); d[0] = 1; d[1] = 2; d[2] = 3;
console.log(%HasSmiElements(a), %HasDoubleElements(c), %HasHoleyElements(d), %HasHoleyElements(a));
```

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** `true true true false`.

**Почему:** вид элементов меняется только в сторону обобщения. После `4.5` массив стал DOUBLE и остался им после записи целого. `new Array(3)` создаёт массив с дырами, и он остаётся HOLEY после заполнения. На скорость реального backend-кода это почти не влияет, но объясняет «wrong map» в `--trace-deopt`.

</details>

### P5. Цена строкой

```js
function orderTotal(order) {
  let sum = 0;
  for (const item of order.items) sum += item.price * item.qty;
  return sum + order.shipping;
}
const body = (shipping) => JSON.stringify({ items: [{ price: 100, qty: 2 }, { price: 50, qty: 1 }], shipping });
for (let i = 0; i < 50000; i++) orderTotal(JSON.parse(body(10)));
console.log('number shipping:', orderTotal(JSON.parse(body(10))));
console.log('string shipping:', orderTotal(JSON.parse(body('10'))));
```

Что напечатается и что покажет запуск с `--trace-deopt`?

<details>
<summary>Ответ и объяснение</summary>

**Ответ:**
```
number shipping: 260
string shipping: 25010
```
В `--trace-deopt` среди прочего: `[marking dependent code … <SharedFunctionInfo orderTotal> … for deoptimization, reason: code dependencies]`.

**Почему:** `250 + "10"` — конкатенация, это семантика JavaScript, оптимизация ни при чём. Объект с полем-строкой меняет представление поля у этой формы, и оптимизированный `orderTotal`, который на него опирался, помечается к деоптимизации. Исправление — валидация на границе ([theory, раздел 3](./theory.md#3-сценарий-цена-строкой-ломает-расчёт-заказа)).

</details>

### P6. Smi в Node.js и в Chrome

```js
console.log(%IsSmi(2 ** 31 - 1), %IsSmi(2 ** 31), %IsSmi(1.5), %IsSmi(-0));
console.log(process.config.variables.v8_enable_pointer_compression);
```

Что выведет Node.js v22.22.2? Совпадёт ли первая строка с Chrome?

<details>
<summary>Ответ и объяснение</summary>

**Ответ:**
```
true false false false
0
```

**Почему:** официальные сборки Node.js собраны без pointer compression, и Smi там 32-битный: `2 ** 31 - 1` помещается. В Chrome включено pointer compression, Smi 31-битный, и `2 ** 31 - 1` там не Smi. `1.5` и `-0` — не целые в смысле Smi (`-0` нельзя представить целым), они хранятся как HeapNumber. Тот же результат на v24.22.0.

</details>

### P7. Четыре формы или пять

Функция `sumX(arr)` читает `arr[i].x` для 10⁵ объектов, 500 проходов. В одном варианте объекты имеют 4 разные формы, в другом — 5. Каждый вариант использует новую функцию со своим feedback vector. Во сколько раз отличается время?

<details>
<summary>Ответ и объяснение</summary>

**Ответ:** примерно в 2 раза: на v22.22.2 — 111 мс для 4 форм и 233 мс для 5 (один запуск, повторные отличались на 10–25 %). Для сравнения: 1 форма — 38 мс, 32 формы — 218 мс.

**Почему:** до 4 map inline cache полиморфный — цепочка проверок, время растёт с числом форм. С пятой картой место становится мегаморфным (`max_valid_polymorphic_map_count = 4`) и переходит на общий поиск. Дальше время почти не растёт: общий поиск стоит одинаково для 5 и 32 форм.

</details>

### P8. Сколько потоков добавит первый fs.readFile

```js
const { execSync } = require('child_process');
const fs = require('fs');
const count = () => Number(execSync(
  `powershell -NoProfile -Command "(Get-Process -Id ${process.pid}).Threads.Count"`).toString().trim());
```

<summary>Ответ и объяснение</summary>

**Почему:** пул libuv создаётся при первой операции, которой он нужен, и сразу целиком: 4 потока по умолчанию, 8 — если так задано переменной окружения до старта. Остальные 13 потоков существуют с запуска: основной, 4 потока платформы V8 и служебные. Точные числа зависят от ОС: в Linux-контейнере (`node:22.22.2-slim`) процесс стартует с 7 потоками, и первый `fs.readFile` так же добавляет 4.

</details>

### P10. Maglev в разных версиях Node.js

```js
function add(a, b) { return a + b; }
```

## Задачи на выбор решения

Формат: условия → варианты → выбор → при каких условиях выбор перестаёт быть верным.

### В1. Оптимизировать горячую функцию под V8 или нет

**Условия.** Сервис отчётов строит агрегаты: загружает из базы 300 тысяч строк, нормализует их и считает суммы по группам. p99 эндпоинта — 4 с, SLO — 1 с. CPU-профиль под нагрузкой: 60 % времени в `normalizeRow` и `aggregate`, 25 % в драйвере базы и `JSON.parse`, остальное — фреймворк. `normalizeRow` добавляет поля условно, в зависимости от типа строки (6 типов), `aggregate` читает поля результата в цикле.

**Варианты:** переписать `normalizeRow` так, чтобы все строки имели одну форму; вынести расчёт в Worker Thread; перенести агрегацию в SQL (`GROUP BY`); оставить код и добавить инстансов.

<details>
<summary>Разбор</summary>

**Выбор.** Перенести агрегацию в SQL: база считает суммы по группам без передачи 300 тысяч строк по сети и без их разбора в JavaScript. Это убирает и 60 % в `normalizeRow` / `aggregate`, и большую часть 25 % на драйвер и `JSON.parse`.

**Почему не остальные.**
- Стабильная форма объектов, вероятно, ускорит `aggregate` (место доступа сейчас мегаморфное: 6 форм), но не уберёт передачу и разбор 300 тысяч строк. Это вторая по ценности мера, если SQL невозможен.
- Worker Thread убирает блокировку event loop для других запросов, но не ускоряет сам отчёт: та же работа на другом ядре плюс копирование данных.
- Новые инстансы не уменьшают время одного запроса: p99 определяется работой внутри запроса.

**Когда выбор перестаёт быть верным.**
- Нормализация требует логики, которую нельзя выразить в SQL (вызовы внешних сервисов, сложные правила) — тогда одна форма объектов плюс Worker Thread, чтобы не блокировать другие запросы.
- База — общий ресурс под нагрузкой, и тяжёлый `GROUP BY` замедлит другие сервисы — тогда реплика для отчётов или предрасчёт агрегатов по событию (5.9, 10.x).
- Профиль показал бы 60 % в драйвере и `JSON.parse` — тогда смотреть на объём выборки и формат, а не на формы объектов.

</details>

### В2. Нативный аддон, WebAssembly или чистый JavaScript

**Условия.** Сервису нужна обработка изображений (ресайз аватаров) — около 50 изображений в секунду в пике. Образ Docker сейчас на `node:22-alpine`, CI собирает образы для amd64 и arm64. Кандидаты: `sharp` (нативный, на libvips), библиотека на WebAssembly, библиотека на чистом JavaScript.

<details>
<summary>Разбор</summary>

**Выбор.** `sharp`: нативный код на libvips быстрее остальных вариантов, а задачи выполняются вне потока JavaScript — в документации `sharp.queue` описан как очередь задач, «waiting for libuv to provide a worker thread». Поэтому event loop не блокируется при 50 изображениях в секунду. Проблему платформы решают prebuilt-бинарниками: у `sharp` 0.35.5 среди опциональных зависимостей есть `@img/sharp-linuxmusl-x64` и `@img/sharp-linuxmusl-arm64`, так что Alpine на обеих архитектурах покрыт. Для другой библиотеки это проверяют до выбора, иначе — образ на glibc (`node:22-slim`). Пропускную способность ограничивает пул libuv (по умолчанию 4 потока, 3.3).

**Почему не остальные.**
- WebAssembly переносим и не требует сборки, но обычно медленнее нативного кода и выполняется в потоке, который его вызвал: без Worker Thread он блокирует event loop.
- Чистый JavaScript — самый медленный вариант, и вся работа идёт в основном потоке.

**Когда выбор перестаёт быть верным.**
- Нагрузка мала (единицы изображений в минуту), а простота сборки важнее — WebAssembly в Worker Thread.
- Среда не позволяет нативные аддоны (некоторые serverless-платформы) — WebAssembly или внешний сервис обработки изображений. Если запрещён и JIT (`--jitless`), WebAssembly тоже недоступен: на v22.22.2 с этим флагом `typeof WebAssembly === 'undefined'` — остаётся внешний сервис.
- Обработка тяжёлая и пиковая — отдельный сервис или очередь (10.2), чтобы не делить CPU с API.

</details>

Полный разбор — в [theory.md, раздел 6](./theory.md#6-ошибки-и-заблуждения). На собеседовании чаще всего звучат три:
- «Node.js однопоточный»;
- «V8 оптимизирует код по типам TypeScript»;
- «в Node.js 22 есть Maglev» (только до 22.9.0).

## Как отличить поверхностный ответ от сильного

| Тема | Поверхностный ответ | Сильный ответ |
|---|---|---|
| Что такое Node.js | «JavaScript на сервере» | хост для V8: libuv, bindings, системные API; V8 не знает о вводе-выводе |
| Потоки | «Node.js однопоточный» | однопоточен JavaScript на event loop; называет потоки V8, пул libuv, Worker Threads, процессы |
| Асинхронный I/O | «всё асинхронное выполняется в фоне» | различает сеть (ядро ОС, поток цикла) и файлы, `dns.lookup`, crypto (пул libuv из 4 потоков) |
| JIT | «V8 компилирует JavaScript в машинный код» | описывает уровни, обратную связь, спекуляцию и деоптимизацию; знает о Maglev по версиям |
| Hidden classes | «нужно объявлять все поля» | объясняет переходы map, роль порядка и способа создания, dictionary mode; знает, где это важно |
| Оптимизация | «избегать `delete` и `try/catch`» | начинает с профиля, оценивает долю функции, исправляет данные и алгоритм, а не «подстраивается под V8» |
| Обновление Node.js | «стало быстрее» | меняется V8, libuv, значения по умолчанию; проверяет нагрузочным тестом и метриками |
