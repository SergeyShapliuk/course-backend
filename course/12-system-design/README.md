## Цель блока

Собрать знания курса в умение проектировать системы и защищать решения через trade-offs. Блок покрывает два типа Senior-интервью: архитектуру кода (принципы, слои, DDD) и system design (данные, масштабирование, согласованность, отказоустойчивость). Завершается методикой прохождения system design сессии.

Блок учит **выбирать архитектуру под ограничения**, а не пересказывать CAP, DDD и микросервисы. Каждый урок строится по одной схеме: исходные условия (нагрузка, объём данных, SLO, размер команды, бюджет) → варианты → цена каждого варианта → решение → условия, при которых решение перестаёт работать. Оценка нагрузки и поиск узкого места — обязательная часть каждого разбора, а не только урока 12.8.

## Состав уроков

**12.1 Принципы проектирования.** SOLID с примерами нарушений в NestJS-коде · coupling и cohesion · DRY, KISS, YAGNI и их конфликты · composition over inheritance · Law of Demeter.

**12.2 Clean и Hexagonal Architecture.** Dependency rule · ports и adapters · слои: domain, application, infrastructure, presentation · реализация в NestJS: модули, токены для портов · когда это избыточно и как выглядит прагматичная версия.

**12.3 DDD, CQRS, Event Sourcing.** Стратегический DDD: ubiquitous language, bounded contexts, context map · тактический DDD: entities, value objects, aggregates и их границы, domain events, repositories · CQRS: от разделения моделей до разных хранилищ · Event Sourcing: когда оправдан и чего стоит.

**12.4 Modular monolith и microservices.** Модульный монолит как разумный старт · критерии декомпозиции · синхронное против асинхронного взаимодействия · API gateway, BFF, service mesh · владение данными и database per service · распределённый монолит как антипаттерн.

**12.5 CAP, PACELC, модели согласованности.** CAP-теорема и частые заблуждения о ней · PACELC · linearizability, sequential, causal, eventual consistency · read-your-writes, monotonic reads · кворумы (R + W > N) и их ограничения.

**12.6 Масштабирование данных.** Leader-follower, multi-leader, leaderless репликация · шардирование: по хешу, по диапазону, consistent hashing · ребалансировка · горячие ключи и партиции · генерация глобальных ID (UUIDv7, Snowflake) · cross-shard запросы.

**12.7 Конкурентность и отказоустойчивость.** Race conditions, lost update, double spend · сквозная идемпотентность от клиента до базы · физические и логические часы: Lamport, vector clocks, HLC · fault tolerance: retries, timeouts, деградация функциональности · технический долг: как измерить и как продать его погашение.

**12.8 System design интервью.** Структура сессии: требования (функциональные и нефункциональные), оценка нагрузки (back-of-the-envelope), API, модель данных, high-level design, deep dives, узкие места · как вести trade-off диалог · теоретический разбор 2–3 кейсов: URL shortener, система уведомлений, платёжный поток.

## Заблуждения, которые нужно развенчать

- **«Микросервисы масштабируются лучше монолита».** Масштабируется архитектура со stateless-узлами и разделёнными данными. Микросервисы добавляют сетевые сбои, распределённые транзакции и операционную стоимость. *(12.4)*
- **«CAP: выбираем любые два свойства из трёх».** От partition tolerance отказаться нельзя. При разделе сети выбор между C и A, а без раздела, по PACELC, — между latency и consistency. *(12.5)*
- **«Eventual consistency означает, что гарантий нет».** Есть промежуточные модели с конкретными гарантиями: read-your-writes, monotonic reads, causal consistency. *(12.5)*
- **«Clean Architecture — это много слоёв и интерфейсов».** Суть в направлении зависимостей. Количество слоёв — компромисс, а не требование. *(12.2)*
- **«Агрегат — это сущность со всеми связями».** Агрегат — граница транзакционной согласованности. Агрегаты делают маленькими и ссылаются друг на друга по ID. *(12.3)*
- **«Идемпотентность достаточно обеспечить на уровне API».** Она нужна по всей цепочке: API, очередь, консьюмер, вызовы внешних систем. *(12.7)*
- **«На system design интервью нужно показать как можно больше технологий».** Оценивают уточнение требований, оценку нагрузки, поиск узких мест и обоснование компромиссов. Лишний компонент без причины — минус, а не плюс. *(12.8)*

## Что должно быть получено

- Провожу system design сессию по структуре и защищаю каждое решение через альтернативы и их цену.
- Объясняю, когда микросервисы оправданы, а когда модульный монолит лучше, на примере конкретной команды и нагрузки.
- Проектирую платёжный поток без двойного списания при сбоях сети и повторах.
